# Feature Specification: Book Chapter Outline

**Feature Branch**: `003-book-chapter-outline`  
**Created**: 2025-10-23  
**Status**: Draft  
**Input**: User description: "書籍の企画をまとめ、全体の章立てを作成する。執筆進行に従い変更可能。インタビュー形式で情報収集。"

## User Scenarios & Testing

### User Story 1 - 全体構造の把握 (Priority: P1)

著者・編集者・レビュアーが書籍全体の構成を理解し、各章の位置づけと依存関係を把握できる。

**Why this priority**: 執筆計画の基盤となる最重要ドキュメント。全ての章の詳細仕様作成の前提となる。

**Independent Test**: 章立てファイルを読んで、読者の学習順序と各章の目的が理解できることを確認。Part構成とページ配分が妥当か判断できる。

**Acceptance Scenarios**:

1. **Given** 章立てファイルが存在する、**When** ファイルを開く、**Then** 序文〜付録まで全16章+付録の構成が一覧できる
2. **Given** 特定の章を確認したい、**When** 章タイトルと概要を読む、**Then** その章で何を学ぶか理解できる
3. **Given** 執筆順序を決めたい、**When** 章の依存関係を確認する、**Then** どの章から書き始められるか判断できる

---

### User Story 2 - 各章の詳細仕様作成の起点 (Priority: P1)

各章の執筆時に、この章立てを参照して独立したfeature specificationを作成できる。

**Why this priority**: 各章を独立したfeatureとして管理するワークフローの起点。章ごとの並行作業を可能にする。

**Independent Test**: 任意の章（例：第1章）について、章立ての情報をもとに `/speckit.specify 第1章の詳細仕様` を実行し、適切なspecが生成できる。

**Acceptance Scenarios**:

1. **Given** 第5章の詳細を書きたい、**When** 章立てで第5章の概要と想定ページ数を確認、**Then** 詳細specを作成する材料が揃う
2. **Given** 複数章を並行執筆したい、**When** 依存関係のない章を特定、**Then** 独立して作業開始できる
3. **Given** 全体のページ数を調整したい、**When** 各章の想定ページ数を集計、**Then** 目標300-400ページに収まるか判断できる

---

### User Story 3 - 執筆進行に応じた構成変更 (Priority: P2)

執筆を進める中で、章の順序変更、章の分割・統合、新章の追加が必要になった際に、章立てを更新できる。

**Why this priority**: 「執筆進行に従い変更を繰り返す」という要件に対応。柔軟性を確保。

**Independent Test**: 章立てファイルを編集し、章番号を振り直し、依存関係を更新して、変更履歴をコミットできる。

**Acceptance Scenarios**:

1. **Given** 第3章が長すぎる、**When** 第3章を3-A, 3-Bに分割、**Then** 以降の章番号が自動調整される（または手動で整合性を保てる）
2. **Given** 新しいトピックを追加したい、**When** 適切な位置に新章を挿入、**Then** 全体構成の整合性が保たれる
3. **Given** Part構成を見直したい、**When** 章のPartを移動、**Then** 学習フローが改善される

---

### Edge Cases

- 章の依存関係が循環している場合（第5章が第7章を前提とし、第7章が第5章を前提とする）
- 想定ページ数の合計が目標範囲（300-400p）を大幅に超える場合
- 特定のPartに章が集中しすぎて、バランスが悪い場合
- 前提知識の章（Part 1, 2）のページ数が多すぎて、読者が実践編に到達する前に離脱するリスク

## Requirements

### Functional Requirements

- **FR-001**: 章立てファイルは、序文、Part 1〜6、付録の構成を含むこと
- **FR-002**: 各章には、章番号、章タイトル、1-2行の概要、想定ページ数を含むこと
- **FR-003**: 各章の概要には「何を学ぶか」が明記されていること
- **FR-004**: 章の依存関係（前提となる章）が明示されていること（該当する場合）
- **FR-005**: 全体で16章（序文含む）+ 付録2つの構成であること
- **FR-006**: Part 1は基礎知識（2章）、Part 2は通信規格詳細（2章）、Part 3はファームウェア（4章）、Part 4はアプリケーション（3章）、Part 5はプロジェクト実践（3章）、Part 6はデバッグ（2章）の配分であること
- **FR-007**: 技術スタックとして、nRF52840 + nRF Connect SDK 3.0、iOS Core Bluetooth、Web Bluetooth API、Android概要が明記されていること
- **FR-008**: プロジェクト実践編に、ビーコン、温度計、OTA（DFU）の3つのプロジェクトが含まれること
- **FR-009**: ファームウェア編に、低消費電力設計、4線IF、LTE統合の内容が含まれること
- **FR-010**: 序文に、GitHub公開とビルド方法の説明が含まれることが明記されていること
- **FR-011**: 序文に、前提知識（micro:bit等の推奨教材）の紹介が含まれることが明記されていること
- **FR-012**: 各章の想定ページ数の合計が、目標範囲300-400ページに収まる配分であること
- **FR-013**: 章立てファイルは、Markdown形式で `manuscript/outline.md` に配置されること
- **FR-014**: 各Partの冒頭に、そのPartの目的と含まれる章の概要が記載されていること
- **FR-015**: 章立てファイルには、最終更新日と変更履歴セクションが含まれること

### Key Entities

- **書籍全体構造**: タイトル、対象読者、学習目標、総ページ数、Part構成
- **Part（部）**: Part番号、Partタイトル、目的、含まれる章のリスト
- **Chapter（章）**: 章番号、章タイトル、概要、想定ページ数、前提章、所属Part
- **技術スタック情報**: ハードウェア（nRF52840）、SDK（nRF Connect SDK 3.0）、アプリプラットフォーム（iOS, Web, Android概要）
- **プロジェクト実践例**: プロジェクト名（ビーコン、温度計、OTA）、対応章
- **変更履歴**: 日付、変更内容、変更理由

## Success Criteria

### Measurable Outcomes

- **SC-001**: 著者が章立てファイルを見て、30秒以内に任意の章の目的と想定ページ数を把握できる
- **SC-002**: 各章の詳細spec作成時に、章立てファイルの情報で「何を書くべきか」が明確になる（著者フィードバックで確認）
- **SC-003**: 全16章の想定ページ数合計が、300-400ページの範囲内に収まる（±10%の誤差許容）
- **SC-004**: Part 1-2（基礎・規格）、Part 3-4（実装）、Part 5-6（実践・デバッグ）のページ配分が、概ね 3:4:3 の比率になる
- **SC-005**: 章立てファイルを初めて見る編集者が、15分以内に書籍全体の構成と学習フローを理解できる
- **SC-006**: 執筆進行中に章の順序変更や追加が発生した場合、1時間以内に章立てファイルを更新し整合性を保てる
- **SC-007**: 章立てファイルに基づいて、各章の詳細specを独立して作成でき、並行執筆が可能になる
- **SC-008**: 技術レビュアーが章立てファイルを見て、「ファーム・アプリの連携を学べる構成」になっていると評価する（5段階で4以上）
- **SC-009**: 全章の依存関係を確認し、循環参照や前提知識の抜けがないことを検証できる

## Assumptions

- 章立ては執筆開始前に確定するが、執筆中の変更は許容される（変更履歴で管理）
- 各章の詳細な節構成、コード例、図表は、各章の独立したfeature specで定義する
- 想定ページ数は目安であり、実際の執筆で±20%の変動は許容される
- 読者は「高校生レベルの基礎知識 + micro:bit等のSTEM教材経験」を持つと仮定
- GitHub公開リポジトリでMarkdown原稿を管理し、Pandocでビルドする前提
- プロジェクト実践編（Part 5）は、Part 3, 4の知識を統合して進めるため、Part 3, 4の後に配置
- デバッグ編（Part 6）は、実装経験を踏まえて理解が深まるため、最後に配置

## Out of Scope

- 各章の詳細な節構成（これは各章の独立specで定義）
- 具体的なコード例やサンプルプログラム（各章のspecで定義）
- 図表の詳細なレイアウトや画像リソース（各章のspecで定義）
- 執筆スケジュールや担当者アサイン（プロジェクト管理の範囲）
- 出版社との契約や販売戦略（ビジネスの範囲）
- 書籍の表紙デザインやレイアウト（デザインの範囲）

## Notes

### 書籍企画の核心

この書籍の最大の特徴は、**「BLE開発における各担当者（ファーム/アプリ/企画）がBLE知識をもとに会話し、技術的連携を生み出す」**ことを目的としている点です。SDKで隠蔽された通信の実態を理解し、チーム全体で共通言語を獲得することが、プロジェクト成功の鍵になります。

### 想定読者の特性

- 組み込みエンジニア、モバイルアプリ開発者、プロダクトマネージャー、ホビイスト
- 各自は自分野の専門家だが、BLE自体の専門家ではない
- ファームウェアとアプリの連携を理解し、良い体験を生み出したい
- 問題発生時に、パケットキャプチャで原因を特定し解決できるレベルを目指す

### 学習スタイル

- 1回目：通読で概要把握
- 2回目以降：目次から必要箇所を引く「リファレンス的使い方」
- 頭から最後まで読む必要はない

### 技術的焦点

- **OTA（DFU）実装**: トラブルが多いため重点解説
- **低消費電力設計**: 4線IF、LTE統合パターンの実装とOTA
- **パケットレベルのデバッグ**: SDKの裏側で何が起きているか可視化

### GitHub公開とコミュニティ

- 本文とコード全てをGitHubでパブリック公開
- 誤字脱字や技術的指摘はGitHubイシューで受付
- ビルドシステム（Pandoc + Makefile）も含めて公開し、読者が自分でビルド可能
