# Feature Specification: Chapter 1 - What is BLE

**Feature Branch**: `004-chapter-01-what-is-ble`  
**Created**: 2025-10-23  
**Status**: Draft  
**Input**: User description: "第1章、BLEとは何か、の執筆。章の詳細を組み立てる。次に文を書いて、レビューをする、これを繰り返していく。本文は人が書くが、概要を書いて詳細の文章を書くのを依頼することもある。柔軟なやりとりとその繰り返しで本文を書いていくフローを用いたい。"

## User Scenarios & Testing

### User Story 1 - 章構成の組み立て (Priority: P1)

著者が第1章の詳細な節構成（1.1, 1.2, ...）を作成し、各節の目的と内容を明確化できる。

**Why this priority**: 執筆の設計図となる最重要タスク。節構成なしでは執筆開始できない。

**Independent Test**: 節構成ファイルを読んで、18-22ページ分の内容が適切に分割され、学習の流れが理解できることを確認。

**Acceptance Scenarios**:

1. **Given** 全体アウトライン（outline.md）の第1章概要がある、**When** 詳細な節構成を作成、**Then** 5-7節に分割され各節の目的が明確
2. **Given** 節構成案ができた、**When** 著者がレビュー、**Then** 内容の過不足や順序の問題を指摘し調整できる
3. **Given** 確定した節構成、**When** 想定ページ数を配分、**Then** 各節が2-4ページ程度で18-22ページ合計に収まる

---

### User Story 2 - 柔軟な執筆とレビューの繰り返し (Priority: P1)

著者が節ごとに「概要を書く → AIに詳細執筆を依頼 → レビュー → 修正」のサイクルを繰り返し、本文を完成させる。

**Why this priority**: 執筆の中核プロセス。柔軟なやり取りで質の高い本文を生み出す。

**Independent Test**: 1つの節について、概要→執筆→レビュー→修正のサイクルを2-3回繰り返し、満足できる本文が完成することを確認。

**Acceptance Scenarios**:

1. **Given** ある節の概要を書いた、**When** AIに詳細執筆を依頼、**Then** スタイルガイドに準拠した本文案が生成される
2. **Given** AI生成の本文案、**When** 著者がレビュー、**Then** 技術的誤り、表現の改善点を指摘できる
3. **Given** レビュー指摘、**When** 修正を依頼、**Then** 指摘が反映され改善された本文になる
4. **Given** 満足できる本文、**When** 次の節に進む、**Then** 前節との繋がりが自然で一貫性が保たれる

---

### User Story 3 - スタイルガイド準拠の検証 (Priority: P2)

完成した本文が執筆スタイルガイド（docs/writing-style-guide.md）に準拠しているか検証できる。

**Why this priority**: 章間の一貫性を保つための品質管理。執筆後の検証フェーズ。

**Independent Test**: 完成した第1章をスタイルガイドのチェックリストで検証し、すべての項目がPASSすることを確認。

**Acceptance Scenarios**:

1. **Given** 完成した本文、**When** 文章スタイル（です・ます調、助詞）をチェック、**Then** ガイドライン違反がない
2. **Given** 完成した本文、**When** 技術用語（BLE, GATT等）の表記をチェック、**Then** 初出時に日本語説明あり、略語展開済み
3. **Given** 完成した本文、**When** 引用・参考文献をチェック、**Then** IEEE形式で正しく引用されている

---

### Edge Cases

- 著者が節の途中で大幅な構成変更を希望した場合（節の分割・統合）
- AI生成の本文が技術的に誤っている場合の検証方法
- ページ数が想定18-22ページを大幅に超過/不足する場合の調整
- 複数の節で同じ内容が重複してしまう場合の整理
- 参考文献が多すぎて読者の負担になる場合の取捨選択

## Requirements

### Functional Requirements

- **FR-001**: 第1章の詳細な節構成（1.1, 1.2, ...）を `manuscript/chapters/01-what-is-ble/outline.md` に作成すること
- **FR-002**: 各節には、節番号、節タイトル、1-2行の概要、想定ページ数を含むこと
- **FR-003**: 全体アウトラインの第1章概要に基づき、以下の内容を含むこと：
  - BLEの歴史
  - Bluetooth Classicとの違い
  - 主な用途
  - 低消費電力の仕組み
  - なぜBLEが選ばれるのか
- **FR-004**: 各節の本文は、`manuscript/chapters/01-what-is-ble/section-X.md` に配置されること（X = 1, 2, 3, ...）
- **FR-005**: 本文は「です・ます」調で記述されること（スタイルガイド準拠）
- **FR-006**: 技術用語（BLE, Bluetooth等）は初出時に日本語説明を付加すること
- **FR-007**: 略語は初出時に展開形を示すこと（例：BLE (Bluetooth Low Energy)）
- **FR-008**: 引用・参考文献はIEEE形式で記載すること
- **FR-009**: 各節の執筆は「概要作成 → AI生成 → レビュー → 修正」のサイクルで進められること
- **FR-010**: 著者とAIのやり取り履歴を `manuscript/chapters/01-what-is-ble/review-log.md` に記録すること
- **FR-011**: 完成した本文の総ページ数が18-22ページの範囲内に収まること（Pandocビルド後）
- **FR-012**: 図表を含む場合は、図番号（図1-1, 図1-2）とキャプションを付けること
- **FR-013**: コード例を含む場合は、言語名を指定したフェンスドコードブロックを使用すること
- **FR-014**: 完成後、スタイルガイドのチェックリストで検証し、すべての項目がPASSすること
- **FR-015**: 第2章への繋がりを意識した結びの文を含むこと

### Key Entities

- **Chapter（章）**: 第1章全体の構造、総ページ数、前提章、次章との繋がり
- **Section（節）**: 節番号、節タイトル、概要、本文、想定ページ数
- **本文コンテンツ**: Markdown形式、段落、見出し、箇条書き、図表、コード例
- **レビュー履歴**: 日付、節番号、指摘内容、修正内容
- **参考文献**: 番号、タイトル、著者、URL、アクセス日（該当する場合）
- **スタイルガイド検証**: チェック項目、PASS/FAIL、指摘内容

## Success Criteria

### Measurable Outcomes

- **SC-001**: 著者が節構成案を見て、10分以内に第1章全体の流れを理解し、修正点を指摘できる
- **SC-002**: 1つの節の執筆サイクル（概要→生成→レビュー→修正）を1-2時間で完了できる
- **SC-003**: 第1章全体（5-7節）の初稿を2-3日で完成できる
- **SC-004**: 完成した本文がPandocでビルドでき、18-22ページのPDFが生成される（±2ページ許容）
- **SC-005**: スタイルガイドのチェックリスト全項目がPASSする（文章スタイル、技術用語、引用）
- **SC-006**: 技術レビュアーが読んで、「BLEの基礎が理解できる」と評価する（5段階で4以上）
- **SC-007**: 第2章の著者が第1章を前提として執筆を開始できる（用語定義や前提知識の不足がない）
- **SC-008**: レビュー履歴を見て、どの節でどのような議論があったか追跡できる
- **SC-009**: GitHub公開時に、読者が第1章を読んでBLEの概要を理解できる（読者フィードバックで確認）

## Assumptions

- 著者は技術的内容を理解しており、AIは執筆補助の役割
- スタイルガイド（docs/writing-style-guide.md）は確定しており、変更なし
- 全体アウトライン（manuscript/outline.md）の第1章概要は確定している
- Pandocビルドシステムは正常に動作している
- 第1章は他章に依存せず、独立して執筆できる（序文のみ前提）
- 参考文献はBluetooth SIG仕様書、O'Reilly書籍等の公開リソースを使用
- 図表は後から追加可能（初稿ではテキストのみでも可）
- ページ数はPandoc + LaTeX（LuaLaTeX）でのビルド結果を基準とする

## Out of Scope

- 第2章以降の執筆（これは別featureで管理）
- 序文の執筆（別featureで管理）
- 図表の作成・デザイン（この featureではプレースホルダーのみ）
- 最終的な校正・編集（出版前の別フェーズ）
- 多言語翻訳（日本語版のみ対象）
- コードサンプルの動作検証（第1章は概念説明が中心で、コードは最小限）

## Notes

### 第1章の位置づけ

全体アウトラインより：
- **概要**: BLEの歴史、Bluetooth Classicとの違い、主な用途、低消費電力の仕組み、なぜBLEが選ばれるのか
- **想定ページ数**: 18-22ページ
- **前提章**: 序文
- **役割**: Part 1（BLE基礎知識）の導入章。ファーム/アプリ/企画全ての読者が理解すべき基盤。

### 執筆ワークフローの柔軟性

- 著者主導：著者が節の概要や骨子を書き、AIに詳細執筆を依頼
- AI主導：AIが節全体の初稿を生成し、著者がレビュー・修正
- 混在：節によって上記を使い分け
- 繰り返し：満足するまで何度でもレビュー→修正サイクルを実行可能

### スタイルガイド準拠の重要性

第2章以降も同じスタイルで執筆するため、第1章で以下を確立：
- 「です・ます」調の自然な文体
- 技術用語の統一表記
- 図表・コードの書式
- 引用形式
