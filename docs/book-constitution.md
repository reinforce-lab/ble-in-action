# BLE In Action 執筆理念

**バージョン**: 1.1.0 ／ **最終更新**: 2026-06-20
**位置づけ**: 本書の執筆判断で優先する理念と品質基準を定める。表記・Markdown書式は [writing-style-guide.md](writing-style-guide.md)、読者層別Noteは [writing-guidelines-reader-notes.md](writing-guidelines-reader-notes.md) を正本とする。

## 基本方針

本書は、SDKやAPIの使い方だけを説明する本ではありません。
BLEで実際に何が通信され、どの層で何が起き、問題が起きたときにどこを疑えばよいのかを、ファーム開発者、アプリ開発者、企画者、ホビーストが共通言語として扱えるようにするための本です。

したがって、執筆では次の順に優先します。

1. 技術的正確性
2. 実際に試せる具体性
3. 読者が段階的に理解できる構成
4. ファーム、アプリ、企画を横断する対話しやすさ
5. 出版物としての一貫した表記・書式

## 原則

### 1. 実践を通じて理解できること

各章は、概念説明だけで終わらせず、読者が手元で確認できる実例へ接続します。
BLEは無線、ファームウェア、OS、アプリが重なる技術であるため、理論だけでは実装時の問題を切り分けられません。

章や節では、可能な範囲で次を満たします。

- 技術概念を、動作するコード例または観測できる通信例へ接続する。
- 主要な概念では、ファーム側とアプリ側の両方から見える形を示す。
- 必要なハードウェア、SDK、OS、ツールの前提を明示する。
- 実際に試せない説明では、なぜ試せないのか、何を観測すればよいのかを補足する。

### 2. コード例と通信例を検証すること

コード例は、掲載前に対象環境で動作を確認します。
BLE通信を扱う例では、可能な限り実機または実OS上でデータ交換を確認します。

特に次を確認します。

- nRF Connect SDK、Zephyr、Xcode、iOS、Android、ブラウザなどのバージョン。
- nRF52840など、前提とするボードやセンサー。
- ファーム、モバイルアプリ、Web、Linuxなど、関係するプラットフォーム間の実通信。
- プラットフォーム固有の制約や回避策。

検証できていないコードや挙動は、断定せず、未検証であることを本文または作業メモで分けて扱います。

### 3. 段階的に難易度を上げること

本書は、BLEの基礎から実装、応用、デバッグへ進む構成にします。
新しい概念は、前提となる概念を示してから導入します。

執筆時は次を確認します。

- 章や節の冒頭で、その節が何を明らかにするのかを示す。
- 新しい用語は、初出時に定義する。
- GAP、ATT、GATT、L2CAP、SMPなどの層を混同しない。
- 後続章で使う概念は、先行章で必要な範囲だけ説明する。
- 詳細に入りすぎる場合は、章末、付録、参考文献へ逃がす。

### 4. 問題解決に使える説明にすること

本書の説明は、読後に「どこを疑えばよいか」が分かる形にします。
BLE開発では、通信距離、接続、GATT設計、権限、OS制約、消費電力、セキュリティなどが絡むため、単なる機能紹介では実務に足りません。

各章では、可能な範囲で次を含めます。

- よくある失敗や誤解。
- ログ、パケットキャプチャ、OSの挙動から切り分ける方法。
- ファーム側、アプリ側、企画側のどこで合意すべきか。
- 仕様上の制約と、SDKやOSの実装上の制約の違い。

### 5. コード例を自己完結させること

コード例は、読者が不足部分を推測しなくてよい粒度にします。
断片を示す場合でも、どのファイルのどこに置くのか、周辺の前提が何かを説明します。

コード例では次を守ります。

- import、設定、初期化、権限、ビルド設定を省略しすぎない。
- 省略する場合は、完全版の所在や省略理由を示す。
- 複数ファイルにまたがる例では、ファイル構成を示す。
- 本書独自のコードは、MITライセンスで再利用できる前提に合わせる。

### 6. 仕様と実装差分を区別すること

BLEは標準仕様に基づく技術ですが、実際の開発ではSDK、OS、ブラウザ、チップの実装差が現れます。
本文では、Bluetooth Core Specificationに基づく説明と、特定プラットフォームの実装上の挙動を区別します。

技術説明では次を守ります。

- BLE仕様に関わる記述は、仕様の版や該当箇所を確認する。
- プラットフォーム固有の挙動を、BLE仕様そのものとして書かない。
- 非推奨機能や古いAPIは、可能な範囲で移行先を示す。
- 不確かな挙動は断定せず、検証条件または確認待ちとして扱う。

## 章設計の基準

各章は、必要に応じて次の要素を持ちます。

1. 章で扱う問い、または読者が到達する状態。
2. 前提となる章や知識。
3. 概念説明。
4. 実装または観測できる例。
5. よくある問題と切り分け。
6. まとめと次章への接続。

ただし、これは固定テンプレートではありません。
章の性格に合わない項目を無理に入れず、読者の理解順に合わせて構成します。

## 品質基準

### 技術レビュー

- 章ごとに、BLE仕様、ファーム、モバイルアプリ、Web、Linuxなど、該当領域の観点で確認する。
- コード例は、対象環境とバージョンを明確にして検証する。
- 数値、制約、仕様上の用語は、公式仕様または公式ドキュメントで裏取りする。

### 編集レビュー

- 本文は「です・ます」調で統一する。
- 用語、表記、図表、引用、コード表記は [writing-style-guide.md](writing-style-guide.md) に従う。
- 読者層別Noteは [writing-guidelines-reader-notes.md](writing-guidelines-reader-notes.md) に従う。
- 図、表、コードは本文の主張と一致させる。

### 出版前確認

- EPUBとPDFの両方で、見出し、図表、コード、脚注、相互参照を確認する。
- Kindle版と紙版で読みやすさが大きく変わる箇所は、レイアウトや説明粒度を調整する。
- 誤字脱字、技術的指摘、サンプルコードの問題を受け付ける導線を明示する。

## 改訂方針

この文書は、本書全体の方針を変えるときだけ更新します。
表記やNoteのような個別ルールは、対応する正本の文書で更新します。

- MAJOR: 基本方針や原則の変更。
- MINOR: 原則、品質基準、正本の分担の追加。
- PATCH: 誤字修正、表現の明確化、リンク修正。
