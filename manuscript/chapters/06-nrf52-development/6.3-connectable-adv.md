## 6.3 接続可能アドバタイジングを開始する {#sec:ch6-connectable-advertising}

前節では、`BT_LE_ADV_NCONN`を使って接続を受け付けないアドバタイジングを送信しました。GATT ClientからServiceを探索してもらうには、Peripheralとして接続を受け付ける必要があります。

本節では、Advertising Dataの構造を保ったまま、接続可能なPeripheralへ変更します。GATT Serviceは次節で追加するため、まず「発見できる」「接続できる」という二つの段階だけを確認します。

### 6.3.1 Peripheral機能を有効にする

`prj.conf`を次のように変更します。

```kconfig
CONFIG_BT=y
CONFIG_BT_PERIPHERAL=y
CONFIG_BT_DEVICE_NAME="BLE In Action"
CONFIG_BT_MAX_CONN=1

CONFIG_LOG=y
```

`CONFIG_BT_PERIPHERAL`は、接続を受け付け、GATT Serverとして動作するために必要な機能を選びます。`CONFIG_BT_MAX_CONN=1`は、同時接続数を1台に限定します。同時接続数を増やすと、接続ごとの状態を保持するRAMも増えます。本書のサンプルでは、一つのクライアントとの状態遷移を先に確認します。

Kconfigを変更したため、以前の生成結果を破棄してビルドします。

```bash
west build -b nrf52840dk/nrf52840 --pristine
west flash
```

### 6.3.2 接続可能なAdvertising Parametersを選ぶ

`main.c`のアドバタイジング開始部分を、次のように変更します。

```c
err = bt_le_adv_start(BT_LE_ADV_CONN_FAST_1,
                      ad, ARRAY_SIZE(ad),
                      sd, ARRAY_SIZE(sd));
if (err) {
    LOG_ERR("Advertising start failed: %d", err);
    return 0;
}
```

`BT_LE_ADV_CONN_FAST_1`は、接続可能なLegacy Advertisingを、接続開始時に見つけやすい間隔で送信するための定義です。前節の`BT_LE_ADV_NCONN`と違い、スキャンしたCentralはCONNECT_INDまたはAUX_CONNECT_REQを送って接続を開始できます。本書のコードはLegacy Advertisingを使うため、実際にはCONNECT_INDを使う経路になります。

アドバタイジング間隔を短くすると、発見までの待ち時間を短縮しやすくなりますが、送信回数が増えます。ここでは開発中の確認を優先します。製品の待機時に使う間隔は、第7章で状態遷移と一緒に設計し、同じ章で実測します。

### 6.3.3 Advertising DataとScan Response Dataを分ける

前節では、FlagsとComplete Local NameをAdvertising Dataへ入れました。接続可能にした後は、常に送信したい情報をAdvertising Dataへ置き、Active Scanningへの応答で追加する情報をScan Response Dataへ分けます。

```c
static const struct bt_data ad[] = {
    BT_DATA_BYTES(BT_DATA_FLAGS,
                  BT_LE_AD_GENERAL | BT_LE_AD_NO_BREDR),
};

static const struct bt_data sd[] = {
    BT_DATA(BT_DATA_NAME_COMPLETE,
            CONFIG_BT_DEVICE_NAME,
            sizeof(CONFIG_BT_DEVICE_NAME) - 1),
};
```

本書で使うLegacy Advertisingでは、Advertising DataとScan Response Dataはそれぞれ最大31 byteです。AD StructureにはLengthとAD Typeも含まれるため、Valueだけで31 byteを使えるわけではありません。

```text
Advertising Event
  └─ Advertising Data: Flags

Active Scanner
  ├─ Scan Request
  └─ Scan Response: Complete Local Name
```

名前をScan Response Dataへ移すと、Passive Scanningでは名前を受信できません。製品の識別に必須の情報をどちらへ置くかは、クライアントのスキャン方法も含めて決めます。次節でService UUIDを定義した後は、接続前に対象Serviceを絞り込めるよう、そのUUIDをAdvertising Dataへ追加します。

### 6.3.4 接続できることだけを確認する

BLE汎用ツールで`BLE In Action`を選び、接続します。この段階では、Zephyrが標準で公開するGATT Service以外に、製品固有のServiceはまだありません。

確認する事実を分けます。

1. スキャン結果に名前が表示される
2. 接続操作が成功する
3. 接続後は同じAdvertising Setの送信が止まる
4. 切断すると、現状のコードではアドバタイジングが自動再開しない

4番目は故障ではありません。接続後に停止したアドバタイジングを、切断コールバックから再開する処理をまだ書いていないためです。接続と切断のライフサイクルは6.8節で実装します。

ここまでで、GAP上のPeripheralとして接続を受け付けられるようになりました。次節では、第4章で設計したGATTインターフェースをZephyrのAttributeへ配置します。
