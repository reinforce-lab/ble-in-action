## 6.9 GATT通信の骨格を第7章へ渡す {#sec:ch6-summary}

本章では、nRF52840 DK上で最小のプログラムを動かし、BLEの観測範囲を段階的に増やしました。

```text
ログ
  Hello Worldが実行された
        ↓
Advertising
  別の機器から電波を観測できた
        ↓
Connection
  Centralから接続できた
        ↓
GATT Discovery
  ServiceとCharacteristicを発見できた
        ↓
ATT／GATT Operation
  Read、Write、Notifyを実行できた
        ↓
Product Contract
  状態、設定、コマンド、応答、イベントを区別できた
```

実装した各要素は、Bluetooth仕様とZephyr APIの次の位置に対応します。

| 製品上の要素 | GATT／ATT | Zephyrで使った要素 |
|---|---|---|
| 現在状態 | Read、Notify | Readコールバック、`bt_gatt_notify()` |
| 設定 | Read、Write Request | Read／Writeコールバック |
| コマンド受付 | Write Request／Response | Writeコールバック、Work Queue |
| コマンド完了 | Notify | Command Response Characteristic |
| 製品イベント | Notify | Device Event Characteristic |
| 購読 | CCCD Write | `BT_GATT_CCC()` |
| 接続ライフサイクル | GAP Connection | `BT_CONN_CB_DEFINE()` |

: 製品上の意味とZephyr実装の対応 {#tbl:ch6-product-zephyr-mapping}

Read、Write、Notifyは、データの意味を自動的には決めません。状態と設定を同じCharacteristicへ混ぜないこと、Write Responseと製品処理の完了を混同しないこと、Command Responseと自然発生したDevice Eventを分けることによって、ファームウェアとクライアントが同じ契約を実装できます。

本章の値は、まだソフトウェア上で生成しています。LED Stateを変更しても、開発ボード上のGPIOは操作していません。Measurement Valueも、実際のセンサーから取得していません。この状態だからこそ、BLE通信の問題と周辺ハードウェアの問題を分けて確認できます。

第7章では、次の対応を追加します。

- LED StateとGPIO出力
- ボタン入力とDevice Event
- I2C／SPIセンサーとMeasurement Value
- Measurement Intervalとタイマー
- Command Requestと製品内部の状態遷移
- 割り込み、Work Queue、待機・復帰

GATTインターフェースは、第7章で周辺機器を交換しても、クライアントとの境界として保ちます。製品内部の実装と、BLE上で公開する契約を分けることで、ファームウェアとアプリケーションを独立して開発・試験できます。
