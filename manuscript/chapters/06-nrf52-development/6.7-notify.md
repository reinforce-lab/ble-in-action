## 6.7 状態、応答、イベントをNotifyする {#sec:ch6-notify}

Readは、クライアントが要求した時点のValueを返します。測定値やLED状態が変化したことをサーバーから知らせるには、NotifyまたはIndicateを使います。

Notifyを送るには、CharacteristicへNotify Propertyを付けるだけでは足りません。Client Characteristic Configuration Descriptor（CCCD）を置き、クライアントが購読を有効にしている必要があります。

### 6.7.1 CCCDで購読状態を受け取る

LED StateとMeasurement Valueの定義では、Characteristic Valueの直後へ`BT_GATT_CCC()`を置きました。

```c
BT_GATT_CHARACTERISTIC(BT_UUID_MEASUREMENT,
    BT_GATT_CHRC_READ | BT_GATT_CHRC_NOTIFY,
    BT_GATT_PERM_READ,
    read_measurement, NULL, NULL),
BT_GATT_CCC(measurement_ccc_changed,
            BT_GATT_PERM_READ | BT_GATT_PERM_WRITE),
```

クライアントがCCCDへ`0x0001`を書くとNotifyが有効になります。`0x0000`を書くと無効になります。ZephyrはCCCDのValueを接続ごとに管理し、変更時にコールバックを呼びます。

```c
static void measurement_ccc_changed(
    const struct bt_gatt_attr *attr, uint16_t value)
{
    bool enabled = (value == BT_GATT_CCC_NOTIFY);

    LOG_INF("Measurement notifications %s",
            enabled ? "enabled" : "disabled");
}
```

この`enabled`は観測用です。複数接続を許す製品で、一つのグローバル変数だけを購読状態の正本にしてはいけません。接続ごとのCCCD状態はZephyrが保持します。

### 6.7.2 Characteristic ValueのAttributeを指定する

`bt_gatt_notify()`には、通知するCharacteristic ValueのAttributeを渡します。`BT_GATT_SERVICE_DEFINE()`が作るAttributeの順序を、コード内の列挙値で明示します。

```c
enum device_service_attr_index {
    DEVICE_SERVICE_ATTR_SERVICE,
    DEVICE_SERVICE_ATTR_LED_DECLARATION,
    DEVICE_SERVICE_ATTR_LED_VALUE,
    DEVICE_SERVICE_ATTR_LED_CCC,
    DEVICE_SERVICE_ATTR_MEASUREMENT_DECLARATION,
    DEVICE_SERVICE_ATTR_MEASUREMENT_VALUE,
    DEVICE_SERVICE_ATTR_MEASUREMENT_CCC,
    DEVICE_SERVICE_ATTR_INTERVAL_DECLARATION,
    DEVICE_SERVICE_ATTR_INTERVAL_VALUE,
    DEVICE_SERVICE_ATTR_COMMAND_REQUEST_DECLARATION,
    DEVICE_SERVICE_ATTR_COMMAND_REQUEST_VALUE,
    DEVICE_SERVICE_ATTR_COMMAND_RESPONSE_DECLARATION,
    DEVICE_SERVICE_ATTR_COMMAND_RESPONSE_VALUE,
    DEVICE_SERVICE_ATTR_COMMAND_RESPONSE_CCC,
    DEVICE_SERVICE_ATTR_EVENT_DECLARATION,
    DEVICE_SERVICE_ATTR_EVENT_VALUE,
    DEVICE_SERVICE_ATTR_EVENT_CCC,
};
```

Service定義へCharacteristicを追加・削除するとAttributeの位置も変わります。数値を直接書かず、Service定義とこの列挙を同じファイルで管理します。

### 6.7.3 状態が変わったときにNotifyする

Measurement Valueを更新する関数を作ります。

```c
int device_service_set_measurement(int16_t value)
{
    uint8_t encoded[2];

    measurement_value = value;
    sys_put_le16((uint16_t)value, encoded);

    return bt_gatt_notify(
        NULL,
        &device_service.attrs[DEVICE_SERVICE_ATTR_MEASUREMENT_VALUE],
        encoded, sizeof(encoded));
}
```

第1引数を`NULL`にすると、Zephyrは対象AttributeのNotifyを購読している接続へ送ります。購読していないクライアントへNotificationは送られません。

内部値を更新してからNotifyを呼ぶため、クライアントはNotificationを受信できなかった場合でも、後からReadして現在値へ同期できます。Notifyだけを履歴の正本にしないことがポイントです。

LED Stateも同じ形で更新します。

```c
int device_service_set_led_state(uint8_t value)
{
    led_state = value;

    return bt_gatt_notify(
        NULL,
        &device_service.attrs[DEVICE_SERVICE_ATTR_LED_VALUE],
        &led_state, sizeof(led_state));
}
```

第7章では、この関数の前後で実際のGPIOを操作し、要求値、ハードウェア操作の結果、公開するLED Stateを対応づけます。

### 6.7.4 Command Responseで完了を返す

Command Responseは4 byteとします。

| Offset | 長さ | フィールド | 意味 |
|---:|---:|---|---|
| 0 | 1 byte | Opcode | 完了したコマンド |
| 1 | 1 byte | Request ID | Requestとの対応 |
| 2 | 1 byte | Status | `0`: 成功、`1`: 失敗 |
| 3 | 1 byte | Result | コマンド固有の結果 |

: Command ResponseのValue形式 {#tbl:ch6-command-response-value}

CharacteristicをServiceへ追加します。

```c
static uint8_t command_response[4];

static ssize_t read_command_response(
    struct bt_conn *conn,
    const struct bt_gatt_attr *attr,
    void *buf, uint16_t len, uint16_t offset)
{
    return bt_gatt_attr_read(conn, attr, buf, len, offset,
                             command_response,
                             sizeof(command_response));
}

BT_GATT_CHARACTERISTIC(BT_UUID_COMMAND_RESPONSE,
    BT_GATT_CHRC_READ | BT_GATT_CHRC_NOTIFY,
    BT_GATT_PERM_READ,
    read_command_response, NULL, NULL),
BT_GATT_CCC(command_response_ccc_changed,
            BT_GATT_PERM_READ | BT_GATT_PERM_WRITE),
```

6.6節で登録したWork Queueの処理を実装します。

```c
static void command_work_handler(struct k_work *work)
{
    uint8_t status = 0U;
    uint8_t result = 0U;

    switch (pending_command.opcode) {
    case 1U:
        device_service_set_led_state(
            (uint8_t)pending_command.argument);
        result = led_state;
        break;

    case 2U:
        measurement_value++;
        device_service_set_measurement(measurement_value);
        result = 1U;
        break;

    default:
        status = 1U;
        break;
    }

    command_response[0] = pending_command.opcode;
    command_response[1] = pending_command.request_id;
    command_response[2] = status;
    command_response[3] = result;

    bt_gatt_notify(
        NULL,
        &device_service.attrs[
            DEVICE_SERVICE_ATTR_COMMAND_RESPONSE_VALUE],
        command_response, sizeof(command_response));

    atomic_clear(&command_pending);
}
```

Request IDによって、クライアントはどのCommand Requestに対する完了かを判断できます。Write Response、LED State Notification、Command Response Notificationは、それぞれ別の意味を持ちます。

実製品では`bt_gatt_notify()`の戻り値も処理します。処理完了前に切断された場合や、クライアントが購読していない場合に、Notificationだけへ完了結果を閉じ込めてはいけません。本章では`command_response`を現在値として保持し、再接続後にReadして確認できる形にしています。履歴を複数件残す要件がある場合は、GATT Valueとは別に不揮発性の記録を設計します。

```text
Client                         Peripheral
   │ Command Request Write         │
   ├──────────────────────────────>│
   │<──────── Write Response ──────┤ 受付
   │                               │ 製品処理
   │<──── LED State Notification ──┤ 状態変化
   │<── Command Response Notify ───┤ 完了結果
```

### 6.7.5 Device Eventを状態や応答と分ける

Device Eventは、ボタン操作、センサー異常、電源状態の変化など、特定のCommand Requestへの応答ではない事実を表します。本章では3 byteとします。

```text
Event ID | Detail | Value
```

Command Responseと同じCharacteristicへ混ぜると、クライアントは「自分の要求への完了」と「製品側で自然に発生した事実」を区別しにくくなります。別のCharacteristicとCCCDを用意します。

```c
BT_GATT_CHARACTERISTIC(BT_UUID_DEVICE_EVENT,
    BT_GATT_CHRC_NOTIFY,
    BT_GATT_PERM_NONE,
    NULL, NULL, NULL),
BT_GATT_CCC(device_event_ccc_changed,
            BT_GATT_PERM_READ | BT_GATT_PERM_WRITE),
```

イベント履歴をReadできるようにするか、接続していない間のイベントを保存するかは製品仕様です。Notifyは、その瞬間に接続して購読しているクライアントへの配送であり、イベントの永続保存を保証しません。

### 6.7.6 NotifyとIndicateを選ぶ

NotifyにはATT上の確認応答がありません。Indicateは、クライアントからConfirmationを受け取るまで、同じ接続で次のIndicationを送れません。

| 操作 | ATT上の確認 | 向く用途 |
|---|---|---|
| Notify | なし | 最新値を継続して送り、次の値で追い付ける場合 |
| Indicate | あり | 一件ずつ受信確認が必要な低頻度の通知 |

: NotifyとIndicateの選択 {#tbl:ch6-notify-indicate}

IndicateのConfirmationは、相手のATT層が受信したことを示します。アプリケーションが処理を完了したことまでは保証しません。本書では汎用ツールで確認しやすいNotifyを使い、製品上の完了はCommand ResponseのStatusで表します。
