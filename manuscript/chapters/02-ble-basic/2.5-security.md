## 接続した通信路を保護する {#sec:pairing}

<!--

- 鍵生成と相手確認を分け、ファームウェアの入出力設定がスマートフォンの操作体験へつながることを示す。

前節では、特定の相手と接続し、接続イベントでパケットを交換する通信路を作りました。しかし、接続しただけでは、通信内容が必ず暗号化されるわけではありません。

暗号化されていない電波を第三者が受信すると、通信内容を読み取られる可能性があります。また、製品が相手を確認せずに操作を受け付ければ、意図しない機器から設定を書き換えられる可能性があります。健康情報を読み出す、設定を書き換える、鍵を開けるといった操作では、内容を隠すことと、操作する相手を確かめることの両方を考える必要があります。

一方、公開情報を知らせるだけの機器など、暗号化しない接続で利用場面を実現できる場合もあります。すべての接続で同じ保護を要求するのではなく、読まれたり操作されたりした場合の影響から必要な条件を決めます。

BLEで通信路を保護するときは、ペアリング、暗号化、ボンディングという三つの処理が関係します。これらは同じ処理の別名ではありません。

通信路を保護してGATT操作へ進む場合は、次の順になります。

1. 接続する
2. 必要ならペアリングで鍵を準備する
3. 鍵を使って接続を暗号化する
4. アクセス条件を満たしたGATT操作を行う
5. 必要なら鍵を保存して次回の接続で使う

### 利用期間と手間から保護方法を選ぶ

製品では、保護を強くすればよいとだけ考えるのではなく、扱う情報や操作の重要度、利用する期間、利用者に求める手間を合わせて考えます。基本的な選択を、次の三つに分けます。

| 使い方 | 接続の保護 | 次回の接続 | 向いている例 |
|---|---|---|---|
| ペアリングしない | 暗号化しない | 鍵を使わず、そのまま接続する | 公開してよい情報の取得、試用 |
| ペアリングするがボンディングしない | その接続を暗号化する | 必要なら再びペアリングする | 一時的な設定、短期間だけ扱う保護対象のデータ |
| ペアリングしてボンディングする | 接続を暗号化する | 保存した鍵で暗号化を再開する | 所有者が継続して使う機器 |

: 利用方法とペアリング、ボンディングの選択 {#tbl:security-usage}

一時的な利用だから、暗号化が不要になるわけではありません。たとえば、短時間だけ使うフィットネス機器でも、健康情報を第三者に読まれたくない場合や、測定値の改ざんが問題になる場合は、その接続中だけペアリングして暗号化する設計が考えられます。反対に、不特定の相手へ公開してよい情報だけを扱う機器なら、ペアリングしないことで利用開始の手間を減らせます。

ボンディングは暗号方式を強くする処理ではなく、ペアリングで得た鍵を次回以降も利用するための処理です。個人が所有して繰り返し使う機器では便利ですが、ファームウェアには鍵の保存領域、登録可能台数、登録解除、工場出荷時リセットの設計が必要になります。

### ペアリングで鍵を準備する

ペアリング（Pairing）は、二つの機器がセキュリティに使う鍵を作り、必要な情報を交換する手続きです。画面やキーボードを持つか、利用者が値を比較できるかなど、機器が持つ入出力能力によって、利用できる認証方法が変わります。

ここで、「鍵を作る処理」と「意図した相手であることを確認する方法」を分けて考える必要があります。Just Works、Passkey Entry、Numeric Comparison、OOBは、主に後者を決めるAssociation Modelです。どの方式を使えるかは、両方の機器が交換する入出力能力と、MITM（Man-in-the-Middle、中間者攻撃）保護の要求などから決まります。ファームウェアが方式名を一方的に指定できるとは限りません。

ペアリングは接続の代わりではなく、接続後の通信を保護するために鍵を準備する段階です。

### STKとLTKは同じ「鍵」ではない

BLEのペアリングには、LE Legacy PairingとLE Secure Connectionsという二つの鍵生成方法があります。現在の製品で基本となるLE Secure Connectionsは、P-256楕円曲線暗号によるECDH（Elliptic Curve Diffie-Hellman）鍵共有を使います。二つの機器は公開鍵を交換し、それぞれが同じDHKeyを計算します。そのDHKeyと乱数などから、ペアリングの確認に使うMacKeyと、接続の暗号化に使うLTK（Long Term Key）を導出します。

一方、LE Legacy Pairingでは、Association Modelで得たTK（Temporary Key）からSTK（Short Term Key）を生成します。まずSTKで接続を暗号化し、その後の鍵配布によってLTKなどを交換します。したがって、「DH鍵交換で短期キーを作り、その後LTKを作る」という一つの流れが、すべてのBLEペアリングに共通するわけではありません。LE Secure ConnectionsではECDHからLTKを導出し、STKは使いません。

Passkeyは、利用者を介して二つの機器へ共有する短い秘密です。名前の似たSTKは、LE Legacy Pairingで暗号化に使う128 bitの鍵です。PasskeyそのものをSTKやLTKとして使うわけではありません。

| 鍵生成方法 | 鍵が作られる流れ | 接続の暗号化に使う鍵 |
|---|---|---|
| LE Legacy Pairing | TKからSTKを生成し、暗号化した接続でLTKなどを交換する | ペアリング中はSTK、その後はLTK |
| LE Secure Connections | ECDHで共有したDHKeyからMacKeyとLTKを導出する | LTK |

: LE Legacy PairingとLE Secure Connectionsの鍵生成 {#tbl:legacy-and-secure-connections-keys}

LTKという名前に「Long Term」とありますが、ボンディングしなければ次回の接続まで保存する必要はありません。ボンディングする場合は、両方の機器がLTKなどの情報を保存し、再接続時の暗号化に使います。鍵を作ること、接続を暗号化すること、鍵を次回のために保存することは、それぞれ別の段階です。

### Association Modelが利用者の操作を決める

ファームウェア側が設定する入出力能力は、スマートフォンに表示されるペアリング操作へつながります。LE Secure Connectionsを使う場合の代表的な組み合わせを次に示します。

| 周辺機器の能力と設計 | 利用者の操作 | MITM保護 |
|---|---|---|
| 画面も入力手段もなく、OOBも使わない | コードを入力せずに進むJust Works | なし |
| 6桁の値を表示できる | 機器に表示されたPasskeyをスマートフォンへ入力する | あり |
| 数値を入力できる | スマートフォンに表示されたPasskeyを機器へ入力する | あり |
| 数値を表示でき、Yes／Noを入力できる | 両方に表示された6桁の値が一致するか確認するNumeric Comparison | あり |
| 別の通信経路で認証情報を渡せる | NFCへのタッチなど、製品が定めた操作を行うOOB | OOB経路の保護による |

: LE Secure Connectionsにおける周辺機器の入出力能力とペアリング体験 {#tbl:pairing-user-experience}

Numeric Comparisonで表示される6桁の値は、秘密のPasskeyではありません。利用者が両方の表示を見比べ、同じ相手と鍵交換していることを確認するための値です。Just Worksも暗号化された接続を作れますが、相手を確認する操作がないため、ペアリング中の中間者攻撃を防ぐ認証済みの鍵にはなりません。

実際のスマートフォンでは、ペアリング画面やPasskey入力画面はOSが表示します。アプリケーション独自の画面だけを用意しても、BLEのAssociation Modelが変わるわけではありません。ファーム開発者は、採用する入出力能力、MITM保護の要求、ボンディングの有無をアプリ開発者へ伝え、OS上でどの操作が発生するかを一緒に確認する必要があります。

### Passkeyの決め方を製品として考える

BLEのPasskey Entryで扱うPasskeyは、`000000`から`999999`までの6桁の10進数です。入力側が4桁しか入力しない場合は、先頭に0を補った6桁として扱われます。たとえば`1234`は`001234`と同じ値です。4桁を選べる別方式があるのではなく、6桁の値の上位桁が0になっているだけです。

Bluetooth仕様では、Passkey Entryを使う各ペアリング手続きで、新しいPasskeyをランダムに生成することを要求しています。6桁のPasskeyが持つ情報量は約20 bitに限られるため、同じ値を使い続けないことが重要です。画面を持つ機器なら、ペアリングを開始するたびに新しいPasskeyを表示する設計が基本になります。

表示器を持たない製品では、ファームウェアへ`1234`などの共通値を固定したくなることがあります。しかし、これはペアリングごとにランダムなPasskeyを生成するという仕様の要件を満たしません。共通の固定値は一台から分かれば同じ製品へ使い回せます。公開される製造シリアル番号の一部からPasskeyを作る方法も、第三者が値を予測できるため、秘密による相手確認にはなりません。このような実装は利用開始を簡単にしますが、中間者攻撃から守るための設計として扱うべきではありません。

本体や同梱物へ個体ごとに異なる値を印刷する製品もあります。共通値やシリアル番号から推測できる値よりは使い回しを防げますが、印刷された値は目視や撮影で漏れる可能性があり、ペアリングのたびに新しい値を生成する方式でもありません。採用する場合は、予測できない個体別の値を製造時に生成し、製造データとファームウェアへ安全に書き込む工程、値が漏れた場合の再設定、ラベルを失った場合の復旧まで設計する必要があります。

したがって、表示器や入力手段のない機器で強い相手確認が必要なら、固定Passkeyだけで解決しようとせず、OOBやアプリケーション層の所有者確認を含めて製品全体で設計します。

### OOBでは別の経路で認証情報を渡す

OOB（Out of Band）は、BLEの無線とは別の経路で、ペアリングに必要な認証情報を渡す方法です。NFCはその代表例です。利用者がスマートフォンを機器へタッチする操作なら、画面やキーボードを持たない機器でも、今触れている機器をペアリング相手として確認できます。

OOBで使う経路はNFCに限定されておらず、Bluetooth仕様は認証情報を運ぶ具体的な手段を一つに定めていません。また、OOBは「別経路でPasskeyを送る方式」とも限りません。LE Secure Connectionsでは、公開鍵に対する確認値や乱数などをOOB経路で交換し、それらをECDHの鍵交換の認証に使います。

OOBを使えば自動的に安全になるわけではありません。別経路が第三者による読み取りや書き換えに弱ければ、中間者攻撃への保護も得られません。NFC部品、アンテナ、スマートフォン側の対応、製造時の情報設定が必要になるため、PasskeyやJust Worksより採用例は限られます。一方、操作部を持たない機器で、利用者の「この個体と接続する」という行為を分かりやすく通信へ結び付けられる利点があります。

### SMPを開始する契機を決める

SMP（Security Manager Protocol）は接続後に使うプロトコルです。ただし、接続が成立しただけで、必ずペアリングが始まるわけではありません。暗号化を必要としないGATT操作だけであれば、ペアリングせずに通信を続けられます。

初回の接続でセキュリティを開始する主な契機は、次の三つです。

1. セントラル側のセキュリティマネージャーが、Pairing Requestを送る
2. ペリフェラルがSecurity Requestを送り、必要なセキュリティレベルをセントラルへ要求する
3. 暗号化や認証を必要とするGATT属性へのアクセスが拒否され、セントラル側のOSやBLEスタックが暗号化またはペアリングを始める

三つ目では、GATTサーバーが、暗号化されていない接続から保護対象の属性へアクセスされたことを検出します。ATTは`Insufficient Encryption`や`Insufficient Authentication`を返します。それを受けたクライアント側のセキュリティマネージャーは、保存済みの鍵があれば暗号化を開始し、必要な鍵がなければペアリングを開始できます。したがって、GATTアクセスがSMPを直接呼び出すのではなく、属性のアクセス条件を満たせなかったことが、OSやBLEスタックのセキュリティ処理を開始する契機になります。

iOSのCore Bluetoothでは、アプリケーションがSMPのPairing Requestを直接送るAPIは提供されていません。従来から一般的なのは、アプリケーションが暗号化を必要とするキャラクタリスティックをRead、Write、または購読し、Core Bluetoothが必要に応じてペアリングを進める流れです。AppleのCore Bluetooth Programming Guideも、暗号化を要求するキャラクタリスティックへのアクセスを契機としてペアリングを試みる動作を説明しています。

ただし、これだけがiOSでペアリングを始める経路ではありません。iOS 18以降のAccessorySetupKitを使う製品では、アクセサリーのセットアップ画面でLEペアリングを行い、その後にCore Bluetoothで接続して通信できます。この場合は、アプリケーションが保護対象のキャラクタリスティックへアクセスするより前に、セットアップ処理の一部としてペアリングが進みます。通常のCore Bluetoothによる通信と、AccessorySetupKitによる発見、許可、ペアリングを分けて考える必要があります。

ファームウェア側で接続直後にSecurity Requestを送るか、保護対象のGATT属性へアクセスされるまで待つかによって、利用者がペアリング画面を見る時点が変わります。接続直後に常にSecurity Requestを送ると、公開情報を読むだけの利用者にもペアリングを求めることになります。保護対象へのアクセスまで待つと、必要な利用者だけにペアリングを求められますが、最初のReadやWriteがセキュリティ処理の間待たされることを、アプリケーション側も考慮する必要があります。

### 鍵を使って接続を暗号化する

ペアリングで鍵を準備した後、その鍵を使ってLink Layerの接続を暗号化します。暗号化されるのは、特定のキャラクタリスティックの値だけではなく、その接続上を流れるLink Layerのペイロードです。暗号化されたData Physical Channel PDUにはMIC（Message Integrity Check）が付き、受信側は共有した鍵を使って改ざんも検出します。暗号化とMICは、別々のチェックボックスとして選ぶ機能ではありません。

GATTの属性には、「暗号化された接続でなければ読み出せない」「認証された接続でなければ書き込めない」といったアクセス条件を設定できます。GATTクライアントがその属性へアクセスしたことをきっかけに、OSやBLEスタックがペアリングや暗号化を始める場合もあります。そのため、接続直後に必ずペアリング画面が出るとは限りません。

過去のBLE仕様には、Link Layerのペイロードを暗号化せず、CSRK（Connection Signature Resolving Key）を使った署名をWrite Commandへ付けるData Signingがありました。これは任意のパケットへ鍵付きチェックサムを付ける機能ではなく、書き込みに限定された仕組みです。Data SigningとLE Security Mode 2はBluetooth Core Specification v6.3で廃止されたため、本書では新しい製品の保護方式として扱いません。通信内容を隠し、改ざんも検出する必要がある場合は、現在のLink Layer暗号化を使います。

暗号化された通信であることは、その利用者に製品の操作権限があることまで保証しません。BLEのリンクを保護することと、アプリケーションやクラウドサービスで利用者を認可することは、別の設計です。

### ボンディングで鍵を保存する

ボンディング（Bonding）は、ペアリングによって得た鍵を、次回以降の接続でも利用できるように保存することです。ボンディングしない場合は、接続を終えた後に鍵を残さず、必要になれば改めてペアリングします。

ボンディングした機器同士は、再接続したときに保存済みの鍵を使って暗号化を開始できます。利用者へ毎回同じ確認操作を求めずに済むため、個人が継続して使う周辺機器に向いています。

ただし、スマートフォン側と周辺機器側は、対応する鍵をそれぞれ保存します。ファームウェアの書き換えや工場出荷時リセットで片側だけの鍵が消えると、もう片側に残った鍵では暗号化を再開できません。開発中に「接続した直後に切れる」場合は、保存済みのボンディング情報が両側で一致しているかも確認します。

### 接続、暗号化、GATT操作を分ける

本章の流れでは、接続を作った後、GATTの値を交換する前または交換中に必要なセキュリティを満たします。

接続後、必要な時点で鍵を準備して暗号化し、属性のアクセス条件を満たしてからGATT操作へ進みます。

すべての通信でこの全段階を通るわけではありません。暗号化が不要な属性は、そのまま読み書きできます。すでにボンディングしている相手とは、保存した鍵を使って暗号化できます。接続済み、ペアリング済み、ボンディング済み、暗号化済みは、それぞれ別の状態として切り分けます。
