### 接続要求から接続が始まるまで {#sec:connection}

スキャンで目的の機器を見つけても、その時点では継続してパケットを交換する通信路はありません。スキャナーが受信したのは、アドバタイザーが周囲へ送ったアドバタイジングパケットです。GATTで値をやり取りするには、ここから通信相手を一台に決めて接続します。

#### 接続可能な相手へ要求を送る

接続を開始する機器は、接続可能なアドバタイジングパケットを受信したチャンネルで接続要求を送ります。このとき、接続を開始する側をイニシエーターと呼びます。アドバタイザーが接続要求を受信して受け入れると、アドバタイジングによる通信を終え、接続中の通信へ移ります。

すべてのアドバタイジングが接続を受け付けるわけではありません。ビーコンのように情報を周囲へ知らせるだけの使い方では、アドバタイジングパケットを受信できても接続できません。アプリケーションから見える「機器を発見した」と「機器へ接続できる」は、別の条件です。

接続要求には、接続イベントの時刻、使用するデータチャンネル、接続の間隔などを両者が共有するための情報が含まれます。各フィールドの構造をまだ知らなくても、接続要求によって「いつ、どのチャンネルで相手を待つか」を両者が予測できるようになることを押さえてください。

#### 接続前後で役割が変わる

接続前は、パケットを送って存在を知らせる側がアドバタイザー、それを受信する側がスキャナーです。接続を開始するとき、スキャナーはイニシエーターとして接続要求を送ります。

接続が始まると、接続イベントを開始する側がセントラル、応答する側がペリフェラルになります。本章で扱うスマートフォンと周辺機器の例では、通常、スマートフォンがセントラル、周辺機器がペリフェラルになります。

これらは機器に固定された名称ではなく、その通信で果たす役割です。同じ機器が別の通信では異なる役割を持つこともあります。接続前後で役割が変わる様子は、続く[@fig:connection-establishment-sequence]でも確認できます。

#### 実際のパケットで接続開始を追う

ここまでの流れを、説明用の`CONNECT_IND`を使って時間軸に当てはめます。次の例では、スマートフォンが、接続可能な`ADV_IND`を送っている周辺機器へ接続します。

`ADV_IND`の受信から最初の接続イベントまでを、[@fig:connection-establishment-sequence]に示します。

![周辺機器がADV_INDを送り、スマートフォンがCONNECT_INDを返した後、両者がペリフェラルとセントラルへ移り、最初のData PDUを交換する時間軸。](images/diagrams/ch02-connection-establishment-sequence.png){#fig:connection-establishment-sequence}

`CONNECT_IND`は、受信した`ADV_IND`と同じプライマリーアドバタイジングチャンネルで送られます。`CONNECT_IND`を送受信した後は、アドバタイジングチャンネルで相手を探す通信から、データチャンネルを使う接続中の通信へ移ります。

次の16進列は、この流れを説明するために作った`CONNECT_IND`のPayloadの例です。実機から取得したパケットキャプチャーではありません。先頭の`InitA`と`AdvA`に続く22 byteが、接続後の条件を伝える`LLData`です。

```text
InitA
01 00 DE C0 DE C2

AdvA
02 00 EF BE AD C3

LLData
70 83 32 9A  12 34 56  02  04 00  18 00
00 00  C8 00  FF FF FF FF 1F  05
```

Bluetoothのパケットでは、複数byteの数値が最下位byteから並ぶフィールドがあります。また、デバイスアドレスも、一般的なコロン区切りの表示とパケット内の並びが逆になります。この例の`InitA`は`C2:DE:C0:DE:00:01`、`AdvA`は`C3:AD:BE:EF:00:02`と表示されます。パケット解析ツールが値を解釈して表示する場合は、画面上の順序がこの16進列と異なることがあります。

`LLData`をフィールドへ分けると、[@tbl:connect-ind-example]のようになります。まず、接続後のパケットを識別するAccess Address、最初の待ち合わせ時刻を決めるWinSizeとWinOffset、接続イベントの間隔を決めるIntervalに注目してください。残りのフィールドは、後続項で役割が必要になったときに読み返せます。

| フィールド | パケット内の値 | この例で表す内容 |
|---|---|---|
| Access Address | `70 83 32 9A` | 接続後のData PDUを識別する値`0x9A328370` |
| CRCInit | `12 34 56` | 接続後のCRC計算で使う初期値 |
| WinSize | `02` | 最初の送信ウィンドウの幅は$2 \times 1.25\ \mathrm{ms} = 2.5\ \mathrm{ms}$ |
| WinOffset | `04 00` | 最初の送信ウィンドウのオフセットは$4 \times 1.25\ \mathrm{ms} = 5\ \mathrm{ms}$ |
| Interval | `18 00` | コネクションインターバルは$24 \times 1.25\ \mathrm{ms} = 30\ \mathrm{ms}$ |
| Latency | `00 00` | Peripheral Latencyは0 |
| Timeout | `C8 00` | スーパービジョンタイムアウトは$200 \times 10\ \mathrm{ms} = 2\ \mathrm{s}$ |
| Channel Map | `FF FF FF FF 1F` | 37本すべてのデータチャンネルを使用する |
| HopとSCA | `05` | 下位5 bitのHopは5、上位3 bitのSCAは0 |

: 説明用CONNECT_INDのLLData {#tbl:connect-ind-example}

この例では、`CONNECT_IND`の末尾から$1.25\ \mathrm{ms}$のTransmit Window Delayを置き、さらにWinOffsetが示す$5\ \mathrm{ms}$を待った位置から、最初の送信ウィンドウが始まります。したがって、セントラルが最初のData PDUを送信する時刻$t1$は、`CONNECT_IND`の末尾から$6.25\ \mathrm{ms}$後に始まる、幅$2.5\ \mathrm{ms}$の範囲に入ります。

ペリフェラルは、この時間に合わせて受信回路を動かします。セントラルが最初のData PDUを送り、ペリフェラルが応答すると、最初の接続イベントで双方向のパケット交換が始まります。その後は、例に含まれる30 msのコネクションインターバルを基準として、接続イベントが繰り返されます。

ここで重要なのは、各フィールド名を暗記することではありません。`CONNECT_IND`という一つのパケットによって、二台が接続後に使う識別値、最初に待ち合わせる時間、接続イベントの間隔、使用するデータチャンネルを共有することです。各フィールドのビット配置、値の制約、チャンネル選択の計算は、[@sec:conn-establish]で詳しく扱います。

#### 発見と接続成立を分けて考える

アプリケーションの画面では、機器を発見してから接続完了が通知されるまでが、一つの「接続操作」に見えることがあります。しかし、無線上では少なくとも次の段階があります。

1. アドバタイジングパケットを受信する
2. アプリケーションが接続する相手を選ぶ
3. 接続要求を送る
4. 最初の接続イベントでパケットを交換する
5. ControllerからHostへ接続成立が通知される

発見結果が表示されるのに接続が完了しない場合は、アドバタイジングの受信までは進んでいます。その後の接続要求または最初の接続イベントから調べられます。このように、最後に確認できた段階を分けると、「つながらない」という現象を狭い範囲へ切り分けられます。
