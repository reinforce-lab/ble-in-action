### アドバタイザーは短いパケットを繰り返し送る {#sec:advertiser}

接続前の周辺機器は、スマートフォンからの問い合わせを常に待ち受けているわけではありません。アドバタイザーとして自分で決めた時刻に短いパケットを送り、それ以外の時間は無線回路を休ませます。ほとんどの時間を眠っていても、繰り返す短い送信によって存在を知らせられます。

#### 三つのチャンネルへ順に送る

接続前の周辺機器はアドバタイザーとして、アドバタイジングイベントごとに短いパケットを送信します。基本となるLegacy Advertisingでは、37、38、39の三つのプライマリアドバタイジングチャンネルへ順に送ります。

三つのチャンネルへ順に送信し、要求を待つ流れを、[@fig:advertising-event-sequence]に示します。

![アドバタイザーがチャンネル37、38、39へ順に送信し、それぞれの送信後にScan Requestまたは接続要求を待ってから休止する流れ。](images/diagrams/ch02-advertising-event-sequence.png){#fig:advertising-event-sequence}

三つのチャンネルでの送受信をまとめたものが、一回のアドバタイジングイベントです。使用するチャンネルは設定で選べます。三つすべてを使えば、スキャナーと同じチャンネル、同じ時刻に出会う機会を増やせます。

アドバタイジングパケットを送った後に何を受け付けるかは、Advertisingの種類によって異なります。

| Advertisingの性質 | 受け付ける要求 | 受信後の動作 |
|---|---|---|
| 接続可能 | 接続要求 | Advertisingを終えて接続へ移る |
| スキャン可能 | Scan Request | Scan Responseを返す |
| 接続不可・スキャン不可 | どちらも受け付けない | 情報を一方向に知らせる |

: Advertisingで受け付ける要求の違い {#tbl:advertising-request-types}

接続可能とスキャン可能は、同じ意味ではありません。接続要求を受け付けるかどうかと、Scan Requestへ応答するかどうかは、分けて考えます。`ADV_IND`は接続可能かつスキャン可能です。接続せずに情報を送るビーコンでは、接続要求を受け付けないAdvertisingを利用できます。

接続可能またはスキャン可能なLegacy Advertisingでは、アドバタイザーはパケットを送った直後に同じチャンネルで短時間受信します。Scan Requestを受信した場合はScan Responseを返し、接続要求を受信した場合はAdvertisingを終えて接続へ移ります。何も受信しなければ次のチャンネルへ進み、イベントが終わると次の送信時刻まで無線回路を休ませます。

#### 31バイトに発見の手がかりを入れる

Legacy Advertisingの`ADV_IND`パケットは、次の要素で構成されます。

| 要素 | サイズ | 役割 |
|---|---:|---|
| Preamble | 1バイト | 受信の準備とビット同期 |
| Access Address | 4バイト | アドバタイジング用の固定値 |
| Link Layer Header | 2バイト | PDUの種類や長さ |
| AdvA | 6バイト | アドバタイザーのデバイスアドレス |
| Advertising Data | 0〜31バイト | デバイスを見つけ、選ぶための情報 |
| CRC | 3バイト | 受信したビット列の誤り検出 |

Link LayerのPDU payloadとしては、AdvAとAdvertising Dataを合わせて最大37バイトです。このうちAdvAの6バイトを除いた最大31バイトが、一般に「Legacy Advertisingのアドバタイジングデータ」と呼ばれる範囲です。ファームウェアは、製品を見つけてもらうための情報を、この31バイトへ取捨選択して入れます。

Advertising Dataの中には、AD Structure（Advertising Data Structure）を必要な数だけ並べます。一つのAD Structureは、長さを示す`Length`、情報の種類を示す`AD Type`、実際の値である`AD Data`から構成されます。

```text
Length | AD Type | AD Data
Length | AD Type | AD Data
...
```

代表的なAD Typeには、次の情報があります。

- Flags：利用するLEの機能や発見モード
- Service UUID：接続後に利用できるサービスの手がかり
- Local Name：画面へ表示する名前
- Manufacturer Specific Data：企業ごとに定義するデータ
- Service Data：特定のサービスUUIDに対応するデータ
- Tx Power Level：パケット送信時の送信電力
- Appearance：機器の種類を表す値

`Length`と`AD Type`にもバイトを使うため、31バイトすべてを値へ使えるわけではありません。長いLocal Nameを入れると、それだけでほかの情報を入れる余地が減ります。接続先を選ぶために必須のService UUIDをAdvertising Dataへ入れ、表示名などを後述するScan Responseへ移す、といった割り振りが必要になります。

#### アドバタイジング間隔をファームウェアで決める

アドバタイジングは一度だけではなく、Advertising Interval（アドバタイジング間隔）ごとに繰り返します。この間隔は、周辺機器のファームウェアからBLEスタックへ設定する製品パラメーターです。Hostは、希望する間隔の最小値と最大値をControllerへ設定します。Legacy Advertisingでは20 msから10.24 sまで指定できるため、実際の製品でも数十 msから数 sまで幅広い値が使われます。

間隔を短くするとスキャナーが受信する機会は増えますが、周辺機器が無線回路を動かす回数も増えます。間隔を長くすると待機中の消費電力を抑えられる一方、アプリケーションが機器を見つけるまでの時間が長くなります。ここで決めているのは通信速度ではなく、発見される機会と待機中の消費電力です。接続後のコネクションインターバルとは別の値です。

Bluetooth Core SpecificationのGAPには、この二つを切り替える推奨例があります。LE 1M PHYで接続可能なAdvertisingを行う場合は、ユーザー操作によってAdvertisingを開始した少なくとも最初の30 sを30〜60 ms、その後のバックグラウンドAdvertisingを1〜1.2 sとしています。

この推奨例では、利用者の操作後に次のように間隔を切り替えます。

1. 最初の30 sは、Advertising Intervalを30〜60 msにして発見の速さを優先する
2. 30 sを過ぎても接続されなければ、1〜1.2 sにして待機中の消費電力を優先する

これはすべての製品にそのまま適用する必須値ではなく、GAPが示す推奨テンプレートです。たとえば、ボタンを押した直後だけ短い間隔に戻す、一定時間が経過したらAdvertising自体を停止する、といった製品の振る舞いを設計できます。

実際のアドバタイジングイベント間隔には、設定したAdvertising Intervalに0〜10 msのランダムな遅延が加わります。複数のアドバタイザーが同じ周期で動いても、送信時刻が重なり続けることを避けるためです。
