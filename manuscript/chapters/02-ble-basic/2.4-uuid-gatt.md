## フェーズ③前半：UUIDとGATT構造——データを「識別・整理する」言語 {#sec:uuid-gatt}

<!-- topic: 導入——接続後にまずすること -->

接続が確立すると、セントラルがすることは**サービス探索（Service Discovery）**です。「このデバイスには何が読み書きできるのか」という目次を調べる作業です。この目次の構造を定義しているのが**GATT（Generic Attribute Profile、ジェネリック・アトリビュート・プロファイル）**です。

GATTはBLEのデータ構造を定義する「言語」です。どのデバイスもこの言語に従ってデータを整理しているため、メーカーが違っても同じ操作で読み書きできます。


## UUID——誰もが使える「固有の名前」

<!-- topic: UUIDの役割と種類 -->

GATT上のすべての要素には**UUID（Universally Unique IDentifier）**という識別子が付いています。UUIDは128ビットの値で、世界中で一意であることが保証されます。数学的には重複の確率が天文学的に小さく、Bluetooth SIGの管理外の独自サービスなら `uuidgen` コマンドで生成したものを使えます。

128ビットのUUIDをそのまま通信でやり取りすると16バイト消費してしまいます。Bluetooth SIGが標準化したサービスや属性には、Bluetooth Base UUIDに埋め込んだ**16ビットの短縮UUID**が使えます。

```
Bluetooth Base UUID:
  0000xxxx-0000-1000-8000-00805F9B34FB

Heart Rate Service (0x180D) の128bit表現:
  0000180D-0000-1000-8000-00805F9B34FB
```

16ビットUUIDは通信では2バイトで済むため、標準サービスはこの短縮形を使います。独自サービスには128ビットのカスタムUUIDを使います。他社製品とUUIDが重複するかを心配する必要はありません。ビット数が十分に大きいため、ランダムに生成したUUIDが意図せず衝突することはまずありません。


## GATTの階層構造

<!-- topic: Profile→Service→Characteristic→Descriptorの関係 -->

GATTのデータは次の4層の階層で整理されています。

```
Profile（プロファイル）
  └─ Service（サービス）: UUID で識別される機能グループ
       ├─ Characteristic（キャラクタリスティック）: 実際のデータ
       │    ├─ Value（値）: センサー値やコマンドなど
       │    ├─ Properties（プロパティ）: Read / Write / Notify など
       │    └─ Descriptor（ディスクリプタ）: Characteristic の補足情報
       └─ Characteristic（2つめ以降も同様）
```

**プロファイル（Profile）**は、機器の振る舞い全体を定義した仕様書に相当します。「心拍センサープロファイル」であれば、心拍数を返すサービスや心拍計測フラグを保持するサービスがまとまっています。

**サービス（Service）**は機能のグループです。Heart Rate Service（0x180D）、Battery Service（0x180F）のように、用途ごとに独立したUUIDを持ちます。1つのデバイスが複数のサービスを持つことができます。心拍計がバッテリー残量も通知するために、Heart Rate ServiceとBattery Serviceの両方を持つというケースも一般的です。

**キャラクタリスティック（Characteristic）**がデータの実体です。Battery Service内の「Battery Level」キャラクタリスティック（UUID: 0x2A19）はバッテリー残量を0〜100の値で持ちます。キャラクタリスティックは**値（Value）**・**UUID**・**プロパティ（Properties）**の3要素で構成されます。

プロパティは「この値で何ができるか」を示すフラグです。Read（読み取り）・Write（書き込み）・Notify（通知）・Indicate（確認付き通知）・Write Without Response（応答なし書き込み）などがあります。プロパティの組み合わせは仕様書に定義されており、すべてのプロパティを持つキャラクタリスティックは存在しません。

**ディスクリプタ（Descriptor）**はキャラクタリスティックの補足情報です。値の単位や説明文を持つものもありますが、最もよく使うのが次に説明するCCCDです。


## CCCD——Notify購読のスイッチ

<!-- topic: CCCDの役割、なぜ必要か -->

**CCCD（Client Characteristic Configuration Descriptor）**は、Notifyまたは Indicateを有効にするためのスイッチです。GATTのDescriptorの一種で、UUID `0x2902` が割り当てられています。

ペリフェラルがNotifyプロパティを持っていても、**セントラルがCCCDに `0x0001` を書き込まない限り、通知は一切届きません**。

これには理由があります。複数のセントラルが同じペリフェラルに接続することがあります。AというアプリとBというアプリの両方が同じ心拍計に接続した場合、どちらのアプリに通知を送るかをペリフェラルが決める必要があります。CCCDを使って「自分はNotifyが欲しい」とセントラルが明示的に宣言する仕組みにすることで、通知を受け取りたいセントラルだけに通知を届けられます。

CCCDへの書き込み値の意味は次の通りです。

| 値 | 意味 |
|---|---|
| 0x0000 | 通知オフ（デフォルト） |
| 0x0001 | Notify を有効にする |
| 0x0002 | Indicate を有効にする |
| 0x0003 | Notify と Indicate の両方を有効にする |

正しい接続フローは「接続 → サービス探索 → CCCDに書き込んでNotify購読」の3ステップです。[@sec:data-exchange]で詳しく扱います。


## nRF ConnectでGATTテーブルを読む

<!-- topic: 実際にツールでGATTテーブルを確認する練習 -->

スマートフォンアプリの**nRF Connect for Mobile**（Nordic Semiconductor製、無料）を使うと、GATTテーブルをそのまま画面で確認できます。

1. アプリを起動してスキャンし、対象デバイスを見つけて「CONNECT」
2. 接続後に「Client」タブを開くと、サービスとキャラクタリスティックの一覧が表示される
3. 各キャラクタリスティックの横にプロパティ（R: Read、W: Write、N: Notify など）が表示される
4. Readアイコンをタップすると値が読み取れる。CCCDの横の「▶」をタップするとNotifyが有効になる

手元に適当なBLEデバイス（micro:bitやBLEイヤホンなど）があれば、nRF Connectで接続してGATTテーブルを眺めてみてください。Battery ServiceとDevice Information Serviceは多くのデバイスに実装されています。


## GATTテーブルのキャッシュ

<!-- topic: クライアントがテーブル情報をキャッシュする仕組み -->

GATTテーブルの構造——サービス、キャラクタリスティック、それぞれのハンドル番号——は、ファームウェアの更新でもない限り、通常は変わりません。たいていのクライアントは、初回接続時に読み出したテーブル情報をキャッシュし、2回目以降の接続ではテーブル情報の読み出しを省略して、すぐにキャラクタリスティックの読み書きに入ります。このキャッシュのおかげで、再接続時には1ゑ1つのパケットで目的のキャラクタリスティックの読み書きができます。これが、BLEの素早い再接続を支える重要な仕組みのひとつです。
