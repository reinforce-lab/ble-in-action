### 接続イベントでパケットを交換する {#sec:connection-events}

接続中のパケットは、いつでも自由な時刻に送るのではなく、接続イベントの中で交換します。セントラルとペリフェラルは、接続時に共有した情報を使い、次の接続イベントが始まる時刻と使用するデータチャンネルを予測します。

#### セントラルから交換を始める

接続イベントでは、セントラルが最初のパケットを送ります。ペリフェラルは、そのパケットを受信してから応答します。さらに送るデータがある間は、両者が交互にパケットを送ります。

ペリフェラルは、接続イベントの開始時刻に合わせて受信できる状態になります。セントラルから最初のパケットが届かなければ、ペリフェラルだけで同じ接続イベントの送信を始めることはできません。ペリフェラル側に送信したいデータがあっても、セントラルから始まるパケット交換の機会を使います。

この関係は、GATTクライアントとGATTサーバーの役割とは別です。GATTサーバーである周辺機器も、Notifyによってデータ送信を要求できます。ただし、そのデータが無線で運ばれるときは、接続イベント内のLink Layerのパケット交換に従います。

#### 一回の接続イベントで送れるパケット数は固定ではない

一回の接続イベントでは、セントラルとペリフェラルが交互に複数のパケットを交換できます。しかし、「一回の接続イベントでは常に何パケットまで」と決まった固定値はありません。

実際に交換できる数は、次の条件で変わります。

- 接続イベントをどこまで継続できるか
- 使用するPHYと一つのパケットを送る時間
- Link Layer Data PDUの長さ
- パケット間の時間
- 同じControllerが処理するほかの接続や無線処理
- 再送の有無
- Host、Controller、受信側アプリケーションのバッファー

送信側に続きのデータがある場合は、Link LayerヘッダーのMD（More Data）で相手へ知らせます。ただし、MDは次のパケットを受信できることや、その接続イベントが希望する時間だけ続くことを保証しません。セントラルのスケジューリングや実装上の制約によって、残りのデータが次の接続イベントへ送られることがあります。

Bluetooth Core Specification 6.xでは、Frame Space UpdateやShorter Connection Intervalsなど、パケット間隔や接続間隔に関係する機能が追加されています。これらは条件が合えば転送量を増やせますが、送信可能なパケット数を示すウィンドウや、受信バッファーの空きを通知する仕組みではありません。

#### 無線を動かす時間と休止する時間

送るデータがなくなり、接続イベント内のパケット交換が終わると、両者は次の接続イベントまで無線回路を休止できます。接続を維持するために、受信回路を常に動かし続ける必要はありません。

セントラルとペリフェラルが交互にパケットを交換する様子と、次の接続イベントまで無線を休める時間を、[@fig:connection-event-timing]に示します。

![一定のコネクションインターバルで始まる接続イベント。各イベントではセントラルとペリフェラルが交互にパケットを送り、交換が終わると次のイベントまで無線を休止する。](images/diagrams/ch02-connection-event-timing.png){#fig:connection-event-timing}

接続イベントが頻繁にあれば、送信するデータが生じてから次の交換機会までの待ち時間を短くできます。その一方で、無線を起動して相手のパケットを待つ回数が増えます。この時間の使い方が、BLEの応答性と消費電力に関係します。

#### 物理チャンネルをホッピングする

接続中は、2.4 GHz帯にある一つのPHYチャンネルだけを使い続けません。接続イベントごとに、0から36までの37個のデータ用PHYチャンネルから一つを選びます。一つの接続イベント内では選んだPHYチャンネルを使い、次の接続イベントでは選択アルゴリズムに従って別のPHYチャンネルへ移ります。この周波数の切り替えをチャンネルホッピングと呼びます。

ここで「チャンネル」と呼ばれるものを、三つに分けます。

| 名前 | 接続中の役割 | ホッピングとの関係 |
|---|---|---|
| PHYチャンネル | 電波を送受信する個々の周波数 | 接続イベントごとに切り替える |
| LE piconet physical channel | Access Address、時刻、PHYチャンネルの選択列などを共有して作る通信の場 | 複数のPHYチャンネルを順に使う |
| L2CAPチャンネル | ATT、SMP、アプリケーション用のデータをCIDで振り分ける論理的な通り道 | 周波数を表さず、ホッピングしない |

: 接続中に現れる三種類のチャンネル {#tbl:connection-channel-types}

LE piconet physical channel（LEピコネット物理チャンネル）は、一つの周波数を指す名前ではありません。接続した二台が、Access Address、接続イベントの時刻、使用できるPHYチャンネルの集合、次のチャンネルを選ぶ規則を共有することで成立します。

一方、L2CAPチャンネルは電波の周波数ではありません。たとえば、基本のATTはCID `0x0004`、SMPはCID `0x0006`のL2CAPチャンネルを使います。同じATTのデータを運んでいる途中でも、接続イベントが変われば異なるPHYチャンネルを使います。L2CAPチャンネルはHost側の多重化、PHYチャンネルのホッピングはController側の無線制御です。

#### 時刻とチャンネルを同時に予測する

セントラルとペリフェラルは、接続開始時に最初の接続イベントの時刻とチャンネルマップを共有します。その後は、接続イベントを数えるカウンターと共通のチャンネル選択アルゴリズムを使い、次に待ち合わせる時刻とPHYチャンネルをそれぞれ計算します。

チャンネルホッピングでは、二台が同じ順序を知るだけでは足りません。同じ接続イベントを同じ番号として数え、同じ時刻に同じPHYチャンネルへ無線回路を合わせる必要があります。セントラルは接続イベントの基準時刻に最初のパケットを送信し、ペリフェラルはその時刻より少し前から受信を始めます。

二台のクロックには誤差があります。最後に同期できたパケットから時間が経つほど、セントラルが送信する時刻の予測にも幅が生じます。ペリフェラルは、その誤差を見込んで受信を開始する時刻を早め、待ち受ける時間を広げます。この広がりをWindow Widening（ウィンドウ拡大）と呼びます。有効なパケットを受信できれば、ペリフェラルはその時刻を新しい同期の基準にできます。

このため、接続イベントを長く受信できない状態が続くと、ペリフェラルはより長く無線回路を動かして次のパケットを探す必要があります。それでもSupervision Timeoutまで有効なパケットを受信できなければ、接続を喪失したと判断します。ホッピング、時刻同期、切断検出は別々の機能ではなく、同じ接続イベントを両者が追い続けるために組み合わさっています。

#### 干渉の多いPHYチャンネルを外す

BLEとWi-Fiは同じ2.4 GHz帯を使うため、場所やWi-Fiの使用チャンネルによって、特定のBLE PHYチャンネルで受信失敗が増えることがあります。BLEは、接続に使用するPHYチャンネルを示す37ビットのチャンネルマップを持ちます。使用するチャンネルをUsed、避けるチャンネルをUnusedとして表し、ホッピングの計算結果がUnusedなら、Usedの集合にある別のチャンネルへ割り当てます。

接続のチャンネルマップを決めるのはセントラルです。接続開始時に最初のマップを伝え、接続後に干渉状況が変われば新しいマップを通知できます。少なくとも二つのPHYチャンネルはUsedとして残します。

Controllerは、パケットの失敗率や電波環境から各PHYチャンネルを評価できます。Hostも、周辺のWi-Fiが使う周波数など、ローカルに得た情報をチャンネル分類としてControllerへ渡せます。Channel Classificationに対応するペリフェラルは、自分が観測したチャンネル状態をセントラルへ報告できます。セントラルは、これらの情報を組み合わせて接続のチャンネルマップを更新します。

ファームウェアからどこまで制御できるかは、製品がセントラルとペリフェラルのどちらで動くか、ControllerとBLEスタックがどのAPIを公開するかによって異なります。組み込み機器がセントラルなら、Hostからチャンネル分類を設定できる場合があります。ペリフェラルなら、対応機能を使って分類結果を報告できますが、接続のチャンネルマップを単独では変更できません。

スマートフォンがセントラルの場合、通常のCore Bluetoothアプリケーションはチャンネルマップを直接指定しません。iOSとBluetooth Controllerが無線環境やほかの通信を含めて管理します。したがって、周辺機器のファームウェアは、特定のPHYチャンネルが常に使われることや、既知のWi-Fiチャンネルが必ず除外されることを前提にしません。

チャンネルホッピングは、干渉をなくす仕組みではありません。使用可能な周波数を分散し、状態の悪いPHYチャンネルをマップから外すことで、一つの周波数の干渉が接続全体へ与える影響を小さくします。チャンネル選択アルゴリズムとチャンネルマップの更新手順は、[@sec:ch3]で詳しく説明します。

#### 無線区間で受信を確認する

Link Layerは、パケットに含まれるシーケンス情報を使い、相手が直前のパケットを受信したかを確認します。正しく受信されたことを確認できなければ、同じデータを再送します。この仕組みは、干渉などによって一つのパケットを受信できなかった場合に、無線区間で回復するためのものです。

ここでの受信確認は、ATTのWrite ResponseやIndicationに対するConfirmationとは別です。Link Layerの確認は相手のControllerへパケットが届いたことを扱います。ATTの応答は、相手のATTがRequestやIndicationを処理したことを扱います。さらに、製品のモーターが動いた、値をフラッシュメモリーへ保存した、といった処理完了も別の位置です。
