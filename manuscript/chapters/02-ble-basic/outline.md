まず「地図」を見せる。BLE通信がどのようなフェーズを経てデータに届くかを一枚の図と文章で示し、その後に各フェーズの仕組みを順番に解説する。読者は常に「いまどのフェーズを学んでいるか」を把握しながら読み進められる。

```

```

#### 2.2 フェーズ①：アドバタイジングとスキャン——デバイスを「見つける」
**ファイル**: `2.2-advertising-scanning.md`  
**概要**:
- アドバタイジングとは：3チャンネルへの間欠ブロードキャスト、電波を「名刺を配る」イメージ
- アドバタイジングパケットの構造と主要フィールド（デバイス名、サービスUUID、メーカーデータ等）
- アドバタイジング間隔：省電力と応答速度のトレードオフ
- スキャンの種類：パッシブスキャンとアクティブスキャンの違い
- スキャンレスポンス：追加情報を返す仕組み
- 接続なしで完結するビーコン動作（iBeacon・Eddystone）との関係

**エピソード：日曜日のファミレスで接続できなかった話**
- BLEデバイスの試作品をファミレスでデモしようとしたら、なかなか接続が確立できなかった
- 原因：周囲の keyfob・スマホ・BLE機器が大量のアドバタイジングパケットをブロードキャスト中
- アドバタイジングチャンネルは37・38・39の3チャンネルのみ（データチャンネルの37本とは別）
- 人が密集する場所では、この3チャンネルが多数デバイスのパケットで飽和しやすい
- 接続要求（CONNECT_IND）もアドバタイジングチャンネルを使うため、タイミングが取れずに接続失敗になる
- 対策：アドバタイジング間隔を短くする、試作時は電波の少ない環境でデモする、本番ではその環境を考慮した設計をする

**想定ページ数**: 5〜6ページ

#### 2.3 フェーズ②：接続と接続パラメータ——通信路を「確立する」
**ファイル**: `2.3-connection.md`

#### 2.4 フェーズ③——前半：UUIDとGATT構造——データを「識別・整理する」言語
**ファイル**: `2.4-uuid-gatt.md`  
**概要**:
- UUIDとは：128bitの識別子、16bit短縮形、SIG割り当てとカスタムの使い分け
- GATTの階層構造：Profile → Service → Characteristic → Descriptor
- サービス：機能グループの単位（例：Heart Rate Service、Battery Service）
- キャラクタリスティック：値・UUID・プロパティの3要素
- CCCD（Client Characteristic Configuration Descriptor）の役割
- nRF ConnectでGATTテーブルを確認し、構造を読み取る練習

**想定ページ数**: 4〜5ページ

#### 2.5 フェーズ③——後半：データ交換——Read / Write / Notify / Indicate
**ファイル**: `2.5-data-exchange.md`  
**概要**:
- プロパティの種類と使い分け：Read・Write・Write Without Response・Notify・Indicate
- Read：セントラルが値を問い合わせる（ポーリング型）
- Write / Write Without Response：セントラルがデバイスに値を書き込む
- Notify：ペリフェラルが値の変化をセントラルに自動送信（応答なし）
- Indicate：Notifyに応答確認を加えた信頼性重視の通知
- CCCDへの書き込みでNotify/Indicateを購読する手順
- 標準プロファイル仕様書でプロパティの組み合わせを確認する読み方

**想定ページ数**: 3〜4ページ

#### 2.6 ペアリングとボンディング——通信を「守る」仕組み
**ファイル**: `2.6-pairing-bonding.md`  
**概要**:
- ペアリングとは：暗号化鍵を交換して通信を保護する手続き
- ボンディングとは：鍵をフラッシュに保存し再接続時の手続きを省略する仕組み
- ペアリングモード：Just Works / Passkey Entry / Numeric Comparison の違いと選び方
- セキュリティレベル（LE Security Mode 1/2）の概念
- ボンディング済みデバイスの管理（iOS・Androidでの削除方法）
- いつペアリングが必要で、いつ不要か——判断基準

**エピソード：iPhoneの設定アプリで読み解くペアリング・ボンディングの違い**
- iPhoneの「設定 → Bluetooth」に表示されるデバイスリストは、鍵の有無・保存状態を直接反映している
  - **なし（ペアリングもボンディングもない）**: 設定アプリには一切表示されない。アプリが直接スキャン→接続する製品はこれが多い
  - **ペアリングのみ（鍵の交換あり・保存なし）**: 接続中は設定アプリにデバイスが表示されるが、切断すると消える
  - **ボンディング（鍵の交換あり・保存あり）**: 切断後も設定アプリにデバイスが残り続ける。次回は鍵交換を省略して素早く再接続できる
- **鍵の不一致問題（開発でよく起きるトラブル）**:
  - デバイス側をファームウェア書き換えや工場リセットで初期化すると、保存していた鍵が消える
  - iPhone側はまだ古い鍵を持っているため、接続してもセキュリティエラーで即切断される
  - 修復手順：iPhone の設定アプリでデバイスを「登録を削除」し、再度ボンディングを行う
  - 開発中に何度もファームを書き換える場合、このリセット作業が頻繁に発生する——ボンディングを使うかどうかは設計段階で意識しておく

**想定ページ数**: 4〜5ページ
