## 一台の機器の初回利用と再接続を追う {#sec:ch2-device-lifecycle}

電池で動くセンサーを、スマートフォンから初めて利用します。このセンサーは接続可能なAdvertisingを行い、設定値へのアクセスを暗号化し、測定値をNotifyで送ります。一度登録したスマートフォンとはボンディングし、切断後も再接続を受け付けます。

公開情報だけを扱ってペアリングしない製品や、必要なときだけ接続してすぐ切断する製品もあります。このセンサーは、その中の一つの設計です。電源を入れてから測定値を受け取るまでを追うと、別々の規格に見えた仕組みが、利用者の一回の操作へ集まってきます。

### 電源投入から接続まで

利用者がセンサーの電源を入れると、ファームウェアは接続可能なAdvertisingを開始します。スマートフォンはスキャン中にアドバタイジングパケットを受信し、OSがアプリケーションへ発見結果を通知します。アプリケーションが機器を一覧へ表示し、利用者が選択すると接続を要求します。

利用者が機器を探している時間は、短いAdvertising Intervalでパケットを繰り返すと発見されやすくなります。そのまま接続されない場合は、一定時間後にAdvertising Intervalを長くして消費電力を抑えられます。AppleのTechnical Q&A QA1931や複数のBluetooth標準プロファイルに現れる「最初の30秒は短く、その後は長くする」という例は、主にこの接続前のAdvertisingやスキャンに対するものです。

接続要求が受け入れられると、周辺機器はアドバタイザーからペリフェラルへ、スマートフォンはスキャナーからセントラルへ役割を変えます。二台は接続イベントの時刻とPHYチャンネルを共有し、同じAccess Addressを使ってパケットを交換します。

### 接続直後の処理を早く終える

接続直後には、製品を使い始めるための通信が集中します。GATTキャッシュを利用できない初回接続では、スマートフォンがサービス、キャラクタリスティック、ディスクリプターを探索します。その後、現在値の読み出し、Notifyの有効化、製品固有の初期設定などを行います。

保護されたキャラクタリスティックへアクセスすると、暗号化や認証が不足していることを示すATTエラーが返り、スマートフォンのOSがペアリングを始める場合があります。ファームウェアが接続後にSecurity Requestを送る構成なら、GATTアクセスより先にペアリングが始まることもあります。ペアリングで作った鍵を保存すれば、このスマートフォンとセンサーはボンディングした状態になります。

これらの処理では、次に送るATTやSMPのパケットがすでに待っていることがあります。Connection Intervalを長くしても、必要なパケット数は減りません。次の接続イベントまでの待ち時間が増えるため、利用者が操作できる状態になるまでの時間が長くなります。

Bluetooth GAPは、LE 1M PHYで接続を開始するときのConnection Intervalとして30 msから50 msを推奨し、ボンディング、暗号化、サービス探索などの初期手続きが終わった後に、用途に合う値へ変更する考え方を示しています。Heart Rate ProfileやBlood Pressure Profileでも、サービス探索や暗号化が終わるまで初期の接続パラメーターを受け入れ、その後に用途に適した値への変更を要求します。

初期処理を短いConnection Intervalで進める目的は、単に通信速度を高く見せることではありません。利用開始に必要な処理を早く終え、利用者が製品を操作できる状態へ移すことです。

### 平常時は用途に合う間隔で接続を維持する

GATT探索、暗号化、現在値の取得、Notifyの設定が終わると、センサーは平常時の動作へ移ります。測定値が変化したときだけNotifyを送り、それ以外の時間は接続を維持するだけなら、接続直後ほど頻繁な交換機会は必要ありません。

ペリフェラルは、用途に適したConnection IntervalやPeripheral Latencyへの変更を要求できます。ただし、使用する値を最終的に決めるのはセントラルです。スマートフォンは、ほかのBLE接続、Wi-Fiとの共存、OSの電力管理なども考慮するため、要求した値がそのまま採用されるとは限りません。ファームウェアは、更新後に実際の値を確認し、許容範囲の異なる値でも動作する必要があります。

通信が少ない状態でConnection Intervalを長くすれば、ペリフェラルが無線を起動する頻度を減らせます。一方、利用者が操作を始めた場合や、連続した測定値、ログ、OTA用データを転送する場合は、再び短いConnection Intervalを要求できます。

Apple Watch向けの公式解説では、待機中も接続を維持する周辺機器に150 ms以上の長いConnection Intervalを使い、低い遅延が必要なときに短い値へ変える設計が紹介されています。Apple製品が受け入れる値には独自の条件があり、HIDなど一部の用途には例外もあります。Apple製品と組み合わせるファームウェアでは、Bluetooth仕様だけでなく、対象OSと製品種別の最新ガイドラインも確認します。

この切り替えによって、GATTの初期処理、利用者が操作できるまでの時間、接続中の消費電力が一つの設計としてつながります。必要な通信が集中する時間は短いIntervalで早く終え、通信が少ない時間は長いIntervalで接続を維持します。

### 切断したら通信途中の状態を確かめる

利用者やアプリケーションが切断を要求した場合は、Link Layerで終了を通知できます。相手の電源断、通信範囲外への移動、強い干渉などによって有効なパケットを受信できなくなった場合は、Supervision Timeoutによって接続喪失を検出します。

切断すると、その接続で実行中だったATTのRequest–ResponseやIndication–Confirmationは完了できません。Writeを送ろうとしていたこと、Link Layerで確認されたこと、ATTのResponseを受け取ったこと、ファームウェアが処理したことは、それぞれ異なる状態です。再接続しただけで、未完了の操作が自動的に続くわけではありません。

センサーのファームウェアは、切断理由と製品の方針に従ってAdvertisingを再開します。意図しない通信途絶ならすぐに再接続を待ち、利用者が明示的に利用を終了した場合はAdvertisingを始めない、といった違いを持たせられます。再接続を待つ場合も、最初は短いAdvertising Intervalを使い、一定時間後に長くできます。

### 再接続では保存した情報を再利用する

スマートフォンがAdvertising中のセンサーを見つけて接続を要求すると、新しいLink Layerの接続が作られます。以前の接続が復活するのではなく、接続イベントの時刻、Access Address、使用するチャンネルなどを改めて決めます。

ボンディング済みなら、両方の機器が保存したLTKを使って接続を暗号化できます。初回と同じAssociation Modelでペアリングをやり直す必要はありません。ただし、片側だけが鍵を失っている場合は暗号化を再開できないため、古いボンドを削除してペアリングし直す処理が必要になります。

GATTサーバーが公開するサービス、キャラクタリスティック、Attribute Handleは、通常、同じファームウェアであれば接続をまたいで変化しません。GATTクライアントは探索結果をキャッシュし、再接続後に再利用できます。GATTデータベースを変更できる製品では、Service ChangedまたはDatabase Hashを使い、古いキャッシュを使い続けないようにします。ボンディングしていない場合でも、Database Hashに対応していればキャッシュを検証できます。

NotifyまたはIndicateを有効にするCCCDの値は、クライアントごとの状態です。ボンディング済みの相手については、GATTサーバーはCCCDの値を接続をまたいで保持します。ボンディングしていない相手では接続ごとに初期値へ戻るため、再接続後にクライアントが設定し直します。アプリケーション側の購読APIやコールバックの復元はOSによって異なるため、GATTサーバーのCCCDと分けて確認します。

再接続時にGATTキャッシュと保存済みの設定を利用できれば、初回より少ないパケットで平常動作へ戻れます。初期用の短いConnection Intervalを使う場合も、その時間は短くなります。一方、ファームウェア更新でGATTデータベースが変わった場合や、ボンドが失われた場合は、探索、ペアリング、Notifyの設定などが改めて必要になります。

| 処理 | 初回接続 | ボンディング済みの再接続 |
|---|---|---|
| Link Layerの接続 | 新しく作る | 新しく作る |
| 接続の暗号化 | 必要ならペアリングして鍵を作る | 保存したLTKを使う |
| GATT探索 | キャッシュがなければ実行する | 有効なキャッシュを再利用できる |
| Notify／IndicateのCCCD | クライアントが設定する | サーバーは保存した値を復元できる |
| 未完了の製品操作 | 製品の状態から開始する | 自動継続せず、状態を確認する |

### 現象を通信の段階へ戻す

一台の機器の時間軸を知っていると、利用者から「つながらない」と報告された現象を、最後に進んだ段階へ戻せます。

| 画面や製品に見える現象 | 最初に確認する段階 |
|---|---|
| 機器が一覧に現れない | Advertisingの開始、電波での送信、スキャン、OSのフィルター |
| 機器は現れるが接続できない | 接続可能なAdvertising、接続要求、最初の接続イベント |
| 接続後に切れる | 接続イベントのパケット交換、電波環境、Supervision Timeout |
| 接続中だが保護された値を操作できない | ペアリング、暗号化、GATTのアクセス条件 |
| 目的の値が見つからない | GATTキャッシュ、サービス探索、キャラクタリスティック探索、UUID |
| Notifyが再接続後に届かない | ボンディング、CCCD、アプリケーション側の購読状態 |
| Writeしたが製品が動かない | ATT操作、各層の通信経路、ファームウェアの処理 |

: 通信の現象と確認する段階 {#tbl:ch2-troubleshooting-map}

「接続した」「送った」「届いた」という言葉だけでは、確認した位置が分かりません。セントラル／ペリフェラルは接続中のLink Layerの役割、GATTクライアント／GATTサーバーは値を操作する役割です。Link Layerの受信確認、ATTの応答、ファームウェアの処理、製品動作の完了も、それぞれ異なる位置にあります。

電波からGATTまでの場所の地図と、初回利用から再接続までの時間の地図は、同じ通信を異なる向きから見たものです。[@sec:ch3]では前者のPHY、Link Layer、Advertising、接続、SMPを拡大します。[@sec:ch4]では、その通信路を流れるATTとGATTを拡大し、周辺機器が公開する機能と値を設計します。
