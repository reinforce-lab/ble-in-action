### スキャナーはパケットを待つ {#sec:scanner}

スマートフォンなど、周辺のデバイスを見つける側はスキャナーとして動作します。スキャナーは、三つのプライマリアドバタイジングチャンネルを切り替えて受信し、周囲のアドバタイザーを探します。一つの無線回路は、同時に三つすべてを受信するのではなく、選んだ一つのチャンネルで待ちます。

アドバタイザーが送信したチャンネルと、スキャナーが受信しているチャンネルが同じで、さらに時間が重なると、アドバタイジングパケットを受信できます。アプリケーションから見ると、このパケットを受信したことが、デバイスの発見として通知されます。

```text
同じ場所
＋ 同じチャンネル
＋ 同じ時間
＝ アドバタイジングパケットを受信
＝ デバイスを発見
```

アドバタイジングイベントとスキャン時間が重なったときに機器を発見できる関係を、[@fig:advertising-scan-timing]に示します。

![アドバタイザーが間欠的に送信するアドバタイジングイベントと、スキャナーが受信するScan Windowの時間関係。送信と受信の時間が重なると、スキャナーはアドバタイザーを発見できる。](images/diagrams/ch02-advertising-scan-timing.png){#fig:advertising-scan-timing}

#### 受信する時間と消費電力

スキャナーは、選んだチャンネルでScan Windowの間受信を続けます。Scan Windowを長くするほど、アドバタイジングイベントと重なる可能性は高くなりますが、その時間だけ受信回路の電力を消費します。受信を休む時間を増やせば消費電力を減らせる代わりに、発見までの時間が長くなります。

この仕組みは、電力を使う待ち受けをなくしているのではなく、役割に応じて分担しています。典型的な製品では、短時間だけ動作するアドバタイザーを小さな電池で動く周辺機器が担当し、長く受信するスキャナーをスマートフォンやゲートウェイのように電力に余裕のある機器が担当します。BLE周辺機器の低消費電力は、短い送受信だけを行う側と、長く待ち受ける側を非対称に分けることで成立しています。

スマートフォンのアプリケーションは、OSのBLE APIへスキャン条件を渡し、OSから発見結果を受け取ります。実際にどのチャンネルをいつ受信するか、Scan Windowをどのように設定するか、重複した結果を通知するかは、OSが管理することがあります。

スキャンには、受信するだけのパッシブスキャンと、追加情報を要求できるアクティブスキャンがあります。アクティブスキャンでは、スキャナーがScan Requestを送り、アドバタイザーがScan Responseを返します。本章では、どちらの場合も「接続する前に相手の情報を集める」段階として扱います。

#### Scan Responseでもう一つのパケットを受け取る

スキャナーがスキャン可能なアドバタイジングパケットを受信すると、同じチャンネルでScan Requestを送れます。アドバタイザーはScan Responseを返し、最初のAdvertising Dataには収まらなかった追加情報を渡します。

```text
アドバタイザー                         スキャナー

Advertising Data  ──────────────────→
                  ←──────────────────  Scan Request
Scan Response Data ─────────────────→
```

Legacy AdvertisingのScan Response Dataも最大31バイトです。ただし、Advertising Dataの上限が62バイトへ増えるわけではありません。AdvertisingとScan Responseは別のパケットであり、Scan Responseを得るにはScan Requestと応答の交換が成功する必要があります。

パッシブスキャンではScan Requestを送らないため、Scan Response Dataは得られません。アクティブスキャンでも、パケットの衝突などによってScan RequestまたはScan Responseを受信できないことがあります。このため、目的の製品を発見し、候補を絞るために必須の情報は、最初のAdvertising Dataへ入れるのが基本です。完全なLocal Nameなど、取得できなかった場合でも発見自体には影響しない情報をScan Response Dataへ移せます。

スマートフォンでは、アプリケーションが無線回路へScan Requestを直接指示するとは限りません。たとえばiOSのCore Bluetoothでは、アプリケーションは周辺機器のスキャンをOSへ要求し、実際の受信タイミングや重複した結果の扱いをOSが管理します。アプリケーションからLink Layerのパッシブスキャンとアクティブスキャンを直接選ぶAPIではありません。発見結果は、Advertising DataなどをOSが項目ごとに分けた`advertisementData`辞書として通知されます。

#### iOSはバックグラウンドで受信機会を減らす

`bluetooth-central`バックグラウンドモードを宣言したiOSアプリは、バックグラウンドでも周辺機器を発見して接続できます。通常のバックグラウンドスキャンでは、`scanForPeripherals(withServices:options:)`へ一つ以上のService UUIDを指定する必要があります。`nil`を指定して周囲のすべての機器を探す方法ではなく、製品がAdvertising Dataで知らせるService UUIDを条件として探します。

ただし、フォアグラウンドと同じ頻度で発見イベントを受け取れるわけではありません。バックグラウンドでは`CBCentralManagerScanOptionAllowDuplicatesKey`の指定が無視され、同じ周辺機器を複数回発見した結果は一つのイベントへまとめられます。さらに、スキャンしているすべてのアプリがバックグラウンドにある場合は、iOSがアドバタイジングパケットを探す間隔を長くするため、発見までの時間も長くなります。

Appleは、これらを無線回路の使用を減らし、iOSデバイスの電池消費を抑えるための動作と説明しています。アプリケーションから見ると、同じアドバタイジングを繰り返し受信してRSSIの変化を追う処理や、短時間で必ず発見することを前提にした処理が、バックグラウンドでは同じように動きません。

なお、iOS 26以降には、Live Activityを開始したアプリがバックグラウンドでもフォアグラウンド相当のCore Bluetooth権限を使える例外があります。この場合はService UUIDを指定しないスキャンや、重複フィルターを無効にしたスキャンも可能です。通常のバックグラウンドモードと同じ動作ではないため、詳細はCore Bluetoothを実装する章で扱います。

一方、Appleの公開資料には、バックグラウンドではLink LayerのScan Requestを送らない、またはScan Response Dataを取得しないとは記載されていません。そのため、「Scan Responseだけに置いた情報は、iOSのバックグラウンドでは取得できない」と仕様として断定することはできません。Core BluetoothからScan Requestの有無を指定できない以上、Scan Response Dataが一定のタイミングで得られることへ依存せず、発見と候補の絞り込みに必須の情報はAdvertising Dataへ置くのが安全です。

発見結果には、同じ表示名の機器が複数含まれることがあります。表示名だけを永続的な識別子として扱うと、別の機器を選ぶ可能性があります。製品では、サービスUUIDやメーカー固有データなど、利用場面に合った情報を組み合わせて候補を絞ります。

#### 発見時間は一周期が目安とは限らない

スキャナーが連続して受信し、アドバタイザーが三つのチャンネルすべてを使い、干渉もない場合は、次のアドバタイジングイベントまでの時間、つまりおおむねAdvertising Interval程度が発見までの目安になります。

実際には、スキャナーが受信を休む、OSがスキャン時間を制限する、送信時刻に別の電波が重なる、といったことがあります。一回のイベントを受信できなければ、次のイベントを待つため、発見までに数周期以上かかります。Advertising Intervalは発見時間を考える基準にはなりますが、発見時間の上限を保証する値ではありません。

このため、スキャンを開始してすぐにデバイスが表示されなくても、それだけでは故障と判断できません。設定したAdvertising Interval、スキャナーの受信時間、電波環境を分けて考える必要があります。

#### アプリケーションが受け取るのは存在ではなくイベント

アプリケーションが受け取るのは、「デバイスが近くに存在し続けています」という状態ではありません。アドバタイジングパケットを一回受信した、というイベントです。

```text
アドバタイジングパケットを受信した
    ↓
アプリケーションが「この機器は近くにいる」と判断する
```

周辺機器の一覧からいつ消すかは、アプリケーションやOSが決めます。最後の受信から消去するまでの時間が短すぎると、パケットを一回受信できなかっただけで一覧が点滅します。長すぎると、電源が切れた機器が長く残ります。BLEから存在状態を受け取るのではなく、受信イベントから存在を推定している、と考える必要があります。
