## フェーズ③後半：データ交換——Read / Write / Notify / Indicate

<!-- topic: 導入——GATTのデータ操作は4種のプロパティで行う -->

GATTテーブルの構造を理解したら、次はそのテーブルを実際に操作します。BLEのデータ交換には、キャラクタリスティックに設定されたプロパティに応じて使える操作の種類が決まっています。操作の種類を理解すると「なぜこの操作が必要なのか」「どのプロパティを選ぶべきか」が判断できるようになります。

---

## Read——問い合わせて読む

<!-- topic: ポーリング型の読み取り -->

**Read**は、セントラルが「今の値を教えてください」とリクエストして、ペリフェラルが応答する操作です。リクエストとレスポンスのペアが1トランザクションを構成します。

```
セントラル → ペリフェラル: ATT_READ_REQ（読み取りリクエスト）
セントラル ← ペリフェラル: ATT_READ_RSP（値を返す）
```

バッテリー残量を確認するような「いまの値を知りたいときに都度聞く（ポーリング）」用途に向いています。値が常にリアルタイムで変化していてもセントラルが取りに行かない限り届かないため、頻繁に変化する値のリアルタイム通知には後述のNotifyを使います。

---

## Write / Write Without Response——書き込む

<!-- topic: 2種類の書き込みと使い分け -->

**Write（Write Request）**は、セントラルがペリフェラルに値を書き込む操作です。書き込みリクエストに対して、ペリフェラルは書き込みが完了したことを示すレスポンスを返します。

```
セントラル → ペリフェラル: ATT_WRITE_REQ（書き込みリクエスト）
セントラル ← ペリフェラル: ATT_WRITE_RSP（書き込み完了応答）
```

LEDのON/OFFを制御したり、設定値を変更したりするときに使います。応答が確認できるため、書き込みが正確に届いたことを確認できます。

**Write Without Response**は、ペリフェラルからの応答を待たない書き込みです。「打ちっぱなし」なのでフロー制御がなく、ペリフェラルがリクエストを精いっぱいに受け取れるところまで高速で連続書き込みができます。音楽のMIDIコマンドやモーター回転数の連続送信など、応答確認より送信スループットを優先したい場合に使います。

---

## Notify——変化を自動で受け取る

<!-- topic: サーバーからの自動通知、応答なし -->

**Notify（Notification）**は、ペリフェラルが値の変化を自発的にセントラルへ送信する操作です。セントラルからのリクエストは不要で、ペリフェラル側のトリガー（値の変化、タイマーなど）で送出されます。

```
セントラル ← ペリフェラル: ATT_HANDLE_VALUE_NTF（通知）
（セントラルからの応答は不要）
```

センサー値のリアルタイム通知に広く使われます。心拍センサーが1秒ごとに心拍数を送信する、加速度センサーが動きを検出したときに通知する、といった用途です。

ただし通知に対してセントラルからの確認応答（ACK）はありません。パケットの欠落は検知できませんが、その分オーバーヘッドが小さく、高頻度な通知に向いています。

---

## Indicate——確認付きの通知

<!-- topic: Notifyとの違い、信頼性重視 -->

**Indicate（Indication）**はNotifyに確認応答を加えた操作です。ペリフェラルが通知を送り、セントラルが受け取ったことを確認（Confirmation）を返します。

```
セントラル ← ペリフェラル: ATT_HANDLE_VALUE_IND（Indicationを送信）
セントラル → ペリフェラル: ATT_HANDLE_VALUE_CFM（受信確認）
```

ConfirmationをペリフェラルはConfirmationを受け取るまで次のIndicationを送れません（1トランザクションずつ）。そのため送信頻度はNotifyより低くなります。確実に届けたい重要な設定変更やアラートなど、頻度は低いが欠落は困る情報に使います。

---

## 接続後のCCCD書き込み手順

<!-- topic: Notify購読の正しいシーケンス -->

NotifyとIndicateを受け取るには、接続後にCCCDへの書き込みが必要です。正しいフローは次の通りです。

```
1. セントラルがペリフェラルに接続
2. サービス探索（GATTテーブルを読む）
3. 対象キャラクタリスティックのCCCDを見つける
4. CCCDに 0x0001（Notify有効）を WriteRequest で書き込む
5. 以降、ペリフェラルからNotifyが届くようになる
```

ステップ4を忘れると、ペリフェラルがNotifyを送出する実装になっていても通知は一切届きません。

---

## エピソード：ATTトランザクション30秒タイムアウトで画面が固まる

<!-- topic: Writeのタイムアウト、Write Without Responseとの使い分け -->

デバイスに設定値を書き込もうとしたとき、「書き込みをリクエストしたが応答が返ってこない」という状況に遭遇することがあります。アプリ画面に「送信中…」というインジケーターが出たまま30秒ほど固まり、最終的に「タイムアウト」のエラーが表示されます。

これはATTトランザクションのタイムアウト仕様によるものです。Write Request（応答ありの書き込み）を送ると、ペリフェラルからのATT\_WRITE\_RSPが返るまでトランザクションが「開いた」状態になります。**このトランザクションが30秒以内に完了しない場合、タイムアウトとみなされます**。しかもタイムアウト後はその接続での以降のATT PDUがすべて無効になり、回復するには接続を切断して再接続するしかありません。

原因として多いのは次の2つです。

1. **ファームウェアがATT\_WRITE\_RSPを返す実装を忘れている**。Writeを受け取ったら処理が完了したあとに応答を返す実装が必要ですが、応答を送る処理が漏れているとタイムアウトになります
2. **処理に時間がかかりすぎている**。フラッシュへの書き込みや外部センサーとの通信など重い処理の後に応答を返そうとすると、30秒を超えることがあります

対策は2つあります。処理が即座に完了する場合は正しくATT\_WRITE\_RSPを返す実装を確認すること。処理に時間がかかる場合は、**Write Without Responseを使って「送りっぱなし」にして、完了通知はNotifyで返す**という設計に変えることです。あるいは、まず「受け取った」という応答だけ即時返し、処理完了は後でNotifyで通知する設計もよく使われます。

---

## エピソード：Notifyを実装したのにデータが来ない——CCCD書き込み忘れ

<!-- topic: BLE開発初期最頻出トラブル、CCCDの役割 -->

BLE開発を始めてしばらく経ったある日、「ペリフェラルのNotifyが動いていないのでは？」という問い合わせを受けました。ファームウェア担当者は「実装した、確かに送信している記録もある」と言います。アプリ担当者は「接続はできているのにデータが届かない」と言います。両者の言い分は合っているのに、データが届きません。

原因はアプリ側でした。**CCCDへの書き込みが漏れていた**のです。

ペリフェラルはNotifyプロパティを備えていましたが、セントラルのアプリがCCCDに `0x0001` を書き込んでいなかったため、ペリフェラルは「このセントラルはNotifyを受け取りたくない」と判断してデータを送っていませんでした。ファームウェア側の送信ログには何も残りません（そもそも送っていないので）。

nRF Connectでテストすると、CCCDの「▶」をタップした瞬間にデータが届き始めました。

この問題はBLE開発では頻繁に起きます。チェックリストに「サービス探索後にCCCDへの書き込みを行うこと」を入れておくと防げます。また、Notify/Indicateを使う場合の接続後フローをチームで明示的に共有しておくと、「送った」「来た」の食い違いが起きにくくなります。
