### データを運ぶ向きと応答の違い {#sec:data-exchange}

前項では、スマートフォンから周辺機器へ向かうWrite Requestを使って、プロトコルスタック全体を通る経路を追いました。Read、Write Without Response、Notify、Indicateも同じ通信路を使います。違いは、どちらが送信を始めるか、ATTの応答を待つか、どのように処理の進み方を制御するかです。

#### Read——クライアントから問い合わせる

Readは、GATTクライアントがGATTサーバーへ値を要求する操作です。クライアントがRead Requestを送り、サーバーが値を含むRead Responseを返します。

現在のバッテリー残量や、機器の設定値を必要なときに取得する用途に向いています。値が変化したかを知るには、クライアントが改めてReadする必要があります。一定間隔で繰り返しReadする方法はポーリングと呼ばれます。

同じATTベアラーでは、クライアントはRead RequestへのResponseを受け取るまで、次のRequestを送りません。この要求と応答の組が、ATT上の一つのトランザクションになります。

#### Write Request——応答を待つ書き込み

Write Requestは、GATTクライアントからGATTサーバーへ値を書き込み、ATTのWrite Responseを待つ操作です。設定値の変更や、LEDのON／OFFのような操作に使えます。

Write Responseが示すのは、ATTサーバーがWrite Requestを処理して応答したことです。フラッシュメモリへの保存、モーターの移動、クラウドとの通信など、その値を受け取った後に始まる処理の完了までを自動的に表すものではありません。

長い処理がある場合は、Write Requestを受け付けたことを応答し、処理結果を別の状態値やNotifyで後から返す設計ができます。ATTの完了と製品機能の完了を分ける考え方は[@sec:ch4]で扱います。

#### Write Without Response——ATTの応答を待たない

Write Without Responseは、ATTのWrite Commandを使う書き込みです。サーバーからATTのResponseは返りません。そのため、ATTのトランザクションが終わるまで待たずに、次のCommandを送れます。

ただし、「Responseがない」と「どれだけでも送れる」は同じではありません。Host、HCI、Controller、受信側のバッファーと処理速度には限界があります。Core v6.3のATTでは、バッファー不足などで処理できないCommandは破棄されるため、信頼できないものとして扱うと定めています。

連続して値を送る場合は、SDKやOSが示す送信可能状態に従います。失ってはいけないデータなら、シーケンス番号、受信済み位置、アプリケーションレベルの応答などを製品のプロトコルに追加します。

#### OTAでは連続送信と再開を設計する

ファームウェアのOTA（Over-the-Air）更新では、数十KBからそれ以上のデータを接続中に連続して送ります。一つのGATT Writeだけでは運べないため、更新イメージを複数のチャンクへ分けます。

GATTで実装する場合は、制御用とデータ転送用のキャラクタリスティックを分ける構成が考えられます。

| 役割 | やり取りする情報 |
|---|---|
| 更新開始 | バージョン、全体サイズ、ハッシュ値、署名方式 |
| データ転送 | オフセットまたはシーケンス番号とデータ |
| 進行確認 | 書き込み済み位置、再送を始める位置、エラー |
| 更新確定 | 全体の検証結果、起動するイメージの選択 |

: GATTでOTA更新を行う場合の情報 {#tbl:gatt-ota-transfer}

データ転送には、Write Without Responseを連続して使う方法があります。Write Responseを毎回待たないため転送量を増やせますが、受信側が処理した位置はわかりません。スマートフォンから送信できたこと、相手のControllerがLink Layerパケットを受信したこと、ファームウェアがフラッシュメモリーへ保存したことは、それぞれ別の完了点です。

このため、OTAの送信側は次の制御を行います。

1. OSが示す一回の最大書き込み長に合わせてチャンクを作る
2. OSが次のWrite Without Responseを受け付けられる間だけ送る
3. ファームウェアから、保存済みのオフセットを定期的に受け取る
4. 切断した場合は、再接続後に保存済みの位置から再開する
5. 全体を受信した後、ハッシュ値や電子署名を検証してから起動対象を切り替える

iOSでは、`maximumWriteValueLength(for:)`で一回の書き込みに渡せる最大長を確認します。`canSendWriteWithoutResponse`が`false`になったら送信を止め、`peripheralIsReady(toSendWriteWithoutResponse:)`の通知を受けて再開します。これはiOS内部の送信バッファーへ無制限にデータを積まないための制御です。相手のファームウェアがフラッシュメモリーへ保存できたことまで保証するものではないため、製品のOTAプロトコルには別の進行確認が必要です。

ファームウェア側も、受信したチャンクをその場でフラッシュメモリーへ書けるとは限りません。BLEスタックが使う受信バッファーと、フラッシュ書き込みを待つバッファーを分け、空き容量を超えるデータを受け付けないようにします。更新途中で切断しても再開できる保存単位と、破損したイメージから起動しない仕組みも必要です。

Write Without ResponseにATTのResponseはありませんが、無線区間の受信確認や、HostとControllerの間の流量管理がなくなるわけではありません。問題になるのは、受信側アプリケーションの処理完了や保存位置を確認できないことです。層ごとに異なる受信確認とフロー制御は、[@sec:throughput]で詳しく扱います。

#### まとまったデータをL2CAPで運ぶ

まとまったデータを運ぶもう一つの方法が、L2CAPのConnection-Oriented Channelです。LE Credit Based Flow Controlでは、受信側が、さらに何個のL2CAPフレームを受け取れるかをクレジットとして送信側へ知らせます。送信側はクレジットを一つ消費してフレームを送り、クレジットがなくなると追加されるまで待ちます。

iOSのCore Bluetoothは、`openL2CAPChannel(_:)`で周辺機器のPSM（Protocol and Service Multiplexer）を指定し、L2CAPチャンネルを開けます。開いた`CBL2CAPChannel`は、入力と出力をストリームとしてアプリケーションへ提供します。PSMはアドバタイジングやL2CAPだけではアプリケーションから発見できないため、GATTのキャラクタリスティックでPSMを知らせ、その後にL2CAPチャンネルを開く構成が考えられます。

GATTは、更新開始、バージョン確認、進行状態など、意味の決まった操作を表しやすい方法です。L2CAP Connection-Oriented Channelは、連続するバイト列を明示的なフロー制御で運びたい場合に向いています。どちらを使っても、整合性確認や切断後の再開は製品として設計します。L2CAPのクレジットとほかの層のフロー制御の違いは[@sec:throughput]で、OTAの具体的なプロトコル、ブートローダー、署名検証、ロールバックは[@sec:ch7-firmware-update]で扱います。

#### Notify——サーバーから応答なしで知らせる

Notifyは、GATTサーバーからGATTクライアントへ値を送る操作です。クライアントが毎回Readしなくても、センサー値の変化や機器のイベントを知らせられます。ATTではNotificationに対するConfirmationを返しません。

Notifyを受け取る前に、GATTクライアントは対象のキャラクタリスティックを探索し、通知を受け取る設定を行います。この設定にはCCCD（Client Characteristic Configuration Descriptor）を使います。アプリケーションからは、OSの購読APIとして見えることがあります。

NotifyにもATTの応答によるフロー制御はありません。Unenhanced ATT bearerでは、受信側がバッファー不足で処理できないNotificationは破棄される可能性があります。周期的なセンサー値のように、次の値で更新できるデータと相性がよい一方、すべての通知を必ず処理する必要がある場合は上位の設計が必要です。

たとえば、温度、モーターの現在位置、OTAの進捗率などは、途中の値を一つ受信できなくても、次の値で現在状態を知ることができます。このような、頻繁に変化し、最新値を優先する情報にはNotifyが向いています。

#### Indicate——サーバーから確認付きで知らせる

IndicateもGATTサーバーからGATTクライアントへ値を送りますが、クライアントはConfirmationを返します。同じATTベアラーでは、サーバーは一つのIndicationに対するConfirmationを受け取るまで、次のIndicationを送りません。

この待ちがあるため、Notifyより送信頻度を上げにくい一方、ATT上で相手が確認した位置を得られます。ただし、Confirmationも製品の処理完了を自動的に保証するものではありません。受信後にアプリケーションが行う保存や表示まで確認したい場合は、さらに上位の仕組みが必要です。

IndicationへのConfirmationを待っている間も、同じ接続上のすべての通信が止まるわけではありません。Notificationを送ることや、クライアントからRequestまたはCommandを送ることはできます。待つ必要があるのは、同じATTベアラー上の次のIndicationです。

Indicateは、受信を確認してから次の状態通知へ進みたい、頻度の低い重要な情報に向いています。たとえば、更新イメージの検証結果、設定変更の確定、扉が目標位置へ到達したことなどです。一方、センサー値や進捗率を高い頻度で送り続ける用途では、一つずつConfirmationを待つことが転送量の制約になります。

NotifyとIndicateの使い分けを、デバイスの振る舞いから見ると次のようになります。

| デバイスから知らせる情報 | 向いている方法 | 理由 |
|---|---|---|
| 温度や加速度の連続値 | Notify | 次の値で現在状態を更新できる |
| モーターや扉の移動中の位置、進捗率 | Notify | 途中値の頻度を優先する |
| 操作の完了、設定の確定、重大な状態変化 | Indicate | ATTクライアントが受信したことを確認して次へ進める |
| 失ってはいけないイベントが連続する | Indicateまたは上位のACK | 順序と受信済み位置を管理する必要がある |

#### 長い製品処理は状態として表す

扉を開閉する機器を例にします。扉が動いている間は、別の開閉操作を実行できない製品があります。この排他制御はIndicateが自動的に行うものではなく、ファームウェアの状態機械として実装します。

たとえば、操作用キャラクタリスティックと状態用キャラクタリスティックを、次のように使います。

1. アプリケーションが操作用キャラクタリスティックへ`Open`をWriteする
2. ファームウェアが要求を受け付け、状態を`Moving`へ変える
3. 移動中の位置や進捗を、必要に応じてNotifyする
4. 移動中に別の操作を受けた場合は、`Busy`として拒否するか、製品仕様に従って予約する
5. 扉が目標位置へ到達したら、状態を`Open`へ変えてNotifyまたはIndicateする

最後の状態をIndicateすると、GATTサーバーは、クライアントのATTが完了状態を受信したことを確認してから、次のIndicationを送れます。ただし、Confirmationが表すのはATTでの受信確認です。利用者が画面を見たこと、アプリケーションが状態を保存したこと、扉が物理的に動作したことを確認する応答ではありません。扉の物理的な完了は、ファームウェアがセンサーなどで判定してから状態値へ反映します。

ATTのRequest–ResponseとIndication–Confirmationのトランザクションには、30秒のタイムアウトがあります。これは、相手が応答しない異常をATTが検出するための上限です。30秒まで製品処理を待たせてよい、という応答時間の目標ではありません。数秒以上かかる処理では、最初のWriteへ速やかに応答し、進行中と完了を別の状態値で知らせます。利用者へ表示する待ち時間やキャンセル方法は、ATTの30秒とは別に製品として決めます。

#### 応答を待つ仕組みと待たない仕組み

五つの操作を、向きとATTの応答で並べると、名前の違いが通信上の違いとして見えてきます。

| 操作 | 開始する側 | ATTの応答 |

| Write Without Response | クライアント | Responseなし |

| Indicate | サーバー | Confirmationあり |

: ATT操作の向きと応答の有無 {#tbl:att-operation-directions}

ResponseまたはConfirmationを待つ操作では、同じATTベアラー上で次の同種のトランザクションを開始する前に待つ位置ができます。Core v6.3では、ATTのトランザクションが30秒以内に完了しなければタイムアウトし、そのATTベアラーでは対象機器へ新しいATT PDUを送れないと定めています。

応答を待たないCommandとNotificationには、ATTとしてのフロー制御がありません。しかし、Link Layerの受信確認やHCIのバッファー管理まで消えるわけではありません。「ATTの応答」「無線区間の再送」「HostとControllerの流量管理」を同じACKやウィンドウとしてまとめないことが大切です。

#### 通信が止まる位置を見分ける

アプリケーションから値が届かないときは、少なくとも次の位置を分けます。

1. アドバタイジングを受信できず、機器を発見していない
2. 接続が成立していない、またはスーパービジョンタイムアウトで切断した
3. 必要な暗号化やアクセス条件を満たしていない
4. サービス探索が終わらず、目的のキャラクタリスティックを見つけていない
5. HostまたはControllerのバッファーへ次のデータを渡せない
6. ATTのRequestまたはIndicationに対する応答を待っている
7. Write Without ResponseまたはNotifyが受信側で処理されず失われた
8. ファームウェアまでは届いたが、製品としての処理が完了していない

アプリケーションのエラー、ファームウェアのログ、HCIログ、パケットキャプチャは、それぞれ観測できる位置が異なります。「送った」「届かない」だけで結論を出さず、最後に確認できた境界を探します。

同じWriteを調べても、観測手段によって確認できる範囲は異なります。HCIログや無線のパケットキャプチャは、利用するOS、開発環境、機材によって取得できる範囲が変わります。代表的な観測位置を、[@tbl:ble-observation-points]に示します。

| 観測手段 | 確認しやすいこと | それだけでは確認できないこと |
|---|---|---|
| アプリケーションのログとBLE APIのコールバック | スキャン結果、接続状態、サービス探索の結果、OSが通知したWriteの結果 | PHY上で実際に送信された時刻、ファームウェアが値を使った結果 |
| ファームウェアのログ | 接続と切断の通知、Write処理の呼び出し、受信した値、LED制御などの処理結果 | スマートフォンのアプリケーションがどのAPIを呼び出したか、途中の無線再送 |
| HCIログ | HostとControllerの間を通ったコマンド、イベント、接続データ | アプリケーション内部の意図、PHY上で送受信できなかった電波 |
| 無線のパケットキャプチャ | アドバタイジング、接続中のパケット交換、再送、無線上の時刻 | 暗号化されていて復号できない上位データ、受信後のファームウェア処理 |

: BLE通信を観測する位置と確認範囲 {#tbl:ble-observation-points}

たとえば、アプリケーションがWrite APIを呼び出したログだけでは、値が相手へ届いたとは判断できません。無線のパケットキャプチャで相手からLink Layerの受信確認を得ても、ファームウェアがLEDを点灯したことまではわかりません。反対に、ファームウェアのログに`0x01`が残っていれば、その値は無線区間と受信側のスタックを通過したと判断できます。

切り分けでは、一つの観測手段ですべてを証明しようとしません。アプリケーションのログで接続と探索を確認し、必要ならHCIログやパケットキャプチャで途中の境界を調べ、最後にファームウェアのログで受信後の処理を確認します。両端から最後に確認できた位置を近づけると、問題のある範囲を狭められます。
