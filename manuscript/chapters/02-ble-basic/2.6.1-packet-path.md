### GATTの値がファームウェアへ届くまで {#sec:packet-path}

前節までに作り、必要に応じて保護した通信路を使い、スマートフォンから周辺機器のLEDへ値を届ける経路を追います。ここでは、応答を伴うWrite Requestを例にします。

アプリケーションは「LEDを点灯する」という意味を知っていますが、下位の層はその意味を知りません。各層は、自分が担当する情報を付け加え、次の層へ渡します。受信側では、その情報を順に外しながら上位へ渡します。

#### 接続後に操作対象を見つける

接続が成立しただけでは、スマートフォンのアプリケーションは、LEDを操作するキャラクタリスティックがどこにあるかをまだ知りません。接続によってできるのは、セントラルとペリフェラルが接続イベントでパケットを交換する通信路です。その通信路の上で、GATTサーバーが公開する構造を調べる必要があります。

GATTクライアントは、最初にGATTサーバーが公開するサービスを探索します。目的のサービスが見つかったら、その中にあるキャラクタリスティックを探索します。NotifyやIndicateを使う場合など、キャラクタリスティックに付随する情報が必要なら、さらにディスクリプターを探索します。

接続後は、次の順に操作対象を見つけます。

1. サービスを探索する
2. UUIDで目的のサービスを選ぶ
3. キャラクタリスティックを探索する
4. UUIDで目的のキャラクタリスティックを選ぶ
5. Read、Write、Notifyなどの操作へ進む

この探索も、接続とは別の電波を使うわけではありません。GATTの探索手順がATTのRequestとResponseになり、前節までに作った接続の上を流れます。アプリケーションからは、OSのBLE APIがサービスやキャラクタリスティックを非同期に返す処理として見えます。

探索によって、アプリケーションが知っているUUIDと、接続中にATTが使うハンドルが結び付きます。アプリケーションは、見つかったキャラクタリスティックを表すOSのオブジェクトを保持し、そのオブジェクトを指定してWriteします。Hostは、その操作を対応するハンドルへのATT Write Requestに変換できます。

OSが以前に探索したGATTの構造をキャッシュしている場合は、接続のたびに同じ探索パケットがすべて送られるとは限りません。それでも、アプリケーションから見た「目的のUUIDを持つキャラクタリスティックを見つけてから操作する」という関係は同じです。GATTキャッシュと、ファームウェア更新でGATTの構造が変わる場合の扱いは、[@sec:ch4]で詳しく説明します。

機器は見つかるのに目的のキャラクタリスティックを操作できない場合は、接続より後の段階を調べます。サービス探索が完了しているか、ファームウェアとアプリケーションでUUIDが一致しているか、キャラクタリスティックがWriteを許しているか、必要な暗号化や認証を満たしているかを確認します。

#### GATTで操作する値を選ぶ

サービスは機能のまとまり、キャラクタリスティックは読み書きする値と、その値に許された操作を表します。UUIDは、どのサービスまたはキャラクタリスティックであるかを識別します。

スマートフォンのアプリケーションは、探索で見つけたLED制御用のキャラクタリスティックへ、点灯を表す`0x01`を書き込みます。Core BluetoothなどのAPIでは、アプリケーションはUUIDやキャラクタリスティックのオブジェクトを扱います。

GATTは、製品の機能をどの値として見せ、どの操作を許すかを定めます。しかし、GATT自体が無線パケットを送るわけではありません。実際の読み書きはATTを使います。

#### UUIDで値の意味を共有する

UUID（Universally Unique Identifier）は、サービス、キャラクタリスティック、ディスクリプターなどの種類を識別します。スマートフォンと周辺機器は、「何番目に見つかった値か」ではなく、UUIDを使って目的の機能を見つけます。

UUIDは機器そのものの識別子ではありません。同じ仕様に従う機器は、同じサービスUUIDとキャラクタリスティックUUIDを使います。たとえば複数の心拍センサーが同じHeart Rate ServiceのUUIDを公開できます。UUIDが表すのは、その値がどの仕様に従い、どのような意味を持つかです。

BluetoothのUUIDは128 bitです。Bluetooth SIGが標準化したサービスやキャラクタリスティックには、Bluetooth Base UUIDと組み合わせて使う16 bitまたは32 bitのAssigned Numberがあります。パケットでは短い表現を使えるため、標準機能の識別に必要なデータ量を減らせます。

製品独自のサービスには、128 bitのカスタムUUIDを割り当てます。ファームウェアとアプリケーションが同じUUIDだけを共有しても、値の意味までは決まりません。値の長さ、バイトオーダー、単位、許可する操作なども、カスタムプロファイルの仕様として共有する必要があります。

#### ATTで書き込み要求にする

ATT（Attribute Protocol、アトリビュートプロトコル）は、GATTサーバーが持つアトリビュートを、GATTクライアントから操作するプロトコルです。各アトリビュートには、接続中に使う16 bitのハンドルがあります。

Write Requestには、書き込み先のハンドルと値が入ります。サーバーは要求を処理し、成功した場合はWrite Responseを返します。アプリケーションが扱った「LED制御キャラクタリスティックへの書き込み」は、この段階では「このハンドルへ、このバイト列を書き込む」というATTの要求になります。

ハンドルは、GATTサーバーのアトリビュートテーブル内で値を指すための番号です。UUIDは目的の値を探索して意味を共有するために使い、ATTの個々の操作ではハンドルを使います。ファームウェアの更新でアトリビュートテーブルが変われば、同じ機能のハンドルが変わる可能性があります。このため、アプリケーションの仕様ではUUIDを機能の識別に使い、以前の接続で見つけたハンドルを製品固有の固定番号として扱いません。

UUID、ハンドル、アトリビュートテーブル、GATTキャッシュの関係は[@sec:ch4]で詳しく扱います。

#### L2CAPでATTの論理チャンネルへ載せる

ATT PDUは、L2CAP（Logical Link Control and Adaptation Protocol）のチャンネルを通ります。L2CAPは、一つのLink Layerの接続上で、ATTやSMPなど複数の上位プロトコルを区別します。

基本的なATTは、L2CAPの固定チャンネルを使います。L2CAPは上位から受け取ったデータへチャンネルを識別する情報を付け、下位へ渡します。データが下位層で一つのパケットに収まらない場合には、必要に応じて分割と再構成にも関わります。

この時点でも、LEDという意味はL2CAPには見えません。L2CAPが扱うのは、ATTのデータをどの論理チャンネルへ運ぶかです。

#### HCIを越えてControllerへ渡す

Hostが作ったL2CAPのデータは、HCIを通ってControllerへ渡されます。HCIは、HostとControllerの間でコマンド、イベント、データを交換するためのインターフェースです。

パソコンとUSB Bluetoothアダプターのように、HostとControllerが物理的に分かれていれば、HCIのデータは実際のバスを通ります。1チップの周辺機器では、同じIC内のソフトウェア境界として実装されることもあります。どちらの場合も、Hostが上位プロトコルを扱い、Controllerが無線の時刻に合わせてLink Layerのパケットを送る、という責務は同じです。

Controllerが持つ送信バッファーは有限です。Hostは、初期化時にControllerが受け取れるバッファーの情報を確認し、完了したパケットの通知に応じて次のデータを渡します。したがって、アプリケーションがWriteを呼び出した瞬間に、値が電波へ出るわけではありません。Host内の処理、HCIでの受け渡し、Controllerの送信待ちが間にあります。

#### Link Layerが接続イベントで送る

ControllerのLink Layerは、L2CAPのデータをLink Layer Data PDUへ載せ、接続イベントの中で送信します。セントラルとペリフェラルは交互にパケットを送り、Link Layerのシーケンス情報を使って受信確認と再送を行います。

ここで行われる受信確認は、ATTのWrite Responseとは別です。Link Layerの確認は、無線区間でパケットが相手のControllerへ届いたことを扱います。ATTのWrite Responseは、相手のATTサーバーがWrite Requestを処理して応答したことを扱います。さらに、LEDが実際に点灯したことまでをWrite Responseが必ず表すわけではありません。

#### PHYが電波として送る

PHY（Physical Layer、物理層）は、Link Layerから渡されたビット列を無線信号に変換し、2.4 GHz帯の物理チャンネルで送信します。受信側のPHYは無線信号からビット列を復元し、パケットとしてLink Layerへ渡します。

本章で扱う基本経路ではLE 1M PHYを前提にします。LE 2M PHYやLE Coded PHYを使っても、GATTからATT、L2CAP、HCI、Link Layerへ下る関係がなくなるわけではありません。変わる位置と性能は[@sec:ch3]で扱います。

#### 周辺機器側で逆の順序を上がる

周辺機器側では、受信したデータが逆の順序で上がります。PHYが受信したパケットをLink Layerが処理し、ControllerからHCIを通ってHostへ渡します。L2CAPはATTの固定チャンネルを識別し、ATTはハンドルを使って書き込み先のアトリビュートを見つけます。GATTサーバーの実装は、LED制御キャラクタリスティックへのWriteとして`0x01`をファームウェアへ知らせます。

Writeがスマートフォンのアプリケーションから周辺機器のファームウェアへ届く経路を、[@fig:gatt-write-packet-path]に示します。

ファームウェアのコールバックが値を受け取るまでに、これだけの境界を通ります。SDKは多くの処理を隠しますが、ログやパケットキャプチャで見える名前はこの経路に対応しています。

#### `0x01`を各層で追う

LEDの点灯を表す1 byteの`0x01`は、各層で別の意味へ変換されるわけではありません。値の周りに、その層がデータを運ぶために必要な情報が加わります。各層から見た同じWriteを、[@tbl:write-value-by-layer]に示します。

| 位置 | その位置から見えるもの |
|---|---|
| アプリケーション | LEDを点灯するため、キャラクタリスティックへ`0x01`を書き込む操作 |
| GATT | LED制御キャラクタリスティックに許されたWrite操作 |
| ATT | Write Requestを示すOpcode、書き込み先のハンドル、値`0x01` |
| L2CAP | ATT用の論理チャンネルを示す情報と、ATT PDU |
| HCI | Controllerへ渡す接続データとしてのL2CAPデータ |
| Link Layer | 接続中のData PDUに載せたL2CAPデータまたはその一部 |
| PHY | Link Layerパケットを送るための無線信号 |
| ファームウェア | LED制御キャラクタリスティックへ書き込まれた値`0x01` |

: Writeの値が各層からどのように見えるか {#tbl:write-value-by-layer}

下位へ進むほど、LEDという製品上の意味は見えなくなります。L2CAPはATTを運んでいることを識別しますが、その値がLEDを制御することは知りません。Link Layerは、接続相手へ渡すデータとして扱います。PHYはビット列を無線信号として送受信します。

暗号化された接続では、無線区間を観測してもATTのハンドルや`0x01`をそのまま読めない場合があります。しかし、受信側で復号された後は、同じ基本経路を上がります。暗号化によってGATT、ATT、L2CAPの役割が別のものへ置き換わるわけではありません。

Writeの値が両機器のプロトコルスタックを通る経路を、[@fig:gatt-write-packet-path]に示します。

#### 「届いた」が指す位置を分ける

開発中に「データは届きましたか」と尋ねるだけでは、確認した位置がわかりません。

- アプリケーションがWrite APIへ値を渡した
- HostがHCIを通じてControllerへデータを渡した
- Link Layerで相手のControllerから受信確認を得た
- ATTサーバーからWrite Responseが返った
- ファームウェアのWrite処理が呼ばれた
- LEDの状態が実際に変わった

これらは異なる完了点です。問題を切り分けるときは、どの完了点をログやAPIで確認したのかを明示します。
