## Web Bluetooth APIの主要な制約

第9章のCore Bluetooth（iOS）と比較して、Web Bluetooth APIには以下の重要な制約があります。

### ①ブラウザサポート制限

2025年時点でSafariは非対応、iOS上のChromeもWebKitを使うため非対応です。実質的に **デスクトップChromeとAndroid Chrome** が主要ターゲットです。

```javascript
// 対応確認コードを最初に実行
if (!navigator.bluetooth) {
    document.getElementById('status').textContent =
        'このブラウザはBLE非対応です。Chrome/Edgeでお試しください。';
    return;
}
```

### ②バックグラウンド動作不可

Webページがバックグラウンドタブになったり、ブラウザが最小化されると、**BLE通信は継続されません**。Notifyの受信も停止します。長時間のバックグラウンド監視が必要なアプリには不向きです。

### ③デバイス選択UIのカスタマイズ不可

デバイスリストUIはOSが描画するため、アプリ側でスタイルをカスタマイズできません。企業ブランドのデザインに合わせたUIを求める場合には制約になります。

### ④アドバタイズデータへの直接アクセス制限

`requestDevice()` はデバイス選択ダイアログを経由するため、**スキャン結果のアドバタイズデータ（RSSIや製造者データ）に直接アクセスできません**。位置ビーコンの距離推定など、アドバタイズデータを継続受信する用途には `watchAdvertisements()` API（一部ブラウザで実験的実装）を使います。

### ⑤ペアリング・ボンディング操作の制限

暗号化が必要なキャラクタリスティクス（`CBAttributePermissionsReadEncryptionRequired` 等）へのアクセスは、ブラウザがOSを介してペアリングを要求します。ペアリングプロセスはOSが管理するため、アプリ側での制御はできません。

## 実用ユースケース

### ユースケース1: デバイス設定・ファームアップ用Webツール

組込みエンジニアが自分たちで使うツールは、App Storeの審査を通す必要のないWebアプリとして作るのが合理的です。

```javascript
// 工場出荷時設定ツール（Chromeのみ配布）
async function calibrateSensor() {
    const device = await navigator.bluetooth.requestDevice({
        filters: [{ namePrefix: 'FactorySensor' }]
    });
    const server    = await device.gatt.connect();
    const service   = await server.getPrimaryService(FACTORY_SERVICE_UUID);
    const calibChar = await service.getCharacteristic(CALIBRATION_UUID);

    // オフセット書き込み
    const calibData = new DataView(new ArrayBuffer(4));
    calibData.setFloat32(0, parseFloat(document.getElementById('offset').value), true);
    await calibChar.writeValueWithResponse(calibData.buffer);
    alert('キャリブレーション完了');
}
```

### ユースケース2: リアルタイムセンサーダッシュボード

IoTセンサーの状態確認ダッシュボードをWebアプリとして提供します。社内で使うツールであればURL共有だけで配布でき、ブラウザが必要なアップデート不要です。

### ユースケース3: 展示・デモ用インタラクティブUI

展示ブースで使うBLEデモをWebページとして作成すれば、スタッフがURLにアクセスするだけで操作できます。

## トラブルシューティング

### デバイスがリストに表示されない

```javascript
// 原因1: withServicesフィルタが一致しない
// → nRF52840のアドバタイズにサービスUUIDが含まれているか確認
// → 16-bit UUIDと128-bit UUIDの混在に注意

// 原因2: 以前のペアリングが残っている
// → ブラウザのBluetooth設定でデバイスを削除してリトライ

// デバッグ: acceptAllDevicesで全デバイスを表示
const device = await navigator.bluetooth.requestDevice({
    acceptAllDevices: true,
    optionalServices: [MY_SERVICE_UUID]
});
```

### SecurityError: Must be handling a user gesture

```javascript
// ❌ User Gestureなし
setTimeout(() => {
    navigator.bluetooth.requestDevice(...)  // エラー
}, 100);

// ✅ User Gestureあり
button.addEventListener('click', () => {
    navigator.bluetooth.requestDevice(...)  // OK
});
```

### GATT接続は成功するがサービスが取得できない

```javascript
// 原因: requestDevice時にoptionalServicesに宣言していない
// → requestDevice のオプションに optionalServices を追加
const device = await navigator.bluetooth.requestDevice({
    filters: [{ services: [PRIMARY_SERVICE] }],
    optionalServices: [OPTIONAL_SERVICE]   // ← これがないとGetPrimaryServiceが失敗
});
```

## 第10章のまとめ

本章では、Web Bluetooth APIを使ってブラウザから直接BLEデバイスを操作する方法を解説しました。

**学んだこと**

| 内容 | 詳細 |
|---|---|
| セキュリティモデル | HTTPS必須 + User Gesture必須 + OSダイアログによるデバイス選択 |
| デバイス選択 | `requestDevice()` + `filters.services` でフィルタスキャン |
| GATT探索 | `gatt.connect()` → `getPrimaryService()` → `getCharacteristic()` |
| 読み出し | `readValue()` → `DataView.getInt16()` 等でパース |
| 書き込み | `writeValueWithResponse()` / `writeValueWithoutResponse()` |
| Notify | `startNotifications()` + `characteristicvaluechanged` イベント |
| 制約 | Safari非対応, バックグラウンド不可, iOS未対応 |

## 第11章への橋渡し: Android BLEとLinux BLE

第9章（iOS）と本章（Web）では、BLEセントラルとしてデバイスに接続する実装をSwift/JavaScriptで学びました。

第11章では、**Android** と **Linux** のBLE対応を概観します。エンジニアが直面する実際の開発シナリオで、iOSやWebとの違いを押さえます。

- **Android BLE API** (`BluetoothLeScanner`, `BluetoothGatt`, `BluetoothGattCallback`)
  - Javaコールバック地獄の歴史と現代的なCoroutineアプローチ
  - Android固有の既知の不具合（特定機種でのBonding問題等）
- **BlueZ on Linux** (`bluetoothctl`, `hcitool`, Python `bleak` ライブラリ)
  - Raspberry PiやLinux PCからnRF52840に接続するコマンドライン操作
  - Python `bleak` ライブラリを使ったシンプルなスクリプト

iOS・Web・Android・Linuxと異なるプラットフォームを横断的に学ぶことで、マルチプラットフォームBLE開発の全体像が見えてきます。
