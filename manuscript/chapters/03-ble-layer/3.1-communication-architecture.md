### レイヤーは処理の責任を分ける

スマートフォンがキャラクタリスティックへ`0x01`を書き込むとき、各レイヤーは同じデータを異なる意味で扱います。

| 位置 | 見えているもの | 担う処理 |
|---|---|---|
| GATT | キャラクタリスティックへのWrite | サービスと値を操作する手順 |
| ATT | ハンドルと`0x01`を持つWrite Request | アトリビュートへの要求と応答 |
| L2CAP | CID `0x0004`で運ぶATT PDU | 上位プロトコルの多重化 |
| HCI | Connection Handleに対応するACL Data | HostとControllerの受け渡し |
| Link Layer | 接続イベントで交換するData PDU | 時刻、受信確認、再送、暗号化 |
| PHY | PHYチャンネルへ送るビット列 | 変調、送信、受信、復調 |

: 一つのGATT Writeを各レイヤーから見た違い {#tbl:write-seen-by-layers}

GATTはLEDのような製品機能を知っていますが、PHYは知りません。PHYは周波数とビットの関係を知っていますが、キャラクタリスティックを知りません。この分離によって、GATTの値の設計を変えずにPHYをLE 1MからLE 2Mへ変更できます。反対に、無線回路を変えずに新しいサービスを追加できます。

BLEの仕様は、大きくHostとControllerへ分かれます。ControllerはPHYとLink Layerを担当し、決められた時刻とPHYチャンネルでパケットを送受信します。HostはL2CAP、SMP、ATT、GATTなどを担当し、上位の通信手順を管理します。

両者の境界がHCI（Host Controller Interface）です。HostはコマンドとデータをControllerへ渡し、Controllerはイベントと受信データをHostへ返します。パソコンとUSBアダプターのように別のICへ分かれる場合も、nRF52840のようなBluetooth SoC内に収まる場合もあります。物理的に一つのチップであっても、Hostが任意の時刻に無線パケットを直接送るのではなく、Controllerへ処理を依頼するという責務は変わりません。

この境界は、実務で「どこまで設定できるか」を判断する手掛かりになります。アプリケーションがPHY変更を要求できても、実際の無線手順はControllerが実行します。Controllerの対応機能、Hostスタックが公開する設定、OSのAPIという三つが揃わなければ、コア仕様に存在する機能を製品から利用できません。

### ATTとGATTが分かれている理由

ATT（Attribute Protocol）は、ハンドルで指定したアトリビュートを読み書きするメッセージを定義します。GATT（Generic Attribute Profile）は、そのATTを使ってサービス、キャラクタリスティック、ディスクリプターを表し、探索や操作を進める手順を定義します。

両者は実際の利用では密接です。それでも仕様上は、一方をプロトコル、もう一方をプロファイルとして分けています。初期BLEのAttributeの概念は、コア仕様へ統合されるときに、抽象的な通信メッセージと、そのメッセージを使う汎用的な構造へ分割されました。

この区別が分かると、GATTの「サービスを探索する」という手順と、電波で送られるATT Read By Group Type Requestを同じ名前で呼ばずに済みます。一つのGATT Procedureが複数のATT PDUを使うことも、一つのATT PDUが異なるGATT Procedureから使われることもあります。

### L2CAPは上位プロトコルを同居させる

初期のBLE設計では、L2CAPの代わりに、Attribute Protocolとシグナリングを振り分ける簡単なProtocol Adaptation Layerが検討されていました。しかし、その方式には大きなPDUを分割して再構成する能力がなく、追加のプロトコルを独立させる柔軟性もありませんでした。

L2CAPを採用すれば、ヘッダーと処理による負担は増えます。一方で、ATTとSMPを別の固定チャンネルへ載せ、上位のPDUをLink Layerで運べる長さへ分割できます。既存のBluetooth実装も再利用できます。設計グループは消費電力への影響を含むコストを比較し、最小限のL2CAP機能をBLEへ採用しました。

LEで基本となる固定L2CAPチャンネルには、次のものがあります。

| CID | 運ぶプロトコル |
|---:|---|
| `0x0004` | ATT |
| `0x0005` | LE L2CAP Signaling |
| `0x0006` | SMP |

: LEで使う主な固定L2CAPチャンネル {#tbl:le-fixed-l2cap-channels-ch3}

後からLE Credit Based Connection-Oriented ChannelやEATTが追加されても、L2CAPがプロトコルを振り分けるという基本は同じです。初期設計で残した多重化と分割の境界が、将来の通信方法を追加する場所になりました。

### SMPと暗号化は同じ位置にない

SMPは、ペアリングで使う能力、確認値、公開鍵、鍵情報などを交換するHost側のプロトコルです。ATTとは異なる固定CID `0x0006`を使うため、保護されたキャラクタリスティックへのアクセスが契機になっても、ペアリングメッセージがATT PDUへ入るわけではありません。

SMPによって鍵が準備されると、HostはHCIを通じてControllerへ暗号化の開始を要求します。実際のLink Layerパケットの暗号化、MICの付加と検証、Packet Counterの管理はController側で行われます。

この境界を知ると、次の状態を分けられます。

- ATTがInsufficient EncryptionなどのError Responseを返した
- SMPでペアリング手続きが始まった
- HostがControllerへ暗号化開始を要求した
- Link Layerの暗号化手順が完了した
- 暗号化された接続でATT操作をやり直した

画面には一つのペアリング操作として見えても、ATT、SMP、HCI、Link Layerをまたぐ手順です。鍵生成の計算方式は第2章で整理したとおりですが、仕様を読むときは「鍵を準備するHost側の手順」と「鍵を使ってパケットを保護するController側の処理」を分けます。

### レイヤーとは別に通信路の性質を表す

Bluetooth Core Specificationには、レイヤーとは別に、データを運ぶ場と性質を表す用語があります。

| 用語 | 表しているもの |
|---|---|
| PHY channel | 2.4 GHz帯にある個々のRFチャンネル |
| physical channel | 使用するPHYチャンネル、時刻、Access Addressなどで作る通信の場 |
| physical link | physical channel上に成立する機器間の関係 |
| logical transport | 一対一かブロードキャストか、確認応答や時間制約をどう扱うか |
| logical link | logical transport上で運ぶ情報の種類 |
| L2CAP channel | 上位プロトコルやアプリケーションの振り分け先 |

: 通信路の性質を表す仕様上の用語 {#tbl:data-transport-terms}

接続中の基本的なGATT通信を、この地図へ載せてみます。

| 見る対象 | GATT通信で使うもの |
|---|---|
| 上位プロトコルの振り分け | ATTのL2CAP固定チャンネル |
| 運ぶ情報の種類 | LE-U logical link |
| データを運ぶ性質 | LE ACL logical transport |
| 二台の関係 | LE active physical link |
| パケットを交換する場 | LE piconet physical channel |
| 実際に使う周波数 | 接続イベントごとに選ばれるPHY channel |

: 接続中のGATT通信を通信路の地図へ対応させる {#tbl:gatt-transport-map}

LE ACLの中でも、情報の種類は一つではありません。ATTやSMPなどL2CAPを通るデータはLE-U logical link、PHY変更や接続パラメーター更新などのLink Layer制御情報はLE-C logical linkとして運ばれます。どちらも同じ接続イベントを使いますが、Link LayerヘッダーのLLIDによって区別されます。

Legacy Advertisingは別の経路です。通常のAdvertising Dataは、ATT、SMP、L2CAP、LE ACLを通りません。Advertising用のlogical linkとlogical transportを使い、Primary Advertising Physical Channelで送られます。

この違いは、パケットキャプチャーにも現れます。GATT Writeを追うには接続開始時の情報からLE ACLを追跡し、L2CAPとATTを解析します。Advertising Dataを読むだけなら、接続を追跡する必要はありません。抽象的な用語は、実際にどのパケットを捕まえるべきかを決める地図でもあります。

### 接続要求が通信路の実体を作る {#sec:conn-establish}

接続前には、CentralとPeripheralの間にLE active physical linkもLE ACL logical transportもありません。Centralが送る接続要求には、接続後の通信路を作るための情報が入ります。

| 情報 | 接続後に決まるもの |
|---|---|
| Access Address | 接続のData Physical Channel PDUを識別する値 |
| CRCInit | Data Physical Channel PDUのCRC初期値 |
| Transmit Window | 最初の接続イベントを始める時間範囲 |
| Connection Interval | 接続イベントを繰り返す間隔 |
| Peripheral Latency | Peripheralが応答を省略できる接続イベント数 |
| Supervision Timeout | 有効なパケットを受信できない状態を切断とする時間 |
| Channel Map | 使用できるデータ用PHYチャンネル |
| Hop、SCAなど | チャンネル選択や受信窓の計算に使う情報 |

: 接続要求が新しい通信路へ渡す情報 {#tbl:connection-request-transport-fields}

第2章では、このパケットを二台が繰り返し会うための予定表として読みました。仕様の地図では、Advertising Physical Channel上の接続要求を境に、接続固有のAccess Addressと時刻を持つLE piconet physical channel、その上のLE active physical link、LE ACL logical transportが作られます。

接続要求のPDU名とフィールドは、使用するAdvertising方式とコア仕様の世代によって異なります。Legacy Advertisingでは`CONNECT_IND`、Extended Advertisingでは`AUX_CONNECT_REQ`などが使われます。また、接続後のChannel Selection Algorithmは常にhopIncrementだけで決まるわけではありません。機能対応と接続要求の情報に応じて、Channel Selection Algorithm #1または#2を使います。

このため、接続開始を解析するときは「`CONNECT_IND`を探す」だけで終わらず、どのAdvertising Physical ChannelとPDU形式で接続が始まったかを確認します。開始パケットを捕まえれば、その後のAccess Address、接続イベントの時刻、PHYチャンネルを予測でき、接続中のパケットを追跡できます。
