## まとめと第4章への橋渡し {#sec:ch3-summary}

<!-- topic: この章で学んだことをスタックに沿って再確認 -->

この章ではBLEプロトコルスタックのコントローラ側——物理層・リンク層——と、振る舞いのプロファイルであるGAPを解説しました。[@sec:ch2]で「使い方」として学んだ各フェーズが、スタックのどの層で実現されているかが見えてきたはずです。

| 節 | 扱った内容 | スタックの対応 |
|---|---|---|
| 3.1 | コントローラとホストの分離、各層の役割 | スタック全体 |
| 3.2 | 物理チャネル、物理リンク、論理トランスポート、論理リンク、L2CAPチャンネル | スタック全体 |
| 3.3 | 2.4GHz ISMバンド、GFSK変調、40チャンネル設計、パケットフォーマット | 物理層（PHY） |
| 3.4 | 5状態の状態機械、各役割（Advertiser/Scanner/Initiator/Master/Slave） | リンク層（LL） |
| 3.5 | 4種のADV PDUタイプ、ADV\_IND構造、デバイスアドレス、AD Structure | リンク層（LL） |
| 3.6 | CONNECT\_INDのシーケンスとPDUフィールド、AFH・周波数ホッピング計算式 | リンク層（LL） |
| 3.7 | GAPの4ロール、発見モード、プライバシーとRPA、用語対応表 | GAP（層横断） |


## 重要用語一覧

<!-- topic: 本章の重要用語まとめ -->

| 用語 | 説明 |
|---|---|
| **物理層（PHY）** | 0/1ビットをGFSK変調で電波にのせる層 |
| **ISMバンド** | 産業・科学・医療向けに開放された周波数帯。2.4GHz帯が代表例 |
| **GFSK** | ガウシアン周波数シフトキーイング。BLEの変調方式（1 Mbps） |
| **アドバタイジングチャンネル** | 発見・接続用の3チャンネル（37 / 38 / 39）。Wi-Fi主要chを避けて配置 |
| **データチャンネル** | 接続後の通信用37チャンネル（0〜36）。AFHで使用 |
| **プリアンブル** | パケット先頭の8ビット。受信回路のAGCとビット同期に使う |
| **アクセスアドレス** | パケットの宛先識別子。アドバタイジングは固定値 0x8E89BED6、データ通信は接続ごとのランダム値 |
| **PDU** | プロトコルデータユニット。パケットが運ぶ実データ部分（2〜39 oct） |
| **ホワイトニング** | PDUの0/1連続を防ぐビット変換処理（送受信回路内で透過的に処理） |
| **リンク層（LL）** | パケット管理・接続確立・タイミング制御を担う層 |
| **5状態** | Standby / Advertising / Scanning / Initiating / Connection |
| **アドバタイザ** | アドバタイジング状態のデバイス |
| **イニシエータ** | Initiating状態のデバイス。CONNECT\_INDを送る直前 |
| **マスター** | 接続後の元イニシエータ。通信タイミングを制御 |
| **スレーブ** | 接続後の元アドバタイザ。マスターのパケットに応答 |
| **ADV\_IND** | 通常のアドバタイジングPDU（接続可・スキャン可・無向） |
| **ADV\_NONCONN\_IND** | 接続不可・スキャン不可。ビーコン用 |
| **AD Structure** | Adv Data内の1単位。Length + AD Type + AD Data の形式 |
| **パブリックアドレス** | Bluetooth SIG発行のOUI＋企業割り当てIDで構成。製造時固定 |
| **ランダムアドレス** | IRK＋乱数から生成するハッシュベースのアドレス。プライバシー保護のため定期更新 |
| **IRK** | Identity Resolving Key（128ビット）。ランダムアドレスの解決に使う鍵 |
| **CONNECT\_IND** | 接続要求パケット。接続パラメータとAFHパラメータが含まれる |
| **hopIncrement** | 周波数ホッピングの刻み幅（5〜16）。B = (A + Hop) mod 37 で計算 |
| **ChM** | チャンネルマッピング（37ビットのビットマップ）。使用チャンネルを指定 |
| **AFH** | 適応周波数ホッピング。コネクションイベントごとにチャンネルを切り替え干渉を回避 |
| **GAP** | Generic Access Profile。デバイスの発見・接続・振る舞いを定義するプロファイル |
| **Peripheral** | GAPのロール。ADV\_INDでアドバタイジングし接続を受け入れる |
| **Central** | GAPのロール。スキャンして接続を開始する |
| **Broadcaster** | GAPのロール。ADV\_NONCONN\_INDのみ送信する接続不可デバイス |
| **Observer** | GAPのロール。パッシブスキャンのみ行う接続なしデバイス |
| **General Discoverable Mode** | 常時発見可能なアドバタイジングモード |
| **Limited Discoverable Mode** | 一定時間だけ発見可能にするアドバタイジングモード |
| **SCA** | Sleep Clock Accuracy。スリープクロック精度。コネクションイベントのタイミングずれ補正に使う |


## 第4章へ

<!-- topic: 第4章ATT・GATTの予告 -->

この章では、電波から接続確立に至るまでの物理的・プロトコル的な仕組みを見てきました。マスターとスレーブが接続を確立した後——つまりCONNECT\_INDが受け入れられ、最初のコネクションイベントが始まった後——は、その通信路の上でデータをやり取りする段階に入ります。

[@sec:ch4]ではその「データのやり取り」を担う**ATT（Attribute Protocol）**と**GATT（Generic Attribute Profile）**を解説します。

- ハンドル番号でアクセスするATTコマンドの種類と動作
- サービス・キャラクタリスティック・ディスクリプタの階層構造をATTテーブルとして実装する方法  
- Read / Write / Notify / Indicateが実際にどのATTコマンドとして送受信されるか
- 標準プロファイル（Heart Rate、Battery、Device Information）の実装例

[@sec:ch2]で「何ができるか」を、この章で「どう動いているか」を理解した後、[@sec:ch4]でいよいよ「データをどう表現して通信するか」に入ります。
