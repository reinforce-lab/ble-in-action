## BLE拡張機能と通信アーキテクチャ {#sec:ch3-summary}

GATTの値は、ATT、L2CAP、HCI、Link Layer、PHYを通って相手へ届きます。この処理の順序に加えて、それぞれの通信路が持つ伝送特性を知ると、Bluetooth LEの拡張機能を同じ仕組みの中で理解できます。

レイヤーは、誰が処理を担当するかを示します。physical link、logical transport、logical linkなどの区分は、データをどの機器間で、どの時間特性と信頼性によって運ぶかを示します。新しい機能が加わったときは、どの処理または通信路が変わるかを確認します。

| 製品で起きる変化 | 仕様上、主に変わる位置 |
|---|---|
| 一つの無線パケットで多く運ぶ | Link Layer Data Length |
| 同じデータを短時間で送る | PHY |
| 上位の大きなPDUを運ぶ | L2CAPの分割と再構成 |
| 接続せず長いデータを送る | Extended Advertising Physical Channel |
| 接続せず送信時刻を共有する | Periodic Advertising |
| 多数機器から応答を集める | PAwRのSubeventとResponse Slot |
| 電波から距離を測る | Channel Soundingの無線手順 |
| 時刻に間に合うデータを運ぶ | Isochronous logical transportとISOAL |

: BLE拡張機能が変更する主な位置 {#tbl:ble-extension-map}

ここから分かるのは、現在のBluetooth LEが、GATTだけで完結する技術ではないことです。GATTは今も、周辺機器の機能と状態を公開する中心的な仕組みです。しかし、Advertisingによる非接続通信、Channel Soundingによる測距、Isochronous Channelsによる時間制約付きデータは、それぞれ別の通信路や無線手順を使います。

この広がりは、初期BLEの考え方を否定したものではありません。HostとController、レイヤー、多重化、physical channel、logical transportという境界があったから、既存のGATT通信を残しながら新しい経路を追加できました。初期設計でL2CAPを採用し、ATTとGATTを仕様上分けた判断も、実装の交換と機能追加ができる現在の構造につながっています。

製品で重要なのは、最新の機能をすべて使うことではありません。要求を満たせない制約がどこにあるかを見つけ、その位置を変える機能を選ぶことです。速度が足りないなら、ATT MTUだけでなくData Length、PHY、接続イベント、バッファーを調べます。距離が足りないなら、送信電力だけでなくPHY、アンテナ、Channel Map、再送を調べます。仕様に機能があっても、双方のController、Host、OS APIが対応するかを確認します。

[@sec:ch4]では、この通信路の上で広く使われるATTとGATTを詳しく扱います。サービス、キャラクタリスティック、ディスクリプターが、Attribute HandleとATT PDUへどのように対応するかを追い、製品の機能とデータを設計する方法へ進みます。
