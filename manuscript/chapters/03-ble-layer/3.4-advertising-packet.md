## 3.4 アドバタイジングパケットの解剖

<!-- topic: 導入——アドバタイジングパケットの種類 -->

アドバタイジングパケットは「存在を知らせる」パケットです。しかし一口にアドバタイジングと言っても、「接続を受け付けるか」「スキャン要求に応じるか」「特定の相手向けか」によって使うPDUタイプが異なります。また、パケットに乗せるデバイスアドレスには2種類あり、プライバシー保護の観点から使い分けられています。

この節では、アドバタイジングパケットの内部構造を分解します。第2章で「アドバタイジング」として扱ったフェーズが、パケットレベルではどのような形をしているかを理解することで、パケットキャプチャを読んだり問題を調査したりするときの足がかりになります。

---

## 4種類のADV PDUタイプ

<!-- topic: PDUタイプと使い分け -->

アドバタイジングに使うPDUタイプは4種類あります。それぞれ「接続を受け付けるか」「スキャン要求に応じるか」「特定デバイス向けか」の組み合わせで役割が決まります。

| PDUタイプ | 接続 | スキャン要求 | 向き | 典型的な用途 |
|---|---|---|---|---|
| `ADV_IND` | ○ | ○ | 無向（不特定多数） | 通常のアドバタイジング |
| `ADV_DIRECT_IND` | ○ | × | 有向（特定デバイス） | 既知デバイスへの高速再接続 |
| `ADV_NONCONN_IND` | × | × | 無向 | ビーコン・一方向ブロードキャスト |
| `ADV_SCAN_IND` | × | ○ | 無向 | 接続なしで情報を広く発信 |

**ADV\_IND**が一般的なアドバタイジングです。不特定多数のスキャナに自分の存在を知らせ、SCAN\_REQにもCONNECT\_INDにも応答します。センサーやウェアラブルがペリフェラルとして動作するときはこのタイプを使います。

**ADV\_DIRECT\_IND**は以前に接続したことのある特定デバイスへの高速再接続に使います。ペイロードに接続先のアドレスが含まれており、そのデバイス以外は接続できません。ボンディング済みのデバイスとの再接続時に有効です。

**ADV\_NONCONN\_IND**はビーコン用です。接続も追加スキャンも受け付けず、アドバタイジングデータを一方的にブロードキャストし続けます。iBeaconや位置推定用ビーコンはこのタイプを使います。

**ADV\_SCAN\_IND**は接続は受け付けないが、SCAN\_REQには応答するタイプです。接続なしにより多くのデータを公開したいときに使います。

## ADV\_IND PDUのフォーマット

<!-- topic: ADV_IND PDUの内部構造 -->

最もよく使われる `ADV_IND` のPDUフォーマットを詳しく見ます。

```
┌──────────────────────────────────────────────────────────────────────┐
│  PDU Header（2 オクテット）                                           │
│  ┌────────────┬───────┬───────┬─────────────────────────────────┐   │
│  │  PDU Type  │ TxAdd │ RxAdd │           Length                │   │
│  │   4 ビット  │ 1 bit │ 1 bit │          6 ビット               │   │
│  └────────────┴───────┴───────┴─────────────────────────────────┘   │
├──────────────────────────────────────────────────────────────────────┤
│  Payload                                                             │
│  ┌─────────────────────────────────┬──────────────────────────────┐ │
│  │  AdvA（デバイスアドレス）         │  Adv Data（広告データ）       │ │
│  │         6 オクテット              │      0〜31 オクテット         │ │
│  └─────────────────────────────────┴──────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

ヘッダの**TxAdd**ビットは `AdvA` のアドレス種別を示します。0ならパブリックアドレス、1ならランダムアドレスです。**Length**フィールドはペイロードのオクテット数です。

`AdvA` はアドバタイザのデバイスアドレスです（次節で詳述）。

`Adv Data` は実際に伝えたい情報で、0〜31オクテットです。内部はAD Structureと呼ばれる形式の配列になっています（3節後で詳述）。

## デバイスアドレスの2種類——プライバシーをどう守るか

<!-- topic: パブリックアドレスとランダムアドレス -->

`ADV_IND` の `AdvA` に入るデバイスアドレスには**パブリックアドレス（Public Device Address）**と**ランダムアドレス（Random Device Address）**の2種類があります。

### パブリックアドレス

パブリックアドレスは**48ビット**の固定値で、製造時にデバイスに書き込まれます。構成は次のとおりです。

```
┌──────────────────────────────────────────────────────────────────┐
│  上位24ビット（OUI）          │  下位24ビット（製品固有ID）         │
│  Bluetooth SIGが企業に発行    │  企業が製品1台ごとに割り当て        │
└──────────────────────────────────────────────────────────────────┘
```

EthernetのMACアドレスと同じ仕組みで、一見わかりやすいですが、このアドレスは**絶対に変わりません**。個人のデバイスがパブリックアドレスでアドバタイジングし続けると、アドレスから特定の人物の行動を追跡することが可能になります。

### ランダムアドレス

ランダムアドレスはプライバシー保護のために導入されました。ランダムアドレスには3つのサブタイプがあります。

| サブタイプ | 上位2ビット | 特徴 |
|---|---|---|
| Static Random Address | `11` | 電源投入ごとに固定。製造時にパブリックアドレスを持たないデバイスの代替 |
| Non-Resolvable Private Address | `00` | 毎回ランダム生成。ボンディング相手にも識別不可 |
| Resolvable Private Address（RPA） | `01` | IRKで解決可能。ボンディング相手だけが同一性を確認できる |

最も重要なのは**Resolvable Private Address（RPA）**です。アドレスは**IRK（Identity Resolving Key、128ビット）**と乱数から計算したハッシュ値で構成され、一定時間（通常15分）ごとに変更されます。

```
┌──────────────────────────────────────────────────────────────────┐
│  ハッシュ（24ビット）                │  ランダム値（24ビット）       │
│  hash(IRK, prand) の下位24ビット   │  上位2ビットは 01（RPA識別）  │
└──────────────────────────────────────────────────────────────────┘
```

アドレスが変わるため、第三者がパケットを傍受しても同じデバイスとして識別できません。一方で、IRKを共有済みのボンディング相手（スマートフォンなど）は、受信したアドレスのハッシュ部分をIRKを使って検証することで、アドレスが変わっても同じデバイスだと認識できます。

Static Random Addressは、パブリックアドレスの代替として、Bluetooth SIG のOUI登録をしない小規模な製品で採用されることがあります。ただし電源投入中はアドレスが固定なので、プライバシー保護の効果はありません。

## Adv Dataのフォーマット——AD Structureの配列

<!-- topic: AD Structureの詳細フォーマット -->

`Adv Data` の内部は**AD Structure**という単位の配列です。各AD Structureは次の形式です。

```
┌───────────────┬──────────────┬─────────────────────────────────────┐
│  Length       │  AD Type     │  AD Data                            │
│  1 オクテット  │  1 オクテット │  ( Length - 1 ) オクテット           │
└───────────────┴──────────────┴─────────────────────────────────────┘
```

`Length` は `AD Type` と `AD Data` を合わせたオクテット数です。`AD Type` がデータの種別を示し、`AD Data` が実際の値です。複数のAD Structureを並べて `Adv Data` を構成します。合計で31オクテットまでという制限があります。

知っておくべき主要なAD typeは5種類です。

### Flags（AD Type: 0x01）

デバイスの発見・接続可否を示すビットフラグです。アドバタイジングパケットに1つだけ含めます。

| ビット | 意味 |
|---|---|
| 0 | LE Limited Discoverable Mode（時間制限付き発見可能） |
| 1 | LE General Discoverable Mode（常時発見可能） |
| 2 | BR/EDR Not Supported（Classicに未対応、BLEのみ） |
| 3〜4 | Simultaneous LE and BR/EDR（両モード同時対応） |

BLEのみをサポートするデバイスは、ビット1が1（General Discoverable）、ビット2が1（BR/EDR Not Supported）になります。

### Local Name（AD Type: 0x08 / 0x09）

ユーザインタフェースに表示するデバイス名です。UTF-8エンコードで格納します。

- `0x08`（Shortened Local Name）：31オクテット制限に収まらない場合に先頭部分だけ格納
- `0x09`（Complete Local Name）：完全な名前

Shortened Local Nameを使った場合、完全な名前はGATTのDevice Name Characteristicから取得できます。

### Service UUIDs（AD Type: 0x02〜0x07）

デバイスが提供するサービスのUUID一覧です。スキャナがこれを見て「目的のサービスを持つデバイスか」を判断します。

| AD Type | 内容 |
|---|---|
| 0x02 | 16ビットUUID一覧（不完全） |
| 0x03 | 16ビットUUID一覧（完全） |
| 0x06 | 128ビットUUID一覧（不完全） |
| 0x07 | 128ビットUUID一覧（完全） |

カスタムサービスの128ビットUUIDを使う場合は0x06/0x07を使いますが、16バイト × サービス数だけスペースを消費するため、31オクテットの制限がすぐ尽きます。

### Manufacturer Specific Data（AD Type: 0xFF）

企業が独自に使えるデータフィールドです。先頭2オクテットにBluetooth SIGが発行した企業識別子（Company ID）が入り、以降に任意のバイナリデータを格納できます。

Apple社のiBeaconはこのフィールドを使っています。Company IDにAppleの識別子（0x004C）を指定し、続くデータにiBeaconの固有フォーマット（UUID・Major・Minor・TX Power）を格納します。

### TX Power Level（AD Type: 0x0A）

アドバタイザの送信電力（dBm単位、符号付き1バイト）を示します。スキャナが受信したRSSI（受信信号強度）とこの値の差分から伝搬損失を計算し、距離の粗い推定に使えます。

$$\text{伝搬損失（dB）} = \text{TX Power Level} - \text{RSSI}$$

ただし電波の反射や遮蔽物の影響で距離との相関は単純ではなく、「近い/遠い」のしきい値に使う程度の精度です。

<!-- topic: コラム——Wiresharkでパケットを読む -->

> **コラム：アドバタイジングパケットをWiresharkで読む**
>
> ここまで学んだAD Structureの構造は、パケットキャプチャツールで実際に確認できます。
>
> **必要なもの**：
> - Nordic Semiconductor製の対応ドングル（nRF52840 Dongleなど）
> - [nRF Sniffer for Bluetooth LE](https://www.nordicsemi.com/Products/Development-tools/nRF-Sniffer-for-Bluetooth-LE)プラグイン
> - Wireshark 3.x以降
>
> **手順**：ドングルをUSBに刺し、nRF Snifferのファームウェアを書き込みます。Wiresharkにプラグインを追加して起動すると、近くのBLEデバイスが送るアドバタイジングパケットが流れてきます。パケットを1つ選択すると、ツリー表示でAD Structureが分解されて表示されます——Local Name、Service UUIDs、Manufacturer Specific Dataがそれぞれの値として見えます。
>
> 自分で書いたファームウェアのアドバタイジングデータを実際に確認したいとき、「なぜスマートフォンに名前が表示されないのか」を調べたいとき、Wiresharkのパケット表示は最も直接的な手がかりになります。パケットキャプチャによるデバッグの詳細は第15章で改めて取り上げます。
