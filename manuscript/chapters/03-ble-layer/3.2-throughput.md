## 大きなデータはどこで待つのか {#sec:throughput}

1バイトの設定値なら、通信経路の途中で待つ時間は目立ちません。ところが、数十KBのファームウェアをOTAで送ると、同じ経路にある制約が順番に見えてきます。

アプリケーションが32 KBのファイルを一度に渡しても、32 KBの無線パケットが送られるわけではありません。ファイルは製品の転送単位へ分けられ、ATT PDU、L2CAP PDU、HCI ACL Data、Link Layer Data PDUへ形を変えます。それぞれに長さの上限と、次のデータを受け取れる条件があります。

### ATT MTUは一つのATT PDUの上限を決める

ATT MTUは、一つのATT PDUで扱える最大長です。接続後、ATTクライアントとATTサーバーはExchange MTU Procedureによって、互いが受信できるMTUを知らせます。実際に使うATT MTUは、両者が示した値の小さい方です。

たとえばWrite Commandには、OpcodeとAttribute Handleが必要です。ATT MTUのすべてをアプリケーションの値へ使えるわけではありません。ATT MTUが23オクテットなら、Write Commandで一度に運べるAttribute Valueは20オクテットです。MTUを大きくすれば一回のATT操作で運べる値は増えますが、それだけで無線パケットが大きくなるとは限りません。

### L2CAPとLink Layerでは長さの意味が違う

ATT PDUはL2CAP SDUとしてL2CAPチャンネルへ渡されます。L2CAPはCIDなどを含むヘッダーを付け、下位へ渡します。L2CAP PDUが一つのLink Layer Data PDUに収まらなければ、Link Layerの複数のパケットへ分割して運ばれます。

LE Data Packet Length Extensionは、Link Layer Data PDUのPayloadで一度に運べるデータ長と、その送信時間を拡張する機能です。これはATT MTUとは別の設定です。

- ATT MTUが大きく、Data Lengthが小さい場合  
  一つのATT PDUを複数のLink Layer Data PDUへ分けて運びます。

- ATT MTUが小さく、Data Lengthが大きい場合  
  無線パケットに余裕があっても、一つのATT PDUが運ぶAttribute Valueは増えません。

- 両方が大きい場合  
  ヘッダーの割合と分割回数を減らせます。ただし、接続イベントやバッファーが次の制約になります。

同じ「パケットサイズ」という言葉で、ATT MTUとLink LayerのData Lengthを混ぜないことが重要です。ログに`MTU 247`と表示されても、Link Layer Payloadが同じ長さで送られているとは限りません。

### LE 2M PHYは空中にいる時間を短くする

LE 2M PHYは、LE 1M PHYより高いシンボルレートを使い、同じ情報を短い時間で送れます。無線で一つのパケットを占有する時間が短くなるため、一つの接続イベントへより多くの交換を収められる可能性があります。

しかし、「2M」という名前だけからアプリケーションの転送速度を2倍と判断できません。次の待ち時間は残ります。

- 接続イベントが始まるまでの待ち時間
- パケット間の間隔
- 相手の応答とLink Layerの受信確認
- Controllerの送受信バッファー
- Hostが次のデータを用意する時間
- フラッシュメモリーへ書き込む時間
- 製品プロトコルの応答や再送

転送速度を調べるときは、PHYのビットレートではなく、一定時間にアプリケーションの有効データが何バイト届いたかを測ります。

### 一つの接続イベントで交換できる数は固定ではない

接続イベントでは、CentralとPeripheralが交互にパケットを送ります。仕様上、必要な条件を満たす間は同じ接続イベントで交換を続けられます。一回のイベントで必ず一往復、あるいは必ず六パケットという共通の固定値はありません。

実際の個数は、Controllerのスケジューリング、接続イベントへ割り当てる時間、PHY、パケット長、ほかの接続やWi-Fiとの共存、送信データを準備できる速さによって変わります。SDKがイベント長や送信キューの設定を公開していても、それはコア仕様で保証されたパケット数とは分けて扱います。

Connection Intervalを短くすれば送信機会は早く来ます。イベント内で多くのパケットを交換できるなら、Intervalが同じでも転送量を増やせます。どちらが支配的かは、パケットキャプチャーとControllerの完了通知を見なければ分かりません。

### HCIのバッファーがHostを止める

Controllerが保持できる送信データは有限です。Hostが無制限にHCI ACL Dataを渡すと、Controllerのメモリーを使い切ります。そのため、HostはControllerが示すバッファー数とデータ長を確認し、完了したパケット数の通知に応じて次のデータを渡します。

このフロー制御は、無線区間のLink Layer受信確認とは別です。

| 仕組み | 確認していること |
|---|---|
| HCIのフロー制御 | HostからControllerへ次のデータを渡せるか |
| Link Layerの受信確認 | 相手のControllerが無線パケットを受信したか |
| ATT Response／Confirmation | 相手のATTが要求やIndicationへ応答したか |
| 製品プロトコルのACK | ファームウェアがデータを検証、保存、適用したか |

: 大量転送に現れる異なる確認の段階 {#tbl:bulk-transfer-ack-layers}

Link Layerで受信確認されたことは、相手のフラッシュメモリーへ書き込まれたことを意味しません。OTAでは、チャンク番号、長さ、ハッシュ、書き込み結果などを使い、再接続後にどこから再開するかをアプリケーションプロトコルとして設計します。

### L2CAP CoCではクレジットを明示する

GATTを使わず、LE Credit Based Connection-Oriented Channelでデータを運ぶ方法もあります。送信側は、受信側から与えられたcreditの範囲でCredit-based Frame（K-frame）を送ります。受信側のバッファーが空けば、新しいcreditを与えます。

この仕組みは、大きなストリームを運ぶ経路をアプリケーションへ提供できますが、ファイル形式、整合性確認、処理完了の意味までは定めません。また、スマートフォンOSが公開するAPIやバックグラウンド動作を確認する必要があります。GATTのWriteをL2CAP CoCへ置き換えるだけでOTAが完成するわけではありません。

大量転送では、「どの層で何個まで先へ渡せるか」を一つずつ確認します。ATT MTU、Data Length、接続イベント、HCIバッファー、L2CAP credit、製品のチャンクは、それぞれ異なる流量調整です。速度が伸びない原因は、最も遅い境界にあります。
