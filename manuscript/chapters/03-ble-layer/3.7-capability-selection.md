## 仕様にある機能を製品で使えるか判断する {#sec:capability-selection}

<!--

- Controller、Host、OS API、相手機器、製品要件を一つの確認経路へまとめる。
- 拡張機能を採用しない判断も含め、実務で使える選択基準を渡す。

Bluetooth Core Specification v6.3に載っている機能が、Bluetooth 6.3対応を名乗るすべての機器で使えるとは限りません。Bluetoothの機能には必須とオプションがあり、ControllerとHostで対応範囲が分かれ、さらにOSがアプリケーションへ公開しない場合があります。

「Bluetoothのバージョンはいくつか」という質問だけでは、製品で利用できる機能を決められません。

### 機能が通る四つの境界を確認する

拡張機能を採用するときは、少なくとも次の四つを確認します。

1. 自機のControllerが無線手順に対応しているか
2. 自機のHostスタックが設定と状態管理に対応しているか
3. 相手機器のControllerとHostが対応しているか
4. OSやSDKが製品から使えるAPIを公開しているか

たとえばControllerがLE 2M PHYに対応していても、HostスタックにPHY変更を要求する方法がなければ、アプリケーションから利用できません。スマートフォンのControllerが対応していても、OSがバックグラウンド中の利用を制限する場合があります。

接続後にFeature Exchangeで確認できるLink Layer機能もあります。しかし、Featureのビットが立っていることは、製品の用途に必要な性能やOSの振る舞いを保証しません。機能の存在確認と、利用条件の確認を分けます。

### フォールバックを基本経路へ戻す

拡張機能は、対応しない相手との通信を考えて設計します。

- LE 2Mを使えなければLE 1Mで通信する
- Extended Advertisingを受信できない相手向けにLegacy Advertisingで発見情報を出す
- 大きなATT MTUを使えなければ小さいチャンクへ分ける
- Channel Soundingを使えなければ、重要操作を許可しない、または別の確認方法を使う

フォールバックは、エラー処理として最後に付け足すものではありません。どこまで機能を落としても製品の目的を満たすかを決める設計です。セキュリティ機能については、互換性のために保護を弱めると製品要件を満たさなくなる場合があります。

### 性能向上には交換条件がある

| 要求 | 候補となる機能 | 主な交換条件 |
|---|---|---|
| 大量データを速く送る | Data Length、LE 2M、短いConnection Interval | 消費電力、バッファー、相互運用性 |
| 遠くへ届ける | LE Coded、送信電力、アンテナ改善 | 空中時間、転送速度、ハードウェア |
| 接続せず長い情報を送る | Extended Advertising | 対応機器、発見方法 |
| 多数機器へ時刻を合わせて送る | Periodic Advertising、PAwR | 同期管理、プロファイル設計 |
| 距離を測る | Channel Sounding | 対応無線回路、校正、セキュリティ設計 |
| 音声を時間どおり運ぶ | Isochronous Channels | Controller、Host、コーデック、プロファイル |

: 製品要求と拡張機能の交換条件 {#tbl:feature-selection-tradeoffs}

一つの機能を有効にすると、ほかの設定も変わります。LE Codedでパケットが長くなれば、接続イベントの使い方や消費電力へ影響します。Data Lengthを大きくすれば、ControllerとHostに必要なバッファーが増えます。多数の機能へ同時対応すれば、テストする組み合わせも増えます。

### 仕様、実装、製品判断をログで分ける

問題を調べるときは、次の情報を別々に残します。

- 仕様上、どの機能と手順を使おうとしたか
- 自機と相手が交換したFeature
- 実際に選ばれたPHY、Data Length、Connection Parameter
- HostがControllerへ送ったHCI Commandと返ったStatus
- OSまたはSDKのAPIが返した結果
- パケットキャプチャーで観測したPDU
- アプリケーションが測った転送速度、遅延、損失

「2Mに設定した」というログだけでは、要求を送ったのか、相手が受け入れたのか、実際のPHYが変わったのかが分かりません。第2章で現象を通信の段階へ戻したように、拡張機能でも最後に確認できた境界を明らかにします。

### 基本経路を選ぶことも設計である

新しい機能を使わず、LE 1M、Legacy Advertising、通常のACL接続、GATTで製品を作る選択もあります。対応機器が広く、開発と検証の範囲を抑えられ、必要なデータ量と距離を満たすなら、基本経路は有力です。

拡張機能は、バージョン番号を新しく見せるために使うものではありません。基本経路のどの制約が製品要件を妨げているかを確認し、その制約を解く機能だけを選びます。
