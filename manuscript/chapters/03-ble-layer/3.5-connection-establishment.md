## 接続確立の仕組み——CONNECT\_INDから周波数ホッピングまで

<!-- topic: 導入——接続確立のシーケンスを追う -->

第2章では「セントラルがペリフェラルに接続する」という動作を概念として学びました。この節ではその動作をパケットレベルまで掘り下げます。接続確立の瞬間に何が起きているか、CONNECT\_INDパケットに何が入っているか、そして接続後の通信がどの周波数チャンネルを使うかを見ていきます。


## 接続確立のシーケンス

<!-- topic: 接続確立のステップとタイミング -->

接続が確立するまでの流れを時系列に沿って整理します。

```
ペリフェラル（アドバタイザ）           セントラル（イニシエータ）

ADV_IND を ch37 に送信  ──────────→  ch37 で受信
ADV_IND を ch38 に送信  ──────────→  ch38 で受信
ADV_IND を ch39 に送信
          ↓（ADV_IND送信終了から150μs後）
                           ←────────  CONNECT_IND を ch39 に送信
CONNECT_IND を受信
  → Slave 状態に遷移                    Master 状態に遷移
          ↓（WinOffset + 1.25ms後）
  受信ウィンドウ開放    ←────────────  最初のデータパケット送信（ch: AA+Hopで決定）
  データパケットで応答  ──────────────→  受信
```

アドバタイザはADV\_INDを3チャンネルに順番で送出します。イニシエータはその中の1チャンネルで受信し、ADV\_INDの送信が終わった後の**150マイクロ秒後に同一チャンネル上でCONNECT\_INDを送信**します。この150マイクロ秒はアドバタイザが「パケット送信後に短時間受信する」ウィンドウに合わせた値です。

アドバタイザがCONNECT\_INDを受信すると、スレーブ状態に遷移してアドバタイジングを停止します。CONNECT\_INDに受信確認のパケットはありません。もしアドバタイザがCONNECT\_INDを受信できなかった場合は、次のアドバタイジングイベントでまた発見を待ちます。マスター側はしばらく通信が成立しないので、タイムアウトで接続失敗とみなします。

接続が確立すると、最初のデータパケットのタイミングはCONNECT\_INDの中の`WinOffset`と`WinSize`で指定されます。マスターは「CONNECT\_INDを送信してから（1.25ms + WinOffset）後から（WinOffset + WinSize）の間に、最初のデータパケットを送信します。


## CONNECT\_IND PDUの解剖

<!-- topic: CONNECT_IND PDUの主要フィールド -->

CONNECT\_INDのPDUには、接続後の通信に必要なすべてのパラメータが含まれています。

```
┌──────────────────────────────────────────────────────────────────────┐
│  CONNECT_IND PDU                                                     │
│  ┌──────────────────┬──────────────────┬───────────────────────────┐ │
│  │  InitA（6バイト） │  AdvA（6バイト）  │  LLData（22バイト）        │ │
│  │  イニシエータの   │  アドバタイザの   │  接続パラメータ            │ │
│  │  アドレス         │  アドレス         │                           │ │
│  └──────────────────┴──────────────────┴───────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

アドバタイザはペイロード内の`AdvA`が自分のアドレスと一致することを確認してから接続状態に遷移します。

`LLData`（22バイト）に入る主要フィールドは次のとおりです。

| フィールド | サイズ | 内容 |
|---|---|---|
| AA | 4バイト | 接続後のデータパケット用アクセスアドレス（ランダム生成） |
| CRCInit | 3バイト | CRC計算用シフトレジスタの初期値（ランダム生成） |
| WinSize | 1バイト | 最初のデータパケット送信ウィンドウサイズ（1.25ms単位） |
| WinOffset | 2バイト | 最初のデータパケット送信ウィンドウの開始オフセット（1.25ms単位） |
| Interval | 2バイト | connInterval（1.25ms単位、7.5ms〜4s） |
| Latency | 2バイト | connSlaveLatency（整数） |
| Timeout | 2バイト | connSupervisionTimeout（10ms単位、100ms〜32s） |
| ChM | 5バイト | チャンネルマッピング（37ビットのビットマップ） |
| Hop | 5ビット | hopIncrement（5〜16の整数） |
| SCA | 3ビット | スリープクロック精度（Sleep Clock Accuracy） |

第2章で「接続パラメータ」として学んだ `connInterval` / `connSlaveLatency` / `connSupervisionTimeout` が、それぞれ`Interval` / `Latency` / `Timeout`フィールドとして実際にパケットに入っています。

**AA（アクセスアドレス）**は、この接続専用のランダム値です。アドバタイジングパケットが固定値（0x8E89BED6）を使っていたのと対照的に、データパケットは接続ごとのランダム値を使います。これにより、第三者が傍受できないようになります（ただし暗号化とは別の仕組みです）。

**ChM（チャンネルマッピング）**は37ビットのビットマップで、0〜36のデータチャンネルのうち「使用する」チャンネルを1ビットで示します。干渉が激しいチャンネルをあらかじめ除外することで、Wi-Fiとの共存精度を高められます。リンク層はLL_CHANNEL_MAP_IND制御パケットを使って、接続後もChMを動的に更新できます。マスター側のスタックがチャンネル品質を監視し、干渉が検出されたチャンネルをビットマップから除外する実装が一般的です。

**SCA（Sleep Clock Accuracy）**はマスターのクロック精度を示す3ビットの値です。スレーブは「マスターがパケットを送信する予定時刻」に合わせて受信回路を起動しますが、両者のクロックには数ppmのずれがあります。このずれからタイミングがどれだけずれるかをSCAが示し、スレーブはその分だけ受信ウィンドウを広げます。


## 適応周波数ホッピング——チャンネルを飛び回る仕組み

<!-- topic: AHFの計算式と設計思想 -->

接続後、マスターとスレーブは**コネクションイベント**ごとに使用するデータチャンネルを切り替えます。これが**適応周波数ホッピング（AFH: Adaptive Frequency Hopping）**です。

チャンネルの計算式はシンプルです。

$$\text{次のチャンネル} = (\text{現在のチャンネル} + \text{hopIncrement}) \mod 37$$

`hopIncrement`は5〜16の整数で、CONNECT\_INDに含まれます。たとえばhopIncrementが5でチャンネル3を使っていた場合、次はチャンネル $(3 + 5) \mod 37 = 8$ です。その次は $(8 + 5) \mod 37 = 13$ ……と続きます。

37は素数です。5〜16のどの値のhopIncrementを使っても、最終的には37本すべてのチャンネルを一巡します（37と素因数が重ならないため）。hopIncrementが1〜4や17以上だと、一巡するチャンネルが偏ったり、少なくなるため、仕様で5〜16に制限されています。

ChMで使用不可とされたチャンネルにホッピングが当たった場合は、代替チャンネルが選ばれます。代替チャンネルの計算も仕様で定義されていますが、要点は「除外されたチャンネルには通信しない」ことです。

### 「再送に頼らず次イベントへ移る」設計思想

AFHの背景にある考え方が興味深いです。

多くの通信プロトコルは「エラーが起きたら再送する」設計です。BLEも同一コネクションイベント内での再送機能はありますが、AFHはその次の段階での戦略として「悪いチャンネルで粘るのではなく、次のイベントでは別のチャンネルで試みる」という方針を取ります。

周波数チャンネルをコネクションイベントごとに切り替えることで、特定チャンネルに干渉があっても、次のイベントでは別のチャンネルを使えます。同じチャンネルに固定したまま再送を繰り返すよりも、チャンネルが変われば短いコネクションインターバルの中で通信が成立する確率が上がります。

これは第2章で触れた「切断を恐れず素早く再接続する」という超低消費電力設計の哲学と一貫しています。「頑張って維持するのではなく、迅速に切り替える」という方針です。


## 第2章の接続パラメータとパケットの対応まとめ

<!-- topic: 第2章の接続パラメータとの対応 -->

第2章で概念として学んだ接続パラメータが、CONNECT\_INDのどのフィールドに対応するかをまとめます。

| 第2章の概念 | CONNECT\_IND フィールド | 制約 |
|---|---|---|
| コネクションインターバル | `Interval`（× 1.25ms） | 7.5ms〜4s |
| スレーブレイテンシ | `Latency` | 0〜（(Timeout/Interval)−1）かつ500以下 |
| スーパービジョンタイムアウト | `Timeout`（× 10ms） | 100ms〜32s、かつ(1+Latency)×Intervalより大 |
| 接続後のアクセスアドレス | `AA` | ランダム生成、31ビット有効 |
| チャンネルホッピングパターン | `ChM` ＋ `Hop` | 37bit bitmap ＋ hopIncrement |

これらの値はBLE SDKから設定できます。OS（iOS/Android）が中心となる接続では、セントラル側のOSがCONNECT\_INDを生成するため、アプリ側から直接制御できる場合と、接続確立後にConnection Parameter Updateをリクエストする手順が必要な場合があります。

次節では、リンク層のアドバタイジングとは別の次元で働く**GAP**——デバイスの振る舞いのシナリオを定義するレイヤをまたいだプロファイル——を解説します。
