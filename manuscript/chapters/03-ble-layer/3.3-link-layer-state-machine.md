## 3.3 リンク層の状態機械——5状態と役割の遷移

<!-- topic: 導入——リンク層の仕事 -->

物理層が「どうビットを電波でやり取りするか」を担うのに対し、**リンク層（Link Layer）**は「誰と、いつ、どのように通信するか」を管理します。デバイスの発見、接続要求、接続の維持と切断、そしてパケットの送受信タイミングの制御——これらすべてがリンク層の仕事です。

リンク層の動作は**状態機械（State Machine）**として定義されています。デバイスは常にいずれか1つの状態にあり、特定のイベントが発生することで次の状態へ遷移します。この状態機械を理解すると、接続が確立するまでの流れ、接続が切れる仕組み、そして仕様書やSDKのログに現れる役割名の意味がつながります。

---

## 5つの状態と遷移の流れ

<!-- topic: 5状態の全体像 -->

リンク層の5状態は次のとおりです。

```
                  ┌────────────────────────────────────────────┐
                  │               Standby（待機）               │
                  └───┬──────────┬──────────────┬─────────────┘
                      │          │              │
                 開始指示     スキャン開始   接続開始指示
                      │          │              │
               ┌──────▼──────┐  ┌▼───────────┐  │
               │ Advertising  │  │  Scanning  │  │
               │（アドバタイズ）│  │（スキャン）  │  │
               └──────────────┘  │ ┌─────────┐│  │
                      │           │ │Passive  ││  │
               接続要求を受信      │ │Active   ││  │
                      │           │ └─────────┘│  │
                      │           └────┬───────┘  │
                      │                │          │
                      │          接続先を決定      │
                      │                │          │
                      │           ┌────▼───────────▼────┐
                      │           │    Initiating        │
                      │           │   （イニシエート）     │
                      │           └──────────┬──────────┘
                      │                      │
                      │            CONNECT_INDを送信
                      │                      │
               ┌──────▼──────────────────────▼────────────────┐
               │              Connection（接続中）              │
               │   ┌──────────────────────────────────────┐   │
               │   │  Master（元イニシエータ）               │   │
               │   │  Slave （元アドバタイザ）               │   │
               │   └──────────────────────────────────────┘   │
               └───────────────────────────────────────────────┘
```

**Standby（スタンバイ）**は初期状態です。電波の送受信は何もしません。上位層（ホスト側のソフトウェア）から指示を受けて他の状態に遷移します。

**Advertising（アドバタイジング）**はアドバタイジングパケットを一定間隔で送信する状態です。この状態のデバイスを**アドバタイザ（Advertiser）**と呼びます。パケット送信後のごく短い受信ウィンドウで、スキャン要求（SCAN\_REQ）や接続要求（CONNECT\_IND）が届かないかを待ちます。

**Scanning（スキャニング）**はアドバタイジングパケットを受信してデバイスを発見する状態です。**パッシブスキャン（Passive Scan）**はパケットを受信するだけで追加の送信はしません。**アクティブスキャン（Active Scan）**はアドバタイジングパケットを受信したのち、SCAN\_REQを送ってスキャンレスポンス（SCAN\_RSP）をリクエストします。追加情報を取得できる分、パッシブスキャンより通信量が増えます。

**Initiating（イニシエーティング）**は、接続したい相手のアドバタイジングパケットを待ち、受信したら即座に接続要求（CONNECT\_IND）を送信する状態です。この状態のデバイスを**イニシエータ（Initiator）**と呼びます。

**Connection（コネクション）**は接続が確立した状態です。CONNECT\_INDを送ったイニシエータが**マスター（Master）**、受け入れたアドバタイザが**スレーブ（Slave）**になります。通信タイミングはマスターが制御し、スレーブはマスターのパケットに応答する形でデータを送ります。

---

## 各状態とデバイスの対応

<!-- topic: 各状態とデバイスの役割 -->

| 状態 | 役割名 | 主な動作 | 典型的なデバイス |
|---|---|---|---|
| Advertising | アドバタイザ | ADV\_INDを3チャンネルに送出 | センサー・ウェアラブル |
| Scanning（Passive） | パッシブスキャナ | ADV\_INDの受信のみ | スマートフォン（発見中） |
| Scanning（Active） | アクティブスキャナ | SCAN\_REQを送りSCAN\_RSPを取得 | スマートフォン（発見中） |
| Initiating | イニシエータ | 特定ADVにCONNECT\_INDを送信 | スマートフォン（接続直前） |
| Connection（Master） | マスター | connIntervalでパケットを送信 | スマートフォン（接続後） |
| Connection（Slave） | スレーブ | マスターのパケットに応答 | センサー・ウェアラブル（接続後） |

## スレーブの制約と役割の柔軟性

<!-- topic: スレーブの制約とソフトウェアで役割を切り替えられること -->

接続状態には重要な制約があります。

**BLE 4.0では、スレーブは同時に2つ以上のマスターとは接続できませんでした。** スレーブになったデバイスはアドバタイジングを停止するため、他のマスターからの接続要求を受け付けられなくなります。1対多の通信が必要な場面では、マスター側が複数のスレーブを管理するスター型（ピコネット）を構成します。

一方、マスターは複数のスレーブと同時に接続できます。接続ごとにランダムなアクセスアドレスが割り当てられ、各スレーブとの通信タイミングがずれるよう調整されます。

**BLE 4.1以降では、この制約が緩和されました。** 1台のデバイスがスレーブとして複数のマスターに同時接続したり、マスターとスレーブの両方のロールを同時に担うことが仕様上可能になっています。たとえば、1台のセンサーがスマートフォンとゲートウェイの両方に同時に接続してデータを送信する、といった構成が実現できます。ただし、この機能の実装はBLEコントローラ（チップ）に依存しており、すべてのデバイスが対応しているわけではありません。SDKやチップのデータシートで、同時接続数の上限を確認する必要があります。

役割はソフトウェアで自由に変えることができます。BLEコントローラはアドバタイザ・スキャナ・イニシエータのどの役割も担えます。スマートフォンがアドバタイザになることも、センサーデバイスがイニシエータになることも技術的には可能です。これは、BLEが特定のハードウェアに役割を固定していない設計になっているためです。

<!-- topic: エピソード——セントラルとイニシエータが別の名前な理由 -->

> **コラム：「セントラル」と「イニシエータ」はなぜ別の名前か**
>
> ここまで読んで「第2章で使った『セントラル』という言葉が出てこない」と気づいた方は鋭いです。
>
> 「セントラル（Central）」と「ペリフェラル（Peripheral）」はGAP（Generic Access Profile）が定義するロールの名称です。リンク層の用語ではありません。GAPの視点では「セントラル」とは「接続を開始するデバイスの振る舞い全体」ですが、リンク層は同じデバイスを「接続確立前はイニシエータ、接続後はマスター」と状態に応じた名前で呼びます。
>
> 同様に「ペリフェラル」はリンク層では「接続前はアドバタイザ、接続後はスレーブ」です。
>
> 対応をまとめると次のとおりです：
>
> | GAPのロール | リンク層（接続前） | リンク層（接続後） |
> |---|---|---|
> | Central | Initiator | Master |
> | Peripheral | Advertiser | Slave |
>
> 仕様書、SDKのログ、パケットキャプチャをそれぞれ見ると、同じデバイスが「Central」とも「Initiator」とも「Master」とも呼ばれることがあります。この対応を知っておくと、資料間の用語の乖離に混乱しなくなります。GAPのロール定義については3.6節で詳しく扱います。
