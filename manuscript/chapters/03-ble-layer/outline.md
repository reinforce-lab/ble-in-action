### 章の構成方針

第2章では「何ができるか」を学んだ。この章では「どう動いているか」に一段降りる。コントローラとホストの2層構造を俯瞰してから、物理層（電波・変調・チャンネル）→ リンク層（状態機械・パケット・接続確立）→ GAP（振る舞いの定義）の順に積み上げる。各節は第2章の対応するフェーズと結びつけながら読む。

```
[BLEスタック全体像]
  アプリケーション
  ─── ホスト ──────────────────────────────────
  GATT  ←── 第4章
  ATT   ←── 第4章
  SMP（Security Manager）
  GAP   ←── この章（3.6節）
  L2CAP
  ─── HCI（ホスト/コントローラ境界）──────────
  リンク層（Link Layer） ←── この章（3.3〜3.5節）
  物理層（Physical Layer） ←── この章（3.2節）
```

#### 3.2 物理層——電波・変調・40チャンネルの設計
**ファイル**: `3.2-physical-layer.md`  
**概要**:
- 2.4GHz帯（ISMバンド）の特性：産業/科学/医療向けで国際的に開放された帯域、電子レンジや Wi-Fi との混在
- GFSK変調：周波数シフトキーイング＋ガウスフィルタで隣接チャンネルへの干渉を抑制、1シンボル＝1ビット、1 Mbps
- 40チャンネルの配置：2 MHz幅 × 40本 = 80 MHz帯域
  - アドバタイジングチャンネル3本（37 / 38 / 39）がWi-Fiの主要チャンネル（1 / 6 / 11）と周波数的に重ならない理由
  - データチャンネル37本と適応周波数ホッピング（AFH）
- パケットフォーマット：プリアンブル / アクセスアドレス / PDU / CRC の4要素
  - プリアンブルの役割：AGC（自動利得制御）とビット同期
  - アクセスアドレス：接続ごとのランダム値（アドバタイジングは固定値 0x8E89BED6）
  - PDU：実際のデータ部分（2〜39オクテット）
  - CRC：エラー検出（暗号化時はMIC追加）
- ビットレートと伝達距離：1 Mbps・見通し50 m・低出力設計の位置づけ

**想定ページ数**: 4〜5ページ


#### 3.3 リンク層の状態機械——5状態と役割の遷移
**ファイル**: `3.3-link-layer-state-machine.md`  
**概要**:
- リンク層の5状態：Standby / Advertising / Scanning / Initiating / Connection
- 状態遷移図と遷移のトリガー：アプリが「接続しろ」と指示したときリンク層で何が起きるか
- 各状態と役割の対応：
  - Advertising → アドバタイザ（ペリフェラルの役割）
  - Scanning（Passive/Active）→ スキャナ
  - Initiating → イニシエータ（接続要求を送る直前）
  - Connection → Master（元イニシエータ）/ Slave（元アドバタイザ）
- スレーブの制約：同時に2つ以上のマスターとは接続できない（1対多のピコネットはマスター側のみ）
- ソフトウェアで役割を切り替えられること：スマートフォンがペリフェラルになることも技術的には可能

**エピソード：「なぜセントラルとイニシエータは違う名前なのか」**
- 第2章で使った「セントラル」と「GATTクライアント」は上位層の概念
- リンク層では接続確立前後で役割名が変わる（Initiating → Master）
- 同様に「ペリフェラル」はGAP層以上の概念で、リンク層ではAdvertiserまたはSlave
- この対応を知っておくと、仕様書・SDKログ・パケットキャプチャの用語が一致して読み解きやすくなる

**想定ページ数**: 4〜5ページ


#### 3.4 アドバタイジングパケットの解剖
**ファイル**: `3.4-advertising-packet.md`  
**概要**:
- PDUタイプ4種の使い分け（★ 第2章の補完）
  - `ADV_IND`：通常アドバタイジング（接続可・スキャン可・無向）
  - `ADV_DIRECT_IND`：既知デバイスへの高速再接続用（接続可・有向）
  - `ADV_NONCONN_IND`：接続も追加スキャンも不可（ビーコン用）
  - `ADV_SCAN_IND`：接続不可・追加スキャンは可
- `ADV_IND` PDUのフォーマット：ヘッダ（PDU Type / TxAdd / RxAdd / Length）＋ペイロード（AdvA 6バイト + Adv Data 最大31バイト）
- デバイスアドレスの2種類：
  - **パブリックアドレス**：SIGが企業に発行したOUI + 企業が機器に割り当てる値、製造時書き込み固定
  - **ランダムアドレス**：IRK + 乱数から計算したハッシュで定期的にアドレスを変える
  - ランダムアドレスの目的：特定個人のデバイスが追跡されることを防ぐプライバシー保護
- AD Structureの詳細フォーマット：`Length` + `AD Type` + `AD Data`
  - Flags（0x01）：接続可否・ClassicBT共存フラグ
  - Local Name（0x08/0x09）：Short/Complete の使い分け
  - Service UUIDs（0x02〜0x07, 0x15〜0x17）：16bit/32bit/128bitの3 種
  - Manufacturer Specific Data（0xFF）：先頭2バイトがCompany ID、iBeaconもここ
  - TX Power Level（0x0A）：受信RSSI差分から距離推定に使える

**コラム：アドバタイジングパケットをWiresharkで読む**
- advInterval = 0.625 ms × 整数（20 ms〜10.24 s）に advDelay（0〜10 ms ランダム）が加算
- `nRF Sniffer for Bluetooth LE` + Wiresharkで実際のパケットを表示するとAD構造体が可視化できる
- 第15章（デバッグ）への伏線として「パケットを見れば仕様書の内容が直接確認できる」

**想定ページ数**: 5〜6ページ


#### 3.5 接続確立の仕組み——CONNECT_IND から周波数ホッピングまで
**ファイル**: `3.5-connection-establishment.md`  
**概要**:
- 接続確立のシーケンス詳細：
  1. アドバタイザがADV_INDを3チャンネルで送出
  2. イニシエータがADV_INDを受信，アドバタイジングチャンネルで CONNECT_IND を送信
  3. アドバタイザが CONNECT_IND を受信 → Slave に遷移 / イニシエータ → Master に遷移
  4. CONNECT_IND 内のパラメータで最初のコネクションイベントのタイミングを決定
- CONNECT_IND PDUの主要フィールド（第2章の接続パラメータをパケットレベルに対応づける）：
  - `AA`（Access Address）：このセッション固有のランダム値
  - `CRCInit`：CRC計算レジスタの初期値
  - `WinSize` / `WinOffset`：最初のデータ送信ウィンドウ
  - `Interval` / `Latency` / `Timeout`：connInterval / connSlaveLatency / connSupervisionTimeout の物理値
  - `ChM`（Channel Map）：使用するデータチャンネルのビットマップ（Wi-Fi干渉チャンネルを除外できる）
  - `Hop`（hopIncrement）：チャンネルホッピングの刻み幅（5〜16の素数的選択で37本を均等に使う）
- 適応周波数ホッピング（AFH）：
  - コネクションイベントごとに `次チャンネル = (現チャンネル + Hop) mod 37` で計算
  - ChMで特定チャンネルを除外することでWi-Fi干渉を低減できる
  - 問題のあるチャンネルを再送で頑張るのではなく、次のイベントで別チャンネルに移って通信を継続する設計思想

**想定ページ数**: 4〜5ページ


#### 3.6 GAP——発見と接続の「振る舞い」を定義する
**ファイル**: `3.6-gap.md`  
**概要**:
- GAPとは：Generic Access Profileの略。リンク層からGATTまでをまたいで「どのように振る舞うか」を定義するプロファイル。通信プロトコルではなく「シナリオ」の仕様
- GAPロールの4種（★ 第2章の「セントラル/ペリフェラル」の正式な上位概念）：
  - **Broadcaster**：接続を受け付けず ADV_NONCONN_IND を送るだけ（ビーコン）
  - **Observer**：パッシブスキャンのみ、接続しない
  - **Peripheral**：ADV_IND を送り、接続を受け入れる。接続後はSlave
  - **Central**：スキャン・接続開始を行う。接続後はMaster
- 発見モードとプロシージャ：
  - **Limited Discoverable Mode**：一定時間だけアドバタイジング（接続しようとしている直後など）
  - **General Discoverable Mode**：常時アドバタイジング
  - **Non-Discoverable Mode**：アドバタイジングなし（ADV_NONCONN_INDはこれには含まれない）
- セキュリティ関連のGAP定義：ペアリングプロシージャの手順（SMP層への委譲）
- プライバシー機能：ランダムアドレスをGAPがIRK管理で解決する仕組み
- GAPと第2章の用語対応表：

| 第2章の用語 | GAPの正式用語 | リンク層の役割 |
|---|---|---|
| ペリフェラル | Peripheral | Advertiser → Slave |
| セントラル | Central | Initiator → Master |
| — | Broadcaster | Advertiser（Non-connectable） |
| — | Observer | Scanner（Passive） |

**想定ページ数**: 3〜4ページ
