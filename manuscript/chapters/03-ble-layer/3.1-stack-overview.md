# BLEの階層構造——コントローラとホストの分離

<!-- topic: 導入——層として整理し直す -->

第2章では、アドバタイジング・接続確立・データ交換という通信フローを「使い方」として学びました。しかしその裏では、それぞれのフェーズを担う明確な層が存在し、互いに役割を分担しています。この章では、その層の構造を分解しながら、物理的な電波から始まりデータの表現に至るまでの仕組みを順に読み解いていきます。

まず最初に「地図」として、BLEプロトコルスタック全体の構造を把握しておきましょう。この節を読み終えた時点で、「いまどの層の話をしているか」が常にわかる状態になります。

---

## コントローラとホスト——2つのブロック

<!-- topic: コントローラとホストの分離 -->

BLEプロトコルスタックは、大きく**コントローラ（Controller）**と**ホスト（Host）**に分かれています。

```
┌──────────────────────────────────────────────────┐
│  アプリケーション                                 │
├──────────────────────────────────────────────────┤
│  ホスト（Host）                                   │
│  ┌─────────────────────────────────────────────┐ │
│  │ GATT（Generic Attribute Profile）           │ │
│  │ ATT （Attribute Protocol）                  │ │
│  │ SMP （Security Manager Protocol）           │ │
│  │ GAP （Generic Access Profile）              │ │
│  │ L2CAP（Logical Link Control and Adaptation）│ │
│  └─────────────────────────────────────────────┘ │
├──────────────── HCI（Host Controller Interface）──┤
│  コントローラ（Controller）                       │
│  ┌─────────────────────────────────────────────┐ │
│  │ リンク層（Link Layer）                       │ │
│  │ 物理層（Physical Layer）                     │ │
│  └─────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

コントローラはアンテナから電波を送受信し、パケットの送受信タイミングをマイクロ秒単位で管理します。物理層とリンク層で構成され、BLEチップ内部（ハードウェアとファームウェア）で実装されます。リアルタイム性が要求されるため、処理がソフトウェアで上position できないよう、専用のICに閉じて実装されているのが一般的です。

ホストは、コントローラが確立した通信路の上でデータをどう表現し、どう運ぶかを担います。セキュリティ管理やGATTのデータベース構造も含め、スマートフォンのOSや組み込みRTOS上で動作するソフトウェアとして実装されます。

コントローラとホストの境界には**HCI（Host Controller Interface）**があります。この境界を明示しているのは、2つを異なるチップに分けた構成が現実にあるからです。

**1チップ構成**では、コントローラとホストが同じ半導体チップ内で動作します。HCIはソフトウェア間の論理的な接続として機能します。nRF52840のようなマイコンでは、チップ内部のマイクロコントローラがコントローラとホストの両方を実行し、ユーザのアプリケーションも同じチップで動きます。機能が単純な周辺機器では、製造コストを最小にするためにこの構成が取られます。

**2チップ構成**では、コントローラが無線モジュールとして部品化され、ホストは別のプロセッサで実装されます。両者はUARTやSPI、USBなどの物理インタフェースを通じてHCIで通信します。電波を出力するモジュールが各国の電波法の承認を取得していれば、機器本体での承認取得が不要になる利点があります。モバイル機器やパソコンでBluetooth USBドングルを使う場合も、おのずとこの構成になります。

規格にHCIがあるので、2チップ構成でも、どのメーカのコントローラでも共通に使えるようになります。ただし、ホストとユーザアプリケーションの間のインタフェースは規格に定義がありません。iOSのCore Bluetooth、AndroidのBluetooth API、ZephyrのBluetooth APIなど、プラットフォームごとに異なります。

## 各層の役割——一言で整理する

<!-- topic: 各層の責務の一言説明 -->

| 層 | 略称 | 一言の役割 |
|---|---|---|
| 物理層 | PHY | 電波のビット送受信（変調・復調・チャンネル管理） |
| リンク層 | LL | パケット管理・接続確立・状態管理・周波数ホッピング |
| ホスト側インタフェース | HCI | コントローラとホストの境界（コマンド/イベント/データ） |
| 論理リンク制御 | L2CAP | パケットの多重化・細分化（上位プロトコルを仮想チャンネルで分離） |
| セキュリティマネージャ | SMP | ペアリング・鍵交換・暗号化のプロシージャ |
| 汎用アクセスプロファイル | GAP | デバイスの発見・接続・振る舞いのシナリオ定義（層横断） |
| 属性プロトコル | ATT | ハンドル番号でアクセスする読み書きコマンド集 |
| 汎用属性プロファイル | GATT | ATTの上に階層、サービスとキャラクタリスティックのデータ構造定義 |

GAPは少し特殊な存在です。通信プロトコルの「一層」ではなく、リンク層からGATTまでをまたいで「どのようにデバイスを発見・接続するか」という振る舞いのシナリオを定義するプロファイルです。第2章で使った「セントラル」「ペリフェラル」という用語は、このGAPが定義したロールです。GAPの詳細は3.6節で扱います。

## この章と第4章でカバーする範囲

<!-- topic: 章とスタックの対応を明示する -->

この章では**物理層・リンク層・GAP**を扱います。電波のレベルから接続確立まで、コントローラ側の仕組みを中心に読み解きます。

第4章では**ATT・GATT**を扱います。確立した接続の上で、データをどのように表現・操作するかを解説します。

L2CAPとSMPについては、この章と第4章でそれぞれ役割に応じて触れますが、独立した節としては扱いません。

## 第2章の通信フローをスタックに対応させる

<!-- topic: 第2章フローとスタックの対応 -->

第2章で学んだ通信フローは、スタックの具体的な層に対応しています。

| 第2章のフェーズ | 担う主な層 | この章での対応節 |
|---|---|---|
| アドバタイジング・スキャン | 物理層 / リンク層 / GAP | 3.2 / 3.3 / 3.4 / 3.6 |
| 接続確立（CONNECT\_IND） | リンク層 | 3.5 |
| サービス探索 / データ交換 | ATT / GATT | 第4章 |
| ペアリング / ボンディング | SMP / GAP | 第4章（SMP）/ 3.6（GAPシナリオ） |

次節からは物理層——電波・変調・チャンネル配置——から順に積み上げていきます。
