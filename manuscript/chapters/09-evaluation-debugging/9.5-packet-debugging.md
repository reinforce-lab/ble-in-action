## 9.5 BLE packetから通信を調べる {#sec:ch9-packet-debugging}

アプリケーションログは、APIへ要求したこととcallbackを受けたことを示します。電波上で何が交換されたかを確認するには、nRF Sniffer for Bluetooth LEなどでpacketをcaptureします。

### 9.5.1 最初に問いを決める

captureを先頭から眺めるのではなく、症状をpacketへ変換します。

| 症状 | 探す事実 |
|---|---|
| 発見できない | 対象Advertisingが存在するか |
| 接続できない | Connect要求と、その後の接続event |
| Serviceが見えない | ATT Service DiscoveryのRequest／Response |
| Writeが失敗する | Write RequestとError Response |
| Notifyが来ない | CCCD WriteとHandle Value Notification |
| 遅い | 接続間隔、packet数、再送、空event |

: 症状とpacket上の確認点 {#tbl:ch9-packet-questions}

### 9.5.2 HandleとUUIDを対応づける

ATTのRead、Write、Notificationは、多くの場合UUIDではなくAttribute Handleを使います。先にService Discovery結果からHandleとCharacteristicを対応づけます。firmwareを変更するとHandleが変わる場合があるため、別buildの対応表を流用しません。

### 9.5.3 captureできないことも証拠にする

snifferは受信機です。距離、アンテナ、channel hopping追従、暗号化鍵によってpacketを取りこぼします。captureにないことだけで送信されなかったと断定せず、Peripheralログ、Central側HCI、再現条件と組み合わせます。

NordicのnRF Utilは、対応するnRF deviceを使うBLE snifferと、Bluetooth Host／Controller間のHCI loggerをWiresharkへ統合できます。空中のpacketとHostから見たpacketは観測位置が異なります。
