## 第9章の振り返り

本章では、iOSアプリからBLEデバイスを操作するためのCore Bluetoothフレームワークを解説しました。

### 学んだこと

**アーキテクチャの理解（[@sec:cb-overview]）**

- iOSのBLE実装はBTServerデーモンがホスト層を担い、アプリはIPCでアクセスする
- Core Bluetoothフレームワークはそのラッパー
- GATT概念（サービス/キャラクタリスティクス）がCBService/CBCharacteristicに対応する

**CBCentralManagerのライフサイクル（[@sec:centralmanager]）**

- `CBCentralManager` はアプリで1インスタンス。アプリライフサイクル全体で保持する
- `centralManagerDidUpdateState` が唯一の必須デリゲートメソッド
- `.poweredOn` になるまでスキャン・接続はできない

**スキャンと発見（[@sec:cb-scanning]）**

- `scanForPeripherals(withServices:)` に対象サービスUUIDを指定してフィルタスキャン
- 発見した `CBPeripheral` は必ずインスタンス変数で保持する（ARC解放防止）
- 接続後は `stopScan()` で速やかにスキャンを停止する

**GATT探索（[@sec:service-discovery]）**

- 接続確立後 `peripheral.delegate = self` を設定し、`discoverServices` → `discoverCharacteristics` のチェーンで探索
- キャラクタリスティクスのプロパティ（Properties）でRead/Write/Notifyサポートを確認できる

**Read / Write（[@sec:cb-read-write]）**

- `readValue(for:)` → `didUpdateValueFor` で非同期読み出し
- `.withResponse`（確認あり）と `.withoutResponse`（確認なし）を用途に応じて使い分ける
- 1回のATT操作では最大20バイト（デフォルトMTU）の制約がある

**Notify受信（[@sec:cb-notify]）**

- `setNotifyValue(true, for:)` でCCCDを有効化し、ペリフェラルの値更新を継続受信
- CCCDは切断でリセットされるため、再接続後は必ず再サブスクリプション
- `didUpdateValueFor` はReadとNotify双方から呼ばれるためUUIDで分岐

**バックグラウンドモード（[@sec:background]）**

- Info.plistに `bluetooth-central` を宣言するとバックグラウンドでBLEイベントを受信できる
- バックグラウンドスキャンは12分に1回の制限。`withServices: nil` は機能しない
- State Restorationで、プロセス終了後の再起動時も接続状態を復元できる


## Core Bluetoothの全体フロー

本章で実装した処理をフローとしてまとめます。

```
① Info.plist に NSBluetoothAlwaysUsageDescription を追加

② CBCentralManager(delegate: self, queue: nil) でインスタンス化

③ centralManagerDidUpdateState → .poweredOn を確認

④ scanForPeripherals(withServices: [uuid], options: nil) でスキャン開始

⑤ didDiscoverPeripheral → peripheral を保持、stopScan()、connect(peripheral)

⑥ didConnect → peripheral.delegate = self、discoverServices([uuid])

⑦ didDiscoverServices → discoverCharacteristics([uuid], for: service)

⑧ didDiscoverCharacteristicsFor →
      ├── readValue(for: readChar)
      └── setNotifyValue(true, for: notifyChar)

⑨ didUpdateValueFor → データをパースしてUIに反映

⑩ didDisconnect → 再接続（②のconnectを再度呼ぶ）
```


## よくある実装ミスまとめ

| ミス | 正しい対処 |
|---|---|
| `CBCentralManager` 初期化直後にスキャン | `centralManagerDidUpdateState` で `.poweredOn` を確認してからスキャン |
| ローカル変数で `CBPeripheral` を保持 | インスタンス変数（`var peripheral: CBPeripheral?`）で保持 |
| `peripheral.delegate` をセットし忘れ | `didConnect` 内で最初に `peripheral.delegate = self` をセット |
| 再接続後にNotifyを再設定し忘れ | `didDiscoverCharacteristicsFor` で毎回 `setNotifyValue` を呼ぶ |
| `withServices: nil` でバックグラウンドスキャン | サービスUUIDを必ず指定する |
| デリゲートメソッド名のタイポ | Xcodeの補完・ドキュメントを活用する |


## nRF52840とiOSの端対端の整合性

[@sec:ch6]のペリフェラル実装と本章のセントラル実装を組み合わせると、端対端（nRF52840 ↔ iPhone）のBLE通信が実現します。整合性を確認するポイントは次のとおりです。

| 確認項目 | nRF52840側 | iOS側 |
|---|---|---|
| サービスUUID | `BT_UUID_DECLARE_128(...)` | `CBUUID(string: "...")` |
| キャラクタリスティクスUUID | 各キャラクタリスティクス定義 | `CBUUID(string: "...")` |
| Notifyキャラクタリスティクス | `BT_GATT_CHAR_NOTIFY` | `setNotifyValue(true, for:)` |
| データ形式 | `struct env_payload { int16_t temp; uint16_t humidity; }` | `Int16 / UInt16` LE解析 |
| ATT_MTU | デフォルト23 / ネゴシエーション可 | `maximumWriteValueLength(for:)` で確認 |


## 第10章への橋渡し: Web Bluetooth API

[@sec:ch9]ではiOSを使ってBLEデバイスを操作する実装を学びました。

iOSアプリを別に開発しなくても、**Webブラウザ上のJavaScriptからBLEデバイスを操作できる** 仕組みが **Web Bluetooth API** です。同じnRF52840ペリフェラルに対して、今度はWebブラウザからアクセスします。

[@sec:ch10]では、次のトピックを扱います。

- Web Bluetooth APIのブラウザサポート状況（Chrome/Edge中心）
- `navigator.bluetooth.requestDevice()` によるデバイス選択
- `BluetoothRemoteGATTServer.connect()` で接続
- サービス・キャラクタリスティクスの取得（Core Bluetoothと対応する概念）
- Notifyのサブスクリプションとイベント受信
- Web Bluetooth APIの制約と利用場面

iOSのCore BluetoothとWeb Bluetooth APIのAPIを比較すると、概念の対応関係が理解しやすくなります。本章で学んだ「スキャン → 接続 → GATT探索 → Read/Write/Notify」のフローは次章でも同じです。


**[@sec:ch9]のまとめ**

Core Bluetoothフレームワークは、iOSアプリがBLEデバイスと通信するための標準インターフェースです。BTServerデーモンとのIPCをラップして、スキャン・接続・GATT操作・バックグラウンド動作を一貫したデリゲートパターンで提供します。[@sec:ch6]でnRF52840に実装したペリフェラルと組み合わせることで、センサーデータのリアルタイム取得、デバイス設定の読み書き、バックグラウンドでの継続動作までを実現できます。

次章では、アプリ開発なしにブラウザから同じBLEデバイスをコントロールするWebアプローチを探求します。
