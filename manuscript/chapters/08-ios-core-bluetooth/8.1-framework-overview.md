## 8.1 Core BluetoothとGAP／GATTを対応づける {#sec:ch8-core-bluetooth-map}

Core Bluetoothのクラスは、BLE仕様の役割と完全に一対一ではありません。まず、アプリから見えるオブジェクトを、第2章から第4章で使った用語へ対応づけます。

| Core Bluetooth | 本書で対応させるBLE上の役割 |
|---|---|
| `CBCentralManager` | Peripheralの発見、接続、接続解除を管理するCentral側の入口 |
| `CBPeripheral` | iOSから見た接続先Peripheralと、そのGATT Serverへの操作窓口 |
| `CBService` | GATT Service |
| `CBCharacteristic` | GATT Characteristicと、現在取得できているValueやProperties |
| `CBDescriptor` | GATT Characteristic Descriptor |
| `CBUUID` | Service、Characteristic、Descriptorを識別するUUID |

iPhoneはCentralとして接続を開始し、GATT ClientとしてnRF52840のGATT Serverを利用します。ただし、Central／PeripheralはGAP側の役割であり、Client／ServerはATT／GATT側の役割です。Core Bluetoothの型名だけを見て、二つの組を同じ意味として扱わないでください。

### オブジェクトは接続先の構造を表す

接続前に得られる`CBPeripheral`には、GATTテーブル全体が入っているわけではありません。接続後にService Discoveryを行うことで`CBService`が得られ、続いてCharacteristic Discoveryを行うことで`CBCharacteristic`が得られます。

```text
CBCentralManager
  └─ CBPeripheral
       └─ CBService
            └─ CBCharacteristic
                 └─ CBDescriptor
```

この階層は、第4章で扱ったGATTの包含関係をアプリ側から見たものです。一方、ATT Handle、ATT MTU交換、接続イベント、再送などは、通常のCore Bluetooth APIから直接操作しません。アプリから見えない処理が失敗しても、最終的にはDelegate Callbackの`Error`や切断として観測されます。

### API呼び出しと完了Callbackを対にする

Core Bluetoothの多くの操作は非同期です。メソッドを呼び出した時点では、無線上のProcedureが完了していません。

| 開始するAPI | 結果を受け取るDelegate Callback |
|---|---|
| `scanForPeripherals(withServices:options:)` | `didDiscover` |
| `connect(_:options:)` | `didConnect`または`didFailToConnect` |
| `discoverServices(_:)` | `didDiscoverServices` |
| `discoverCharacteristics(_:for:)` | `didDiscoverCharacteristicsFor` |
| `readValue(for:)` | `didUpdateValueFor` |
| `writeValue(_:for:type:)`の`.withResponse` | `didWriteValueFor` |
| `setNotifyValue(_:for:)` | `didUpdateNotificationStateFor` |

アプリでは、開始した操作と対応するCallbackを同じログへ記録します。メソッドが戻ったことを成功として扱うと、接続待ちや探索待ちの状態で次の操作を始めてしまいます。

### 製品処理の完了は別に受け取る

Measurement IntervalへのWriteが成功した場合、ATT Serverが書き込みを受け付けたことは分かります。しかし、センサーの再設定まで完了したことは保証しません。同様に、Command Requestの`didWriteValueFor`は、コマンドの完了通知ではありません。

本章では、次の三段階を分けます。

```text
Core Bluetooth APIを呼ぶ
    ↓
ATT／GATT Procedureの結果をDelegate Callbackで受け取る
    ↓
製品処理の結果を公開ValueまたはCommand Responseで受け取る
```

【ファーム開発者の方へ】

アプリへ「Writeが成功したら処理完了」と説明すると、非同期処理や失敗時の扱いが曖昧になります。受付結果とは別にCommand Responseや状態Valueを定義し、完了条件とエラーを両側で共有してください。
