## 8.9 バックグラウンド動作を含めて端対端で確認する {#sec:ch8-background-e2e}

Foregroundで一連の操作が動いた後に、製品がBackgroundで何を必要とするかを決めます。Core Bluetoothを使うからといって、アプリが常に実行され続けるわけではありません。

AppleのCore Bluetooth Programming Guideでは、Foreground専用アプリがSuspendedになるとBluetooth関連処理を実行できず、その間の関連イベントはシステムが保持し、Foregroundへ戻った後に届けると説明しています。BackgroundでCentralとして特定のイベントを処理するには、`UIBackgroundModes`へ`bluetooth-central`を宣言します。

```xml
<key>UIBackgroundModes</key>
<array>
    <string>bluetooth-central</string>
</array>
```

この宣言により、接続成立、切断、Characteristic Valueの更新など、Central側のDelegate Eventを処理するためにアプリが起こされる場合があります。任意のコードを常時実行できる権利ではありません。イベントを処理したら、短時間で状態を保存して処理を終えます。

### Backgroundでは発見条件が変わる

Backgroundでスキャンする場合、`CBCentralManagerScanOptionAllowDuplicatesKey`は無視され、複数の発見が一つへまとめられます。また、スキャンしているすべてのアプリがBackgroundにある場合、スキャン間隔が長くなり、発見まで時間がかかることがあります。固定された「何分に一回」という値を製品要件の根拠にはしません。

したがって、Foregroundでの発見時間をそのままBackgroundの保証値にしないでください。発見までの許容時間を実機で測り、即時性が必要なら、接続維持、Peripheral側のデータ蓄積、別の通知経路も比較します。

### State Preservation and Restorationを使う

Background Modeを宣言しても、システムはメモリー確保などの理由でアプリを終了できます。長時間のスキャン、接続、接続待ちを製品要件にする場合は、Core BluetoothのState Preservation and Restorationを検討します。

`CBCentralManagerOptionRestoreIdentifierKey`へ、実行をまたいで同じ値を指定します。

```swift
private static let restorationID = "jp.example.ble.device-session"

central = CBCentralManager(
    delegate: self,
    queue: nil,
    options: [
        CBCentralManagerOptionRestoreIdentifierKey: Self.restorationID
    ]
)
```

復元可能な状態があると、`centralManager(_:willRestoreState:)`が呼ばれます。復元DictionaryからPeripheralを取得したら、Delegateを設定し、現在の接続状態、探索済みService、購読状態を調べ、不足している段階から再開します。

```swift
func centralManager(
    _ central: CBCentralManager,
    willRestoreState dict: [String: Any]
) {
    guard let restored = dict[
        CBCentralManagerRestoredStatePeripheralsKey
    ] as? [CBPeripheral],
          let peripheral = restored.first else {
        return
    }

    self.peripheral = peripheral
    peripheral.delegate = self
    resumeSession(from: peripheral)
}
```

Sceneを使うアプリでは、Managerを識別する安定したUIDをアプリ自身で保存し、起動ごとに同じRestore Identifierとして渡す方法がAppleの現行資料で示されています。古い`launchOptions`だけを前提にしません。

状態復元は、アプリ独自のDevice Stateや未完了コマンドを自動的に復元する仕組みではありません。Request ID、最後に確定した設定、利用者が接続を望んでいるかは、アプリ側で必要に応じて保存します。

### 製品要件から接続方法を選ぶ

バックグラウンド動作を追加する前に、必要なデータ経路を確認します。

| 製品要件 | 検討する構成 |
|---|---|
| 画面を開いたときだけ最新状態が必要 | Foregroundで接続し、Readする |
| 接続中のイベントをBackgroundでも受けたい | `bluetooth-central`とNotifyを使う |
| 一時的に離れても測定履歴を失いたくない | Peripheral側へ蓄積し、再接続後に取得する |
| 長期間、接続または接続待ちを継続したい | State Restorationを含めて設計する |
| 即時の遠隔通知が必要 | BLEだけで満たせるかを再検討する |

【企画者の方へ】

Background Modeは「アプリを常時動かす設定」ではありません。製品が必要とするのが最新値、履歴、即時通知のどれかを分け、BLE接続を維持する構成とデバイス側へ保存する構成を比較してください。

### 端対端のシナリオを確認する

最後に、第6章から本章までの実装を一つのシナリオで確認します。

1. nRF52840のアドバタイジングをiOSが発見します。
2. 接続し、Device Control Serviceと必須Characteristicを確認します。
3. LED State、Measurement Value、Measurement IntervalをReadします。
4. Measurement Value、Command Response、Device Eventを購読します。
5. Measurement Intervalを書き込み、公開された現在値を確認します。
6. Request ID付きのCommand Requestを書き込みます。
7. 同じRequest IDのCommand Responseを受け取ります。
8. Device EventとMeasurement ValueのSequenceを記録します。
9. Peripheralを再起動し、切断、再接続、初期同期を確認します。
10. アプリをBackgroundへ移し、必要なイベントだけを処理できるか確認します。

各段階で、iOSの操作開始とDelegate Callback、nRF52840のログ、BLEパケットへ時刻とRequest IDを残します。「画面に値が出ない」という症状を、発見、接続、探索、購読、受信、パース、Device State、UIのどこで止まったかに分けます。

本章では、同じGATT契約をiOSから実装しました。第9章では、この契約をWeb Bluetoothから利用し、デバイス選択、権限、対応環境の違いを確認します。
