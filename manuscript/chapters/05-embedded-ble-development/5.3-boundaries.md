## 5.3 ハードウェアの形とソフトウェアの境界 {#sec:ch5-boundaries}

BLE製品を「外付け」「モジュール」「1チップ」だけで分類すると、責任範囲を誤ることがあります。物理的な部品形態と、ソフトウェアの役割分担は別の軸です。

### 5.3.1 部品形態を確認する

USBドングルは、USB機器として完成した外付け部品です。多くの場合はControllerとして使いますが、内部にはCPU、ファームウェア、無線回路があります。

アンテナ付き無線モジュールは、SoC、クロック、整合回路、アンテナなどを基板へまとめた部品です。無線設計と各国認証の一部を利用できることが利点です。しかし、モジュールのソフトウェア上の役割は一つではありません。Controller専用の場合も、HostとGATTまで持つ場合も、製品ロジックそのものを動かせる場合もあります。

SiP（System in Package）は、複数の構成要素を一つのパッケージへまとめます。外観は一つの部品でも、外部アンテナ、クロック、電源回路が必要な場合があります。モジュールと同じ意味ではありません。

裸のSoCを採用すると、アンテナ、整合回路、クロック、電源、基板レイアウトを製品側で設計します。部品面積と原価を最適化しやすい一方、無線性能の評価と認証の範囲が広がります。

物理的に基板へ直付けしていても、HostとControllerが別チップならソフトウェアは分離構成です。反対に、アンテナ付きモジュールの中で製品ロジックまで動かせば、製品から見たソフトウェアは1チップ構成に近くなります。

### 5.3.2 ソフトウェアから見える境界

構成が違っても、アプリケーションは最終的にAdvertising、Connection、Service、Characteristic、Read、Write、Notifyなどを扱います。そのため、どの構成でもGAP／GATT付近の抽象度で開発しているように見えます。

ただし、GAPとGATTは共通のプログラミングAPIを定めていません。Linux、モジュールSDK、BLE SoCのSDKでは、関数、オブジェクト、コールバック、非同期処理、エラー表現が異なります。

| ソフトウェア境界 | アプリケーションから見えるもの | 境界の下に隠れるもの |
|---|---|---|
| LinuxのBluetooth API | Scan、Connection、Service探索、Read、Write、Notify | BlueZ、HCI、Controller |
| MCU SDKのGAP／GATT API | Advertising、Connection、Service、Characteristic | Host内部、HCI、Controller |
| BLEモジュールのSDK／コマンドAPI | ベンダー定義の接続・GATT操作 | モジュール内のHostとController |
| BLE内蔵MCUのSDK | GAP／GATT API、設定、コールバック | スタック内部、Controller、無線制御 |

: ソフトウェアから見えるBLEの境界 {#tbl:ch5-software-boundaries}

違いが現れるのは、問題が起きたときです。API呼び出しは同じプロセス内で完結するのか、UARTを越えるのか。接続やBondの状態はOS、本体マイコン、BLEモジュールのどこに保存されるのか。どのログと無線パケットを観測できるのか。何を同じ更新イメージに含めるのか。これらは構成によって異なります。

### 5.3.3 GATTをどこへ置くか

Controllerの位置だけでなく、GATTサーバーをどこで動かすかが製品仕様に影響します。

本体側にGATTを置けば、製品状態とCharacteristicを同じソフトウェアで管理できます。Service構成やアクセス制御を柔軟に変更できますが、本体側へBluetooth Hostと十分なメモリーが必要です。

BLEモジュール側へGATTを置けば、本体側は高水準のコマンドからCharacteristicを更新できます。ただし、モジュールがServiceをどのように定義するか、接続中の状態をどう通知するか、モジュール再起動後にGATT Valueをどう復元するかが製品内APIの仕様になります。

第4章で整理した「状態」「設定」「コマンド」「イベント」は、無線の向こう側だけでなく、製品内部のチップ間境界にも現れます。たとえば、本体からBLE側へ「Advertisingを開始する」はコマンドです。BLE側から本体へ「接続された」はイベントです。センサーの現在値は、どちらを正とするか決めるべき状態です。
