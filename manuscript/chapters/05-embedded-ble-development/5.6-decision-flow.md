## 5.6 製品構成を決める {#sec:ch5-decision-flow}

ここまでの分類を、製品構成を決める順序へまとめます。この流れは正解を自動的に選ぶものではありません。採用するもの、自社で作るもの、完成製品に残る評価を明らかにするために使います。

### 5.6.1 製品の出発点を確認する

最初の分岐は、既存の本体コンピューターと製品ロジックがあるかどうかです。

```text
BLEを使う製品を作る
    ↓
既存の本体コンピューター／MCUと製品ロジックがあるか
    ├─ ある → 何を変更せず残すかを決める
    └─ ない → 製品要件からコンピューターを選ぶ
```

既存製品の場合は、本体ファームウェアへBluetooth Hostを追加できるか、外付けBLEへGATTまで任せるかを検討します。新規開発の場合は、Linux、Wi-Fi等を持つSoC、BLE内蔵マイコンのどれで製品要件を満たすかを考えます。

### 5.6.2 製品全体を動かすコンピューターを選ぶ

```text
Linux、画面、大容量処理、既存Linuxソフトウェアが必要か
    ├─ はい → Linux＋BLE
    └─ いいえ
         ↓
BLE以外の通信を製品自身が必要とするか
    ├─ はい → Wi-Fi等＋BLE MCU／SoC
    └─ いいえ
         ↓
BLE内蔵MCUで製品ロジックと周辺回路を実行できるか
    ├─ はい → BLE内蔵MCU
    └─ いいえ → 本体MCU＋外付けBLE
```

この分岐では、CPUクロックだけで処理能力を判断しません。Flash、RAM、周辺回路、スリープ、起動時間、更新、開発チームが持つソフトウェア資産を含めます。

### 5.6.3 BLE側へ持たせる責任を選ぶ

本体コンピューターとBLEデバイスを分ける場合、次にHostとGATTの位置を決めます。

```text
本体側でBluetooth HostとGATTを制御したいか
    ├─ はい → 外付けController
    │          自社で作る：Host設定、GATT、製品ロジック
    │          追加する：HCI Transport、起動、リセット
    └─ いいえ → BLEコプロセッサー
               採用する：モジュール内のHost、GATT、Controller
               自社で作る：コマンド、イベント、状態同期、復旧
```

GATTを自由に変更したい、Bluetoothスタックの状態を詳しく観測したい、本体側で複数Controllerを扱いたい場合は、本体側にHostを置く理由になります。既存製品への変更を小さくし、BLEの詳細を隠したい場合は、GATTまで持つモジュールが候補になります。

### 5.6.4 部品形態と認証条件を選ぶ

```text
無線基板とアンテナを自社で設計・評価するか
    ├─ はい → 裸のSoC
    │          無線回路、アンテナ、送信部の認証を計画
    └─ いいえ → 認証済みモジュール
               認証条件、アンテナ、配置、表示を確認

どちらの場合も残るもの
    ├─ 完成製品のBluetooth Qualification
    ├─ Bluetooth商標の使用条件
    ├─ 完成製品の不要輻射／EMC評価
    ├─ 表示と取扱説明書
    └─ 販売国・地域ごとの規制確認
```

試作では開発ボードや認証済みモジュールを使い、量産時に裸のSoCへ移る方法もあります。その場合、ファームウェアが同じでも、アンテナ、電源、クロック、基板、認証、製造試験は同じではありません。量産移行を別のハードウェア開発として計画します。

構成は一度で確定しない場合があります。仮の構成を選び、認証条件、電力、基板面積、供給期間、SDK、試作結果を確認して、前の分岐へ戻ります。

本書では、次の判断を行います。

```text
新規開発
  → BLEを中心にした小型デバイス
  → BLE内蔵MCUによる1チップ構成
  → 製品ロジック、GATT、Host、Controllerを同じ環境で開発
  → nRF52840とnRF Connect SDKを採用
```

次節から、この選択を具体的な半導体と開発環境へ落とします。
