# 組み込みBLE開発とnRF Connect SDK {#sec:ch5}

第4章までは、BLEの通信規格をたどってきました。第3章ではBluetooth HostとControllerの役割を分け、第4章ではGATTを使って製品の状態、設定、コマンド、イベントを表現しました。本章からは、それらを実際の半導体、基板、ファームウェア、OS、SDKへ配置します。

BLEを使う製品は、BLE内蔵マイコン一つで作るものだけではありません。Linuxを動かすボードへUSBドングルを接続することも、すでに製品を制御しているマイコンへBLEモジュールを追加することもできます。Wi-FiとBLEを持つマイコンを使えば、スマートフォンによる初期設定とクラウド通信を一つの製品へ組み込めます。

構成が違っても、利用者からは同じ「BLE対応製品」に見えるかもしれません。しかし、開発者が作る範囲は異なります。ある構成ではLinuxがBluetooth Hostを提供し、別の構成では自社のファームウェアがHostとGATTを動かします。BLEモジュールへGATTを任せるなら、本体マイコンとの間にコマンドとイベントの契約が必要です。1チップへまとめるなら、BLE処理と製品ロジックがCPU、Flash、RAM、割り込み、電力を共有します。

この違いは、実装だけでなく製品化にも影響します。Bluetooth Qualification、販売する国の無線規制、完成製品から出る不要輻射の評価は、それぞれ別の制度です。認証済みモジュールを採用すると無線回路の設計と認証負担を減らせますが、完成製品に必要な手続きがすべてなくなるわけではありません。

本章では、次の順で一つの製品構成を選びます。

1. 既存製品へBLEを追加するのか、BLEを前提に新規開発するのかを決めます。
2. 製品全体を動かすコンピューターと、BLE機能の置き場所を決めます。
3. 製品ロジック、GATT、Host、Controller、無線回路の責任者を決めます。
4. 既存のQualificationや無線モジュールの認証を利用できる範囲を確認します。
5. 採用するものと自社で作るものを整理します。

その後、本書のサンプルをBLE内蔵マイコンによる新規開発として位置づけ、Nordic SemiconductorのnRF52840とnRF Connect SDKへ具体化します。章の最後には、nRF52840 DKでHello Worldを実行し、最小のアドバタイジングを観測します。

本章の目的は、特定の型番を正解として勧めることではありません。製品を構成するブロックと境界を説明し、「この部品を採用するので、この部分は作らなくてよい」「この境界を置くので、このAPIと更新手順は自社で設計する」と判断できるようにすることです。
