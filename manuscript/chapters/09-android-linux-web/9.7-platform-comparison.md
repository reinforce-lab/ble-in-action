## 9.7 プラットフォーム間で共通にするものを整理する {#sec:ch9-platform-compare}

iOS、Android、Linux、WebではAPIの形が異なります。しかし、別々の製品プロトコルを作る必要はありません。Service UUID、Characteristic UUID、Properties、Value Format、コマンドとレスポンスの対応、互換性の規則は、ファームウェアとすべてのクライアントで共有します。

| 観点 | iOS | Android | Linux | Web |
|---|---|---|---|---|
| 主な役割 | 製品アプリ | 製品アプリ | 開発、試験、製造、常設システム | 一時的な設定、診断 |
| API境界 | Core Bluetooth | Android Bluetooth API | BlueZ、Bleak | Web Bluetooth API |
| 非同期結果 | Delegate | Callback | D-Bus、`async`／`await` | Promise |
| デバイス選択 | アプリが候補を管理 | アプリが候補を管理 | ツールやプログラムが管理 | 利用者がブラウザーUIで選択 |
| 製品側で確認すること | バックグラウンド、復元 | 権限、端末差、操作順 | Adapter、権限、サービス管理 | 対応環境、利用者操作、画面のライフサイクル |

この表は優劣ではなく、製品内の役割を選ぶためのものです。たとえば、一般利用者向けにはiOS／Androidアプリを提供し、開発と製造試験には同じGATT契約を扱うBleakスクリプトを使えます。設置時の設定だけをWeb Bluetoothで提供する構成も考えられます。

### APIではなく製品状態を共通にする

プラットフォームごとのコードを似せることより、次の状態と結果を同じ意味で扱うことが重要です。

- Bluetoothを利用できるか
- 目的のデバイスを発見したか
- 接続し、必要なCharacteristicを取得したか
- 初期値を読み、Notifyを購読したか
- 設定要求やコマンドを送ったか
- 製品側で処理が完了したか
- 切断後に参照と処理中の要求をどう破棄するか

第8章で使った`ready`という製品状態は、AndroidのCallback、BleakのCoroutine、WebのPromiseでも表現できます。OS APIの成功と製品処理の完了を分け、同じRequest ID、Status、Versionを使えば、プラットフォームをまたいだログの比較もしやすくなります。

### 端対端の試験項目を共有する

各クライアントでは、正常なRead／Writeだけでなく、同じ異常系を確認します。

1. 対象外のデバイスを選ばないこと
2. 必須ServiceまたはCharacteristicがないときにReadyへ進まないこと
3. 未対応Versionや不正な長さを正常値として扱わないこと
4. コマンドの受付と処理完了を混同しないこと
5. 切断時に処理中の要求を終了し、再接続後に状態を同期し直すこと

Linux上のBleakスクリプトは、この共通試験を自動化する基準クライアントとしても利用できます。モバイルアプリで問題が起きたときに同じ要求をLinuxから送り、ファームウェア、無線環境、OS API、画面状態のどこに差があるかを切り分けます。

本章では、同じGATT製品をAndroid、Linux、Webから利用したときの差を確認しました。次章では接続を維持せず、Advertisement Dataで情報を配信するビーコンとブロードキャストへ進みます。
