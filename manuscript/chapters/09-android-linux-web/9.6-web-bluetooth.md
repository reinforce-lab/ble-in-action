## 9.6 Web Bluetoothを採用できる条件を知る {#sec:ch9-web-bluetooth}

Web Bluetoothを使うと、WebページのJavaScriptからBLEデバイスのGATT ServiceとCharacteristicへアクセスできます。接続後に行うことは、第8章や本章前半と同じです。Characteristic Valueを読み書きし、必要ならNotifyを購読します。そのため、Web Bluetoothを別のBLE方式として学び直す必要はありません。

違いは、Webページが無線機器へ自由にアクセスできないことです。利用者の操作を起点にデバイスを選び、Webページへアクセスを許可する仕組みがAPIの入口になります。Webアプリから周囲のデバイスを継続的に収集する用途や、画面を閉じた後も常時接続する用途とは相性がよくありません。

### 最小の接続処理を見る

次の例では、ボタン操作を起点として、本書のDevice Control Serviceを持つデバイスを選択します。選択後はGATTへ接続し、目的のServiceとCharacteristicを取得します。

```javascript
const device = await navigator.bluetooth.requestDevice({
  filters: [{ services: [DEVICE_CONTROL_SERVICE_UUID] }]
});

const server = await device.gatt.connect();
const service = await server.getPrimaryService(
  DEVICE_CONTROL_SERVICE_UUID
);
const characteristic = await service.getCharacteristic(
  LED_STATE_CHARACTERISTIC_UUID
);

const value = await characteristic.readValue();
const ledIsOn = value.getUint8(0) === 1;
```

`requestDevice()`はiOSやAndroidのスキャン結果Callbackと同じではありません。Webページが候補一覧を直接構成するのではなく、利用者がブラウザーの選択UIを介して対象を選びます。一方、`getPrimaryService()`、`getCharacteristic()`、`readValue()`は、GATTの探索とReadをPromiseとして表現したものです。

Value Formatはプラットフォームが変わっても同じです。上の例を製品コードへ進めるなら、第8章と同様に、長さ、Version、エンディアン、符号、単位を確認するDecoderをJavaScript側にも用意します。

### インストール不要だけで採用しない

Web Bluetoothが有力なのは、次のように利用時間と対象環境を限定できる場合です。

- 購入時や設置時に、数項目だけ設定する
- 保守担当者がPCから状態を読み出す
- 製造工程や展示で、一時的な操作画面を提供する
- 対応するブラウザーとOSを運用側で指定できる

反対に、一般消費者が所有する多様な端末を対象にする製品、バックグラウンドで継続動作する製品、通知を確実に届ける製品では、ネイティブアプリを先に検討します。「アプリのインストールが不要」という利点だけで決めると、対応環境や接続ライフサイクルの制約が製品要件と衝突します。

ブラウザーとOSの対応状況、必要なセキュリティ条件、利用できるAPIは変化します。製品へ採用するときは、対象とするOS、ブラウザー、バージョンを決め、実機でデバイス選択、再接続、切断後の回復まで確認します。
