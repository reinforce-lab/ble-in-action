## GATTの4層階層——Profile・Service・Characteristic・Descriptor {#sec:gatt-hierarchy}

<!-- topic: 導入——ATTテーブルに「意味の区画」を与える -->

前節で学んだATTはデータの「読み書き手順」です。しかし、ハンドルが1から順に並んでいるだけでは、「どこからどこまでがセンサーデータの機能で、どこからがバッテリー情報か」がわかりません。GATTはATTテーブルに**意味の区画と階層**を与える仕組みです。

GATTが定義する階層は4層です。

```
Profile（プロファイル）
  └─ Service（サービス）
        └─ Characteristic（キャラクタリスティック）
              ├─ Characteristic Declaration（宣言）
              ├─ Characteristic Value（実データ）
              └─ Descriptor（ディスクリプタ）0個以上
```

この階層構造はATTテーブルのハンドル番号の並び順によって物理的に表現されます。特別なファイルシステムや目次アトリビュートがあるわけではなく、特定のタイプUUIDを持つアトリビュートが「区画の始まり」を示す形になっています。


## Profile——サービスを束ねる機器の振る舞い仕様

<!-- topic: Profile の定義 -->

**Profile（プロファイル）**は、1台の機器がどのサービスの組み合わせを持ち、どのように振る舞うかを定義したドキュメントです。ATTテーブル上のデータ構造ではなく、仕様書レベルの概念です。

Bluetooth SIG が標準化したプロファイルをSIG採択プロファイルと呼びます（Heart Rate Profile、Cycling Speed and Cadence Profile など）。開発者が独自に設計した製品固有のプロファイルはカスタムプロファイルと呼びます。

クラシックBluetoothでは、プロファイル外の機能を追加することは困難でした。BLEではGATTとATTが共通の通信基盤を提供しているため、カスタムプロファイルを定義しても標準的な探索手順（サービスディスカバリ）でアクセスできます。これが「カスタムプロファイルでもBluetooth認証を取得できる」構造の背景です。


## Service——独立した機能単位

<!-- topic: Primary / Secondary / Included Service -->

**Service（サービス）**は、デバイスの1つの独立した機能単位です。ATTテーブル上ではサービス宣言アトリビュートから始まり、その機能に属するキャラクタリスティックが続く形で表現されます。

BLEにおけるサービスの概念は、ユーザーやアプリケーションから見た「製品の機能」ではありません。**機器の内部にある互いに独立したハードウェアの機能単位**です。たとえばエアコンであれば、消費電力の計測、気温の検出、室温制御は、それぞれ個別に3つのサービスとして実装されるでしょう。ユーザーから見れば「エアコン」という1つのサービスに見えますが、GATTの設計では内部のハードウェア構成に対応した分割が正しい設計です。

この分離が重要なのは、**サービスの使われ方（プロファイル）をクライアント側が自由に決められる**からです。たとえばデバイスに音や振動でユーザーにアラートを出すサービスがあるとします。スマートフォンの置き忘れ防止アプリがこのサービスを使えば離れたときにアラートを鸣らせ、電話着信通知アプリが同じサービスを使えば着信時にアラートを鸣らせます。サービス側は「アラートを出す」という機能を提供するだけで、その利用目的は限定していません。

サービスには3種類あります。

### Primary Service（プライマリサービス）

外部のATTクライアントに公開するサービスです。サービス宣言のタイプUUIDは**0x2800**です。バリューにはそのサービスのUUID（16ビット標準またはカスタム128ビット）が格納されます。

```
Handle 0x0001: Type=0x2800, Value=0x180F → Battery Service のプライマリサービス宣言
```

### Secondary Service（セカンダリサービス）

他のサービスから参照されることを前提とした共有定義のサービスです。タイプUUIDは**0x2801**です。単独でクライアントに公開されるものではなく、Included Serviceの参照先として利用されます。

### Included Service（Includedサービス）

別のサービスを「取り込む」ための仕組みです。タイプUUIDは**0x2802**です。すでに定義済みのサービスを別のサービスの一部として組み込む場合に使います。

```
例: Body Composition Service が Battery Service を Included Service として参照
    → Battery Level のキャラクタリスティックを別途定義せず、Battery Serviceごと取り込む
```

これにより、共通部品（Battery Serviceなど）をコピーせず再利用できます。後方互換性を保ちながらサービスを拡張する際にも役立ちます。

たとえば、Battery Serviceに充電式電池の満充電容量の値を追加したいとします。この場合、Battery ServiceをIncluded Serviceとして参照し、満充電容量のキャラクタリスティックを追加した新しいサービスBを定義できます。サービスBに対応していない古いクライアントはBattery Serviceを発見して従来どおり動作し、新しいクライアントは拡張された満充電容量の値も読めます。なお、Included Serviceの参照先の振る舞いを変更することは禁止されており、新しい値や振る舞いの追加のみが許可されます。


## Characteristic——3アトリビュートの組で表現するデータ

<!-- topic: Characteristic の3アトリビュート構造 -->

**Characteristic（キャラクタリスティック）**はGATTの中心的な構成要素です。1つのキャラクタリスティックはATTテーブル上で**最低3つのアトリビュート**の組として表現されます。

```
┌────────┬───────────────────┬──────────────────────────────────┐
│ Handle │ Type（UUID）       │ Value の意味                     │
├────────┼───────────────────┼──────────────────────────────────┤
│ 0x0002 │ 0x2803            │ Characteristic Declaration       │
│        │ （固定：宣言UUID）  │ = Properties(1B) + ValueHandle(2B)│
│        │                   │   + CharacteristicUUID(2 or 16B) │
├────────┼───────────────────┼──────────────────────────────────┤
│ 0x0003 │ 0x2A19            │ Characteristic Value             │
│        │ （データのUUID）    │ = 実際のセンサー値・設定値       │
├────────┼───────────────────┼──────────────────────────────────┤
│ 0x0004 │ 0x2902            │ Descriptor（CCCD）               │
│        │ （ディスクリプタ）  │ = Notify/Indicate の購読設定     │
└────────┴───────────────────┴──────────────────────────────────┘
         ↑ Characteristic Declaration
                   ↑ Characteristic Value
                             ↑ Descriptor（0個以上）
```

**Characteristic Declaration**（タイプ: 0x2803）  
このアトリビュートの存在がキャラクタリスティックの開始を示します。バリューには次の3つの情報が詰め込まれています。

- **Properties**（1バイト）：そのキャラクタリスティックができる操作を示すフラグ
- **Value Handle**（2バイト）：Characteristic Valueのハンドル番号
- **UUID**（2バイト or 16バイト）：このキャラクタリスティックが表すデータの種類（Battery Levelなら0x2A19）

**Characteristic Value**  
実際のデータを保持するアトリビュートです。ATTクライアントがReadやWriteを行う対象は基本的にこのアトリビュートです。

**Descriptor**（0個以上）  
Characteristic Valueの補足情報や振る舞いを設定するアトリビュートです。Notify/Indicateの購読設定に使うCCCDが最も重要な例です。ディスクリプタは次節（[@sec:descriptors]）で詳しく扱います。


## Characteristic Properties——8ビットのフラグ

<!-- topic: Properties フィールドの各ビット -->

Characteristic DeclarationのPropertiesフィールドは1バイトで、各ビットがその操作の可否を示します。

| ビット | 値 | 意味 |
|---|---|---|
| bit 0 | 0x01 | Broadcast（アドバタイジングパケットにバリューを含める） |
| bit 1 | 0x02 | Read（Read Requestで読める） |
| bit 2 | 0x04 | Write Without Response（Write Commandで書ける） |
| bit 3 | 0x08 | Write（Write Requestで書ける） |
| bit 4 | 0x10 | Notify（Handle Value Notificationを送信できる） |
| bit 5 | 0x20 | Indicate（Handle Value Indicationを送信できる） |
| bit 6 | 0x40 | Authenticated Signed Writes（Signed Write Commandを受け付ける） |
| bit 7 | 0x80 | Extended Properties（さらに拡張Properties Descriptorあり） |

たとえばBattery Levelのキャラクタリスティックは一般的に「Read可・Notify可」のため、Propertiesは `0x12`（bit1 + bit4 = 0x02 + 0x10）になります。

Propertiesはあくまで「できる操作の宣言」であり、実際のパーミッション（セキュリティレベル）はPermissionフィールドで別途制御されます。PropertiesでReadビットが立っていても、Permissionがないアクセスにはエラーが返ります。


## ATTテーブルとGATT階層の対応——ハンドルの並び順で区画される

<!-- topic: ATTテーブルとGATTの対応 -->

GATTの階層はATTテーブルのハンドル番号の順序によって表現されます。ルールはシンプルです。

1. **プライマリサービス宣言**（UUID 0x2800）が現れたら、新しいサービスの開始
2. 次の**プライマリサービス宣言**が現れるまで（または0xFFFFまで）が、そのサービスに属するキャラクタリスティック群
3. **Characteristic Declaration**（UUID 0x2803）が現れたら、新しいキャラクタリスティックの開始
4. 次のCharacteristic DeclarationまたはService Declarationが現れるまでが、そのキャラクタリスティックに属するValue + Descriptor群

```
ATTテーブル（Battery Service + Device Information Serviceの例）

Handle | UUID   | 意味
0x0001 | 0x2800 | ← プライマリサービス宣言（Battery Service, UUID=0x180F）
0x0002 | 0x2803 | ← Characteristic Declaration（Battery Level）
0x0003 | 0x2A19 | ← Characteristic Value（Battery Level の実値）
0x0004 | 0x2902 | ← CCCD（Notifyの購読設定）
0x0005 | 0x2800 | ← プライマリサービス宣言（Device Info, UUID=0x180A）← 新サービス開始
0x0006 | 0x2803 | ← Characteristic Declaration（Manufacturer Name）
0x0007 | 0x2A29 | ← Characteristic Value（メーカー名：文字列）
0x0008 | 0x2803 | ← Characteristic Declaration（Model Number）← 次のキャラクタリスティック
0x0009 | 0x2A24 | ← Characteristic Value（モデル番号：文字列）
```

この構造を理解すると、[@sec:ch2]で「サービスを探す」「キャラクタリスティックを列挙する」と説明した操作が、実際にはATTテーブルを`Find Information`や`Read By Group Type`で走査することに対応しているとわかります。
