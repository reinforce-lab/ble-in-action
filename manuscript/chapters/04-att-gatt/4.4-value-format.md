## Attribute Valueをバイト列で表す {#sec:gatt-value-format}

ATTはAttribute Valueをオクテット列として運びます。Read Response、Write Request、NotificationなどのATT PDUにはValueが入りますが、その中にある`0x01`や`0x64`が何を意味するかをATTは解釈しません。

GATTは、ServiceとCharacteristicによってValueを機能へ対応づけます。さらに、各Characteristicの仕様が、Valueの長さ、フィールド、数値形式、単位、利用手順を定めます。ATTが同じでも、Characteristic UUIDが違えばValueの意味は異なります。

### ATTが運ぶものと上位仕様が決めるもの

LED Stateを1オクテットで表す場合、`0x00`をOFF、`0x01`をONと定義できます。ATTから見ると、どちらも長さ1のAttribute Valueです。`0x02`を受け取ったときに予約値として拒否するのか、新しい点滅状態として扱うのかは、Characteristicの仕様が決めます。

センサー値を2オクテットで表す場合は、さらに多くの取り決めが必要です。

- 符号付きか符号なしか
- バイトオーダーはどちらか
- 整数値をどの倍率で実際の量へ変換するか
- 単位は何か
- 測定不能やセンサー異常をどう表すか

たとえば、温度を0.01 ℃単位の符号付き16 bit整数として表し、リトルエンディアンで送るとします。Valueが`0xD7 0x07`なら、整数値は`0x07D7`、10進数で2007です。アプリケーションはこれを100で割り、20.07 ℃として表示します。

この規則を共有しなければ、通信が正常でも値を正しく利用できません。ファームウェアが20.07を浮動小数点数のメモリー表現で送り、アプリケーションが符号なし整数として読めば、ATT上はエラーのないValueでも製品の表示は壊れます。

### Bluetooth SIGのデータ型を読む

Bluetooth SIGが定めるCharacteristicには、Valueの構造を記述する仕様があります。単純なValueだけでなく、フラグによって後続フィールドの有無が変わるものや、複数の測定値を一つのNotificationに含めるものもあります。

標準Characteristicを利用するときは、UUIDとPropertiesだけを見て実装しません。対応するCharacteristic仕様で、少なくとも次を確認します。

- Value Fields
- Field Requirement
- Data Type
- Unit
- Decimal ExponentまたはResolution
- Special Values
- 各ビットの意味
- 複数フィールドの出現順序

標準ServiceやProfileが追加の手順を定めている場合は、それらも確認します。同じCharacteristicでも、採用するProfileによって必須となる操作や利用条件が加わることがあります。

### 固定長と可変長

固定長Valueは、いつ読んでも同じオクテット数を返します。LED Stateのように一つの状態を1オクテットで表す値や、3軸の測定値をそれぞれ16 bitで並べた6オクテットのValueが該当します。受信側は長さから構造を予測でき、不正な長さを検出しやすくなります。

可変長Valueは、内容に応じて長さが変わります。文字列や、フラグによって任意フィールドを追加するValueが該当します。通信量を減らせる一方、受信側は長さとフラグを確認しながら解析する必要があります。

可変長にする場合も、最大長と各フィールドの出現条件を決めます。「残りのオクテットを任意に解釈する」という仕様では、将来の追加と壊れたパケットを区別できません。

### 列挙値とビットフィールド

互いに排他的な状態は、列挙値として表せます。

| 値 | LED State |
|---:|---|
| `0x00` | OFF |
| `0x01` | ON |
| `0x02` | BLINKING |
| `0x03`〜`0xFF` | Reserved for Future Use |

: LED Stateの列挙値 {#tbl:ch4-led-state-enum}

複数の状態が同時に成立する場合は、ビットフィールドを使えます。たとえばOperation Statusの1オクテットへ、処理中、完了、エラーのフラグを割り当てる方法です。

ビットフィールドでは、予約ビットの送信値と受信側の扱いも決めます。送信側は予約ビットを0にし、受信側は未知のビットを無視する規則にすると、将来の拡張で既存アプリケーションを壊しにくくなります。ただし、未知のビットを無視しても安全な意味に限ります。

### 無効値とエラーを区別する

センサーがまだ測定していない場合、測定に失敗した場合、値が測定範囲を超えた場合は、それぞれ意味が異なります。数値の0をすべての異常に使うと、実際に0を測定した場合と区別できません。

表現方法には、予約した特殊値、状態フラグ、別のStatus Characteristic、ATT Error Responseなどがあります。どれを使うかは、エラーが発生する位置と、クライアントが必要とする情報によって変わります。

- Read要求そのものを処理できない場合は、ATT Error Responseを返せます。
- Readはできるが測定結果がまだない場合は、Value内の状態で表せます。
- 継続的な処理の失敗を後から知らせる場合は、Operation StatusをNotifyできます。

ATTエラーと製品の状態を同じ一つのエラー番号へまとめません。ATT Error Responseはプロトコル上の要求を処理できなかった理由を示し、Characteristic Valueは製品機能の状態を表します。

### 複数フィールドは一つの更新として読む

一つのValueに複数のフィールドを入れると、一回のRead ResponseまたはNotificationでまとめて受け取れます。これは、同じ時刻の測定結果を一つのスナップショットとして扱う場合に有効です。

別々のCharacteristicへ分けると、クライアントが順番にReadする間に値が更新され、異なる時刻の組み合わせになることがあります。同時性が必要なら、一つのValueにまとめるか、測定番号やタイムスタンプを付けます。

反対に、更新頻度やアクセス条件が異なるフィールドを一つにまとめると、一部だけを変更したいときにもValue全体を読み書きする必要があります。フィールドをまとめるか分けるかは、意味だけでなく、更新の単位、通知の頻度、アクセス条件から判断します。

### 時刻には基準が必要になる

タイムスタンプをValueへ含めるなら、オクテット数だけでなく、時刻の基準を決めます。

- UTCかローカル時刻か
- 起動からの経過時間か
- 単位は秒、ミリ秒、ティックのどれか
- カウンターが一周した後をどう扱うか
- 周辺機器の時計を誰が設定するか
- 時刻が未設定の状態をどう表すか

「32 bitのtimestamp」とだけ記載しても、双方が同じ時刻を復元できません。絶対時刻が不要なら、測定ごとに増えるシーケンス番号の方が目的に合うこともあります。

### Value形式を表として残す

章内のSensor Measurementを、次の形式にします。

| Offset | Length | Field | Format | Meaning |
|---:|---:|---|---|---|
| 0 | 1 | Format Version | `uint8` | Value形式の版。初版は`0x01` |
| 1 | 2 | Measurement | `sint16`, little-endian | 0.01単位の測定値 |
| 3 | 1 | Status | bit field | bit 0: 有効、bit 1: センサー異常 |
| 4 | 2 | Sequence Number | `uint16`, little-endian | 測定ごとに1増加 |

: Sensor MeasurementのValue形式 {#tbl:ch4-sensor-measurement-format}

この表だけで、通知する時期や再接続後の扱いまでは決まりません。GATTインターフェース仕様には、Value形式に加えて、初期値、更新条件、利用する操作、不正な値を受け取った場合の振る舞いを記載します。

【アプリ開発者の方へ】OSのBLE APIが返すのは、多くの場合、Characteristic Valueのバイト列です。数値型や単位へ自動的に変換されるとは限りません。UUIDに対応するValue仕様と、実際に受け取った長さを確認してから解析してください。
