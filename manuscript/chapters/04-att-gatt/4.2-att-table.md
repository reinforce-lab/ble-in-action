## GATTの構造をATTテーブルで表す {#sec:att-table}

GATTは、製品の機能をService、Characteristic、Descriptorとして構成します。ATT (Attribute Protocol、アトリビュートプロトコル)は、その構造をアトリビュートの並びとして保持し、接続相手から探索、読み出し、書き込みできるようにします。

GATTとATTは同じ対象を異なる側面から見ています。GATTでは「LED Control CharacteristicへWriteする」と表現します。ATTでは「LED ControlのValueを表すHandleへWrite Requestを送る」と表現します。

### アトリビュートの4要素

ATTサーバーが公開する一つのAttribute（アトリビュート）は、論理的に次の4要素を持ちます。

| 要素 | 役割 |
|---|---|
| Attribute Handle | ATTデータベース内でアトリビュートを指定する番号 |
| Attribute Type | そのアトリビュートの種類を示すUUID |
| Attribute Value | Typeに従って解釈する値 |
| Attribute Permissions | ReadやWriteを許可する条件 |

: ATTアトリビュートの4要素 {#tbl:ch4-attribute-elements}

Attribute Handleは、`0x0001`から`0xFFFF`までの16 bitの番号です。一つのATTデータベース内で、各アトリビュートを識別します。ATT PDUは、このHandleを使って操作対象を指定します。

Attribute TypeはUUIDです。Typeが同じでも、Handleが違えば別のアトリビュートです。たとえば複数のCharacteristic Declarationは、すべて同じTypeを持ちますが、それぞれ別のHandleに置かれます。

Attribute Valueの意味と長さは、Attribute Typeによって決まります。Characteristic Valueの場合は、そのキャラクタリスティクスの仕様がバイト列の意味を定めます。Attribute Permissionsは、ReadやWriteを許すか、暗号化や認証を要求するかといった条件です。PermissionsそのものをATTで読み出すことはできません。条件を満たさない操作には、ATTサーバーがError Responseを返します。

### ServiceもCharacteristicもアトリビュートで表す

Device Control Serviceの一部をATTテーブルへ置くと、次のようになります。HandleとUUIDは説明用です。

| Handle | Attribute Type | Attribute Value | 役割 |
|---:|---|---|---|
| `0x0010` | Primary Service | Device Control Service UUID | サービスの開始 |
| `0x0011` | Characteristic | Write、`0x0012`、LED Control UUID | LED Controlの宣言 |
| `0x0012` | LED Control UUID | LEDへ指示する値 | Characteristic Value |
| `0x0013` | Characteristic | Read、Notify、`0x0014`、LED State UUID | LED Stateの宣言 |
| `0x0014` | LED State UUID | 現在のLED状態 | Characteristic Value |
| `0x0015` | CCCD | クライアントの通知設定 | LED StateのDescriptor |
| `0x0016` | Characteristic | Read、Notify、`0x0017`、Sensor Measurement UUID | 測定値の宣言 |
| `0x0017` | Sensor Measurement UUID | 現在の測定値 | Characteristic Value |
| `0x0018` | CCCD | クライアントの通知設定 | 測定値のDescriptor |

: Device Control ServiceのATTテーブル例 {#tbl:ch4-device-control-att-table}

Primary Service DeclarationのAttribute Typeは、Bluetooth SIGが定めたPrimary ServiceのUUIDです。そのAttribute Valueには、Device Control ServiceのUUIDが入ります。このアトリビュートから、次のService Declarationの直前までが一つのサービスの範囲になります。

一つのキャラクタリスティクスは、Characteristic DeclarationとCharacteristic Valueを中心に表されます。Notifyなどに必要なDescriptorがあれば、その後に続きます。

Characteristic DeclarationのValueには、Properties、Characteristic ValueのHandle、Characteristic UUIDが入ります。表の`0x0013`を読むと、LED StateがReadとNotifyに対応し、実際の値が`0x0014`にあり、その意味をLED State UUIDで識別できると分かります。

Characteristic ValueのAttribute Typeは、そのキャラクタリスティクスのUUIDです。LED StateをReadするとき、クライアントはDeclarationの`0x0013`ではなく、Valueの`0x0014`を指定します。

### UUIDとHandleは用途が異なる

UUIDは、サービスやキャラクタリスティクスの意味を共有します。Handleは、現在接続しているATTサーバーのデータベース内で、そのアトリビュートを操作するために使います。

アプリケーションは、目的のService UUIDとCharacteristic UUIDを指定して探索します。探索によって、現在のGATTデータベースで使われているHandleが分かります。その後のATT ReadやWriteでは、Handleを使います。

ファームウェア更新によってアトリビュートが追加または削除されると、Handleが変わる可能性があります。以前の接続で`0x0012`がLED Controlだったとしても、その番号を製品仕様へ固定値として書くことはできません。UUIDで意味を探し、現在のHandleを使う必要があります。

### PropertiesとPermissionsは別に評価する

Characteristic DeclarationのPropertiesは、クライアントがどのGATT Procedureを利用できるかを示します。Attribute Permissionsは、現在の接続や相手に、その操作を許可するかを決めます。

たとえばMeasurement IntervalにReadとWriteのPropertiesを付け、Readは暗号化なしで許可し、Writeには暗号化を要求できます。クライアントは探索によってWriteに対応していると分かりますが、暗号化されていない接続からWriteすると、ATTサーバーはアクセス条件を満たしていないことを示すエラーを返します。

PropertiesとPermissionsを一つの「読み書き可能フラグ」として扱うと、アプリケーションが何を実行できる可能性があり、なぜ現在の操作が拒否されたのかを説明できません。GATTインターフェース仕様には、両方を分けて記載します。

### ATT PDUはHandleでアトリビュートを操作する

ATTクライアントがLED StateをReadする場合、Read RequestにHandle `0x0014`を入れます。ATTサーバーはPermissionsを確認し、そのHandleのValueをRead Responseで返します。

```text
GATTクライアント                         GATTサーバー
      |                                       |
      |-- Read Request (Handle 0x0014) ------>|
      |<----------- Read Response (0x01) -----|
      |                                       |
```

アプリケーションから見ると「LED StateをReadする」という一つの操作です。その下では、探索で得たHandleをATT PDUへ入れ、ATT固定チャンネルからL2CAP以下へ渡しています。第2章で追った通信経路へ、GATT構造とATTテーブルを対応づけられます。
