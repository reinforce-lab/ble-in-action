## 4.5 ディスクリプタの種類と実践的使い方

<!-- topic: 導入——Characteristic Value の付属情報 -->

前節のATTテーブルの図で、Battery Levelキャラクタリスティックの後ろにもう1つのアトリビュート（CCCD, UUID 0x2902）があることに気づいたかと思います。このような、Characteristic Valueの補足情報や動作設定を担うアトリビュートを**Descriptor（ディスクリプタ）**と呼びます。

ディスクリプタは大きく2種類に分けられます。

- **振る舞いを設定するディスクリプタ**：クライアントまたはサーバの動作を制御する（CCCD、SCCDなど）
- **メタデータを提供するディスクリプタ**：バリューの型・単位・説明文字列など補足情報（Presentation Format、User Descriptionなど）

---

## CCCD——Notify/Indicateを「受け取る側」が有効化する

<!-- topic: CCCD の仕組みと重要性 -->

**CCCD（Client Characteristic Configuration Descriptor）**はUUID 0x2902を持つディスクリプタで、BLE開発において最も頻繁に登場します。

CCCDは2バイトの値を持ち、下位2ビットが意味を持ちます。

| ビット | 意味 |
|---|---|
| bit 0 | 0x0001 に設定するとNotificationを有効にする |
| bit 1 | 0x0002 に設定するとIndicationを有効にする |
| 両方0 | Notification・Indication ともに無効（デフォルト） |

ATTサーバは**CCCDのビットが0の間はHandle Value NotificationもHandle Value Indicationも送信しません**。クライアントがCCCDに0x0001を書き込んで初めて、サーバはそのキャラクタリスティックの変化をクライアントに通知し始めます。

```
クライアント                              サーバ
    │                                      │
    │── Write Request（CCCD=0x0001） ─────▶│  ← Notify有効化
    │◀─ Write Response ────────────────────│
    │                                      │
    │                                      │  値が変化
    │◀─ Handle Value Notification ─────────│  ← 通知が届く
    │◀─ Handle Value Notification ─────────│
```

### CCCDがクライアント固有である理由

CCCDの設定は接続しているクライアントごとに独立しています。ATTサーバに複数のクライアントが同時に接続している場合、クライアントAのCCCDとクライアントBのCCCDは独立した値を持ちます。実装上はサーバがクライアントごとにCCCDの値を保持することになります。

### ボンディングとCCCDの永続化

ボンディングなし（暗号化なし）の接続では、**接続が切れるたびにCCCDはデフォルト（0x0000＝無効）にリセット**されます。再接続のたびにクライアントがCCCDへの書き込みを行わなければ、Notifyは届きません。

ボンディングあり（ペアリング済みの暗号化接続）の場合、GATT仕様ではCCCDの設定を不揮発メモリに保存（永続化）してよいとされています。多くのBLE SDKはこの永続化に対応しており、再接続後も設定が維持されます。

> **コラム：CCCDを書き忘れるとNotifyは届かない**
>
> 「センサーのデータが来ない」BLEアプリのデバッグでよくある原因が、CCCDへの書き込み忘れです。ATTレベルで見るとシンプルで、「CCCDのbit0が0なので、サーバはNotificationを送信していない」というだけです。
>
> iOSのCore Bluetoothでは`setNotifyValue(_:for:)`、AndroidのBluetoothGattではCCCDを指定して`writeDescriptor()`を呼ぶ必要があります。SDKのラッパーAPIを使っているときは内部で自動的に書き込まれることも多いですが、ロウレベルのATTログを確認すると、Write RequestがCCCDハンドルに発行されているのが見えます。
>
> 再接続後にNotifyが届かなくなった場合は、CCCDの再書き込みを接続イベントハンドラに実装できているかを確認するのが最初のチェックポイントです。

## SCCD——サーバ側のBroadcast設定

<!-- topic: SCCD の役割 -->

**SCCD（Server Characteristic Configuration Descriptor）**はUUID 0x2903を持つディスクリプタで、Broadcast操作の有効/無効をサーバ側で設定します。

CCCDがクライアントごとに独立した設定であるのに対し、SCCDは**どのクライアントが書き込んでも、サーバグローバルの動作が変わる**という特性があります。Broadcastプロパティを持つキャラクタリスティックで、アドバタイジングパケット内にバリューを含めるかどうかを制御するために使います。

実際の製品設計でSCCDを使うケースはBroadcast機能を持つニッチなプロファイルに限られ、一般的なセンサーデバイスの設計ではほとんど登場しません。

---

## Characteristic User Description——人間可読の説明文字列

<!-- topic: User Description Descriptor -->

**Characteristic User Description**はUUID 0x2901を持つディスクリプタで、キャラクタリスティックの意味を人間が読める文字列で説明します。UTF-8エンコードの文字列を格納します。

汎用のBLEスキャナアプリ（nRF Connect等）がカスタムプロファイルのデバイスに接続したとき、User Descriptionがあればキャラクタリスティックの意味をツール上に表示できます。「Unknown Characteristic」と表示される代わりに「Temperature Sensor（℃）」のように表示できます。

Extended PropertiesにWritable Auxiliariesビット（bit1）が設定されている場合、クライアントがUser Descriptionを書き換えることも可能です（ユーザーが独自ラベルを付ける用途）。

---

## Characteristic Presentation Format——型・単位の機械可読な定義

<!-- topic: Presentation Format Descriptor -->

**Characteristic Presentation Format**はUUID 0x2904を持つディスクリプタで、バリューの型・スケール・単位を機械可読な形式で定義します。仕様書なしでも汎用クライアントがデータを正しく解釈・表示できるようにする目的で使います。

フォーマットは7バイト固定です。

| フィールド | サイズ | 内容 |
|---|---|---|
| Format | 1B | データ型（0x04=uint8, 0x06=uint16, 0x0E=IEEE-754 32bit float など） |
| Exponent | 1B | 10のべき乗スケール（sint8：例えば-1なら実値×0.1） |
| Unit | 2B | SIG定義の単位UUID（0x272F=celsius, 0x27E4=percentage など） |
| Namespace | 1B | Descriptionフィールドの名前空間（0x01=SIG） |
| Description | 2B | 同一キャラクタリスティックに複数Presentation Formatがある場合の識別番号 |

たとえば「0.01℃単位の気温（sint16）」のPresentation Formatは次のようになります。

```
Format     = 0x0E（sint16）
Exponent   = -2  （× 10^-2 = 0.01単位）
Unit       = 0x272F（摂氏）
Namespace  = 0x01
Description= 0x0000
```

1つのキャラクタリスティックに複数のPresentation Formatが付く場合（例：緯度と経度のペア）は、Aggregate Formatで組み合わせを定義します。

---

## Characteristic Aggregate Format——複数値の組み合わせ

<!-- topic: Aggregate Format Descriptor -->

**Characteristic Aggregate Format**はUUID 0x2905を持つディスクリプタで、複数のPresentation Format Descriptorのハンドルを列挙することで、バリューが複数の値の組み合わせであることを示します。

たとえば位置情報のキャラクタリスティックが「緯度（sint32）+ 経度（sint32）」という2つの値を持つ場合、緯度用・経度用のPresentation Formatを別々に定義し、Aggregate Formatにそれぞれのハンドルをリストとして格納します。

実装の複雑さに対してメリットが限定的なため、多くのカスタムデバイスでは使われません。ただし、標準プロファイルの一部には定義されています。

---

## Extended Properties——Propertiesの拡張フラグ

<!-- topic: Extended Properties Descriptor -->

**Extended Properties**はUUID 0x2900を持つディスクリプタで、Characteristic Declarationの8ビットPropertiesだけでは足りない2つの追加フラグを提供します。

| ビット | 意味 |
|---|---|
| bit 0 | Reliable Write：Prepare/Execute Writeによる信頼性重視の書き込みをサポートする |
| bit 1 | Writable Auxiliaries：User Description Descriptorへの書き込みを許可する |

Characteristic DeclarationのPropertiesでbit7（Extended Properties）が立っている場合のみ、このディスクリプタが存在します。

---

ディスクリプタの全種類を見てきました。実際の開発で最も重要なのはCCCDです。CCCDを正しく扱えること——有効化のタイミング、ボンディングなし時のリセット挙動、クライアントごとの独立性——を理解しておくと、Notify関連のトラブルの大半に対処できます。次節では、これらのサービス・キャラクタリスティック・ディスクリプタを組み合わせてプロファイルを設計する実践的なパターンを学びます。
