## ATTで長いデータを運ぶ {#sec:att-large-data}

Attribute Valueの長さと、一回のATT PDUで運べるValueの長さは同じではありません。さらに、ATT PDUが一つのLink Layer Data PDUに収まるとも限りません。第3章で見た複数の長さを、ATTの操作へ対応づけます。

### ATT MTUはATT PDUの上限を示す

ATT MTU (Maximum Transmission Unit)は、一つのATT PDUの最大長です。従来のATTベアラーの既定値は23オクテットです。ATT PDUにはOpcodeやAttribute Handleも入るため、ATT MTUのすべてをAttribute Valueへ使えるわけではありません。

ATT MTUが23オクテットの場合、代表的なPDUで一度に運べるValueは次のようになります。

| ATT PDU | Value以外の主なフィールド | 一度に運べるValue |
|---|---|---:|
| Read Response | Opcode: 1オクテット | 最大22オクテット |
| Write Request | Opcode: 1、Handle: 2オクテット | 最大20オクテット |
| Write Command | Opcode: 1、Handle: 2オクテット | 最大20オクテット |
| Notification | Opcode: 1、Handle: 2オクテット | 最大20オクテット |
| Indication | Opcode: 1、Handle: 2オクテット | 最大20オクテット |

: ATT MTUが23オクテットの場合に一度に運べるValue {#tbl:ch4-att-mtu-payload}

接続後にExchange MTU Procedureを行うと、クライアントとサーバーが受信できるATT MTUを交換できます。実際のATT MTUは、双方が示した値の小さい方になります。ATT MTUを大きくすると、一回のATT操作で運べるValueを増やせます。

一つのAttribute Valueの最大長は512オクテットです。Attribute Valueが`ATT_MTU - 1`オクテットより長い場合、ATTではLong Attributeとして扱います。Attribute Valueの上限と、一つのPDUで運べる長さを混同しません。

ただし、ATT MTUはLink Layer Data Lengthではありません。大きなATT PDUが一つのLink Layer Data PDUへ収まらなければ、L2CAPが分割し、受信側で再構成します。アプリケーションは通常、このL2CAPの分割をValueのチャンクとして扱いません。再構成されたATT PDUを受け取ります。

### 長いAttribute ValueをReadする

一回のRead Responseに収まらないAttribute Valueは、最初のRead Requestに続けてRead Blob Procedureを使い、オフセットを変えながら読み出せます。

```text
クライアント                              サーバー
    |-- Read Request (Handle) ------------->|
    |<-- Read Response (先頭部分) -----------|
    |-- Read Blob Request (Offset=n) ------>|
    |<-- Read Blob Response (続き) ----------|
```

クライアントは、返された部分の長さから続きを要求するか判断します。OS APIがこの手順を隠し、一回のCharacteristic Readとして見せる場合もあります。どの長さまで扱えるか、アプリケーションからオフセットを指定できるかは、対象プラットフォームのAPIで確認します。

センサーの一回の測定値を、理由なく長いAttributeへする必要はありません。Read Blobは、デバイス情報の文字列や、比較的長い一つの論理値を扱う仕組みです。継続するログや任意長のファイル転送を、そのまま一つの巨大なAttributeとして設計することとは分けて考えます。

### 長いAttribute ValueをWriteする

Write RequestまたはWrite Commandへ一度に入らないValueは、Prepare WriteとExecute Writeを使って書き込めます。Prepare Write RequestにはHandle、Offset、Valueの一部が入り、サーバーは準備した値をキューへ保持します。すべての部分を準備した後、Execute Write Requestによって書き込みを実行するか、取り消します。

この手順は、一つのAttribute Valueを複数のATTトランザクションで準備し、最後にまとめて反映するために使えます。サーバーには、Prepare Writeを保持するキューとメモリーが必要です。組み込み機器のATTサーバーが、常に十分な長さのPrepare Writeへ対応できるとは限りません。

Reliable Writesでは、Prepare Write Responseに返されたHandle、Offset、Valueが要求と一致することをクライアントが確認してから実行します。これはAttributeへ書き込む値の整合性を確認するATTの手順です。製品がそのValueを使って外部処理を完了したことまで保証するものではありません。

### Characteristicの長さと製品データの長さを分ける

ログ、画像、ファームウェア更新データは、Attribute Valueの最大長を超えることがあります。長さが上限内でも、接続が切れた後に途中から再開したい、受信側のフラッシュメモリーへ順次保存したい、転送した部分を検証したいという要求があります。

この場合は、一つのCharacteristic Valueを長くするだけでなく、製品の上位プロトコルとしてデータを分割します。

たとえば、次のCharacteristicを使えます。

- Transfer Control: 開始、終了、中止、再開位置の要求
- Transfer Data: チャンク本体
- Transfer Status: 受領済み位置、処理中、完了、エラー

Transfer DataのValueには、転送ID、オフセット、チャンク長、データを入れます。サーバーは、保存できた位置をTransfer Statusで返します。接続が切れた後は、クライアントが保存済み位置を確認し、続きから再開できます。

これはATTが自動的に提供するファイル転送ではありません。ATTのRead、Write、Notifyなどを使って、製品仕様が転送手順を作っています。

### Write Without Responseには送信可能量がある

Write Without ResponseはATTの応答を待ちませんが、クライアントが無制限にCommandを渡せるわけではありません。アプリケーション、Host、Controller、相手側のHost、ファームウェアには、それぞれバッファーと処理速度があります。

OSやSDKが「次のWrite Without Responseを受け付けられる」ことを示すAPIやイベントを提供する場合は、それに従います。これは送信側のキューへさらに渡せることを示します。相手のファームウェアがフラッシュメモリーへ保存したことを示すACKではありません。

相手側の処理完了位置まで知る必要がある場合は、Transfer StatusなどでアプリケーションレベルのACKを返します。ACKの単位をチャンクごとにすると確認回数が増え、まとめて返すと再送範囲が大きくなります。転送速度、メモリー、再開に必要な粒度の間で決めます。

### シーケンス番号で欠落と重複を検出する

連続するチャンクには、シーケンス番号またはオフセットを付けます。受信側は、期待する番号と比較して、欠落、順序の違い、再送による重複を検出できます。

番号だけでは、異なる転送の同じ番号を区別できません。再接続をまたいで転送するなら、転送IDも必要です。受信側が再起動した場合に、どの状態を保存し、どこから再開できるかも決めます。

OTAでは、受信したデータの完全性や署名の検証も必要です。本節ではATT上の分割と進行管理までを扱い、更新イメージの検証、MCUboot、SMPは第14章で扱います。

【企画者の方へ】「BLEでファイルを送れるか」という問いには、ファイルサイズだけでは答えられません。許容する転送時間、中断後に最初からやり直せるか、製品が保持できるバッファー、スマートフォンを操作し続ける必要があるかを開発者と確認してください。
