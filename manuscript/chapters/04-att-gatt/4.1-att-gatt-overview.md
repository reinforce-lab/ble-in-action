# ATTとGATTの位置づけ——接続の上に乗るデータプロトコル

<!-- topic: 導入——接続確立の「その先」 -->

第3章では、BLEデバイスが電波を送り出してから接続が確立するまで——物理層・リンク層・GAPの仕組みを順に学びました。セントラルとペリフェラルがCONNECT\_REQパケットを交わした瞬間、2台のデバイスは接続状態に入ります。しかし、接続が確立しただけでは「何もできない」状態です。センサーの値を読む、LEDを光らせる、通知を受け取る——そういった実際の操作はすべて、接続の上に乗るもう1つの仕組みによって実現されます。

その仕組みが**ATT（Attribute Protocol）**と**GATT（Generic Attribute Profile）**です。

ATTは「通信プロトコル」です。「ハンドル番号を指定してバリューを読む」「バリューを書き込む」「変化したら通知する」といった操作のコマンド体系を定義します。GATTは「データ構造の定義」です。ATTのテーブルをどのように区画し、どのような意味を持つ情報をどこに置くかを規定します。第2章で使ったRead・Write・Notify・Indicateは、ATTのコマンドがそのAPIとして見えていたものです。この章では、その中身を開いていきます。

---

## ATTとGATTの前身——クラシックBluetoothとの違い

<!-- topic: 分離の経緯 -->

クラシックBluetoothでは、「通信の手順」と「データの構造」は1つのプロファイルに一体化されていました。たとえばHFP（ハンズフリープロファイル）は、電話の音声をやり取りするコマンドとその意味を1つの仕様書に定義しています。新しい機能を追加するには新しいプロファイルをゼロから設計しなければならず、Bluetooth SIGの承認プロセスも経る必要がありました。

BLEはこの構造を変えました。通信プロトコル（ATT）とデータ定義（GATT）を分離し、独立した層として規格化したのです。

この分離によって生まれた最大のメリットは**カスタムプロファイルの自由度**です。開発者は自社製品専用のサービスとキャラクタリスティックを独自のUUIDを使って自由に定義できます。しかもその場合でも、GATTとATTがBluetooth SIG側の標準層として存在しているため、「BLEを実装している」という意味でのBluetooth認証を取得できます。プロファイルの中身がオリジナルであっても、BLEの標準的な探索手順（サービスディスカバリ）で発見でき、標準的なATTコマンドでアクセスできるのです。

## ATTサーバとATTクライアント——接続のどちら側か

<!-- topic: ATTサーバ/クライアントの役割 -->

ATTプロトコルには「ATTサーバ」と「ATTクライアント」という2つの役割があります。これはリンク層のMaster/Slaveとは独立した概念です。

**ATTサーバ**はアトリビュート（データ）を保持する側です。センサーデバイス、ウェアラブル、BLEビーコン——値を保持して外部からのアクセスに応じる機器がATTサーバになります。**ATTクライアント**はサーバにアクセスしてデータを読み書きする側です。スマートフォンのアプリや、PCのBLE管理ツールがクライアントになります。

```
                  ATT クライアント              ATT サーバ
              （スマートフォン等）         （センサーデバイス等）
                        │                           │
                        │   Read Request            │
                        │ ─────────────────────▶   │
                        │   Read Response           │
                        │ ◀─────────────────────   │
                        │                           │
                        │   Write Request           │
                        │ ─────────────────────▶   │
                        │   Write Response          │
                        │ ◀─────────────────────   │
                        │                           │
                        │   Handle Value Notification│
                        │ ◀─────────────────────   │
```

ここで重要な点があります。リンク層の「セントラル」（接続を開始した側）は、多くの場合ATTクライアントですが、これは仕様上の必然ではありません。一般的な実装パターンとして定着しているというだけです。実際、BLEでは同一接続内で双方向にATT操作を行う構成も可能です。ただし本書では「セントラル＝スマートフォン＝ATTクライアント」「ペリフェラル＝センサー＝ATTサーバ」という最も一般的な配置を前提として話を進めます。

## HCI境界——ControllerとHostが分かれる理由

<!-- topic: HCI境界の意義と業界分業 -->

ATTとGATTがBLEスタックのどこに位置するかを、もう一段解像度を上げて確認しましょう。

```
┌─────────────────────────────────────────────────┐  ← OSベンダー / アプリ開発者の領域
│  アプリケーション                                │
├─────────────────────────────────────────────────┤
│  GATT（Generic Attribute Profile）               │  ← この章（4.4〜4.6節）
├─────────────────────────────────────────────────┤
│  ATT （Attribute Protocol）                      │  ← この章（4.2〜4.3節）
├─────────────────────────────────────────────────┤
│  GAP / SMP / L2CAP                              │  ← 第3章（GAP）
╠═════════════════════════════════════════════════╣  ← HCI境界（USB / UART / SPI）
│  HCI（Host Controller Interface）               │
├─────────────────────────────────────────────────┤
│  リンク層 / 物理層（RF）                          │  ← 第3章 / 半導体ベンダーの領域
└─────────────────────────────────────────────────┘  ← SoCまたは専用コントローラチップ
```

二重線で示した**HCI（Host Controller Interface）境界**は、BLE規格が明示的に定めたスタックの分割線です。この境界より下が**Controller**（物理層・リンク層）、上が**Host**（L2CAP以上のソフトウェアスタック）です。

この分割が業界の分業構造を生み出しました。半導体ベンダー（Nordic Semiconductor、Qualcomm、Texas Instrumentsなど）はController側——RF回路設計とリンク層のファームウェア——に集中して製品を設計できます。一方、OS ベンダー（Apple、Google、Microsoft、Linux カーネルのBlueZコミュニティ）はHostスタックをソフトウェアとして独立して実装・更新できます。HCIがあることで、両者は互いの内部実装を知らなくても連携できるのです。

ATTとGATTはHostスタックの中に位置するピュアなソフトウェア層です。新しいプロファイル仕様への対応や、プロトコル実装上のバグ修正は、OSのソフトウェアアップデートだけで行えます。ハードウェア（Controllerチップ）の交換は不要です。

---

> **コラム: USB ドングルが成立する理由——HCI が切り分けるControllerとHost**
>
> HCI境界は、物理的な分離をも可能にしています。BLE規格はHCIの物理伝送路として複数の方式を定義しています——USB、UART（H4プロトコル）、BCSP（Bluetooth Serial Controller Protocol）、3線UART。どの伝送路を使っても、HCIコマンドとイベントの体系は共通です。
>
> これが「USB BLEドングル」を成立させます。RF回路を内蔵しないデスクトップPCやラズベリーパイでも、Controllerチップを搭載したUSBドングルを1つ挿すだけでBLEに対応できます。RF設計という高度な専門領域を隔離したまま、既存のホストマシンをBLE対応にできるのです。
>
> 対比として、Wi-FiにはHCIのような標準化された分割境界がありません。Wi-Fiチップのドライバはチップベンダーがカーネル向けに独自に提供することが多く、OSを跨いで同一のHostスタックを使い回すことは難しい構造です。BLEのHCI境界はそのアーキテクチャ上の先見性を示しています。
