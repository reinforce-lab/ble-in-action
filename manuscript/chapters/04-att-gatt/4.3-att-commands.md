## ATTコマンドの種別——Request/Response/Command/Notification/Indication

<!-- topic: 導入——ATT PDUの種類 -->

ATTのコマンドは総称して**PDU（Protocol Data Unit）**と呼ばれます。すべてのATT PDUは1バイトのOp Codeから始まり、そのOp Codeによってパケットの構造と意味が決まります。ATT仕様ではPDUを大きく5種類の交換パターンに分類しています。

| パターン | 方向 | 応答 | フロー制御 |
|---|---|---|---|
| Request / Response | クライアント → サーバ | あり（必ず1対1対応） | あり |
| Indication / Confirmation | サーバ → クライアント | あり | あり |
| Command | クライアント → サーバ | なし | なし |
| Notification | サーバ → クライアント | なし | なし |
| Signed Command | クライアント → サーバ | なし | なし |

第2章で使ったAPIとの対応は次のとおりです。

| BLE APIの操作 | ATTのパターン |
|---|---|
| Read（値を読む） | Request / Response |
| Write with Response | Request / Response |
| Write Without Response | Command |
| Notify（サーバからの通知） | Notification |
| Indicate（応答が必要な通知） | Indication / Confirmation |

以下、パターンごとに詳しく見ていきます。

---

## Request / Response——トランザクションと30秒タイムアウト

<!-- topic: Request/Response パターン -->

**Request / Response**は最も基本的な交換パターンです。クライアントがRequestを送ると、サーバがResponseを返します。1つのRequestに対して必ず1つのResponseが対応します。

重要な制約があります。**同一接続内でRequest/Responseのトランザクションは同時に1つしか実行できません**。あるRequestを送った後、そのResponseを受け取る前に別のRequestを送ることはできません。

この制約は一見厳しく見えますが、BLEの設計意図としては合理的です。サーバ側のデバイスは多くの場合、RAMもCPUも限られた小さなマイコンです。トランザクションが同時に1つだけであれば、サーバはリクエストのキューイングや並列処理を実装する必要がなく、「1つ受けて、処理して、返す」という単純なループで実装できます。これはBLEが小型・低コストのデバイスでも実装できるよう設計されていることの皔おれです。

```
クライアント                              サーバ
    │                                      │
    │── Read Request(handle=0x0003) ──────▶│
    │                                      │ 処理中
    │                        ← (他のRequestは送れない)
    │◀─ Read Response(value=0x64) ─────────│
    │                                      │
    │── Write Request(handle=0x0004) ─────▶│
    │◀─ Write Response ────────────────────│
```

サーバがRequestに応答しない場合、BLE仕様では**30秒のタイムアウト**が設定されています。30秒以内にResponseが届かないと、クライアントは接続を切断します。これはエラー状態として定義されており、再接続しなければATTセッションを続けられません。

> **エピソード：ATTタイムアウトの30秒ルール**
>
> あるスマートフォンアプリの開発中、特定のWrite操作の後にアプリが「30秒後に突然切断される」という問題が発生しました。調査すると、ファームウェアがWrite Requestを受け取った後、処理に時間のかかる外部フラッシュへの書き込みをメインループ内で行っていたためでした。外部フラッシュへの書き込みが30秒を超え、Write Responseを返せないまま接続がタイムアウトしていたのです。
>
> 対処は「長時間処理を別タスクに移す」ことでした。Write Requestを受け取ったら即座にWrite Responseを返し、実際の書き込み処理は別スレッドに委譲します。処理完了をアプリに伝えたい場合は、専用の「処理完了通知」キャラクタリスティックからNotificationを送る設計にします。
>
> Read/Write Requestへの応答は「受け付けた」ことの確認であり、「処理完了」の確認ではないという分離が、BLEファームウェア設計の基本パターンです。

## Indication / Confirmation——サーバ起点の確認付き通知

<!-- topic: Indication/Confirmation パターン -->

**Indication / Confirmation**はRequest/Responseと逆方向のトランザクションです。サーバがIndicationを送り、クライアントがConfirmationを返します。

```
クライアント                              サーバ（センサーデバイス）
    │                                      │  値が変化した
    │◀─ Handle Value Indication ───────────│
    │                                      │
    │── Handle Value Confirmation ────────▶│
    │                                      │
             ↑ Confirmationが返るまで次のIndicationは送れない
```

Indicationは「確実に届いた」ことをクライアントが確認するまで次を送れません。Notificationより信頼性が高い反面、スループットが下がります。心拍計などの継続的なデータ送信にはNotificationが使われることが多く、決済端末や医療機器のように「1回でも取りこぼせない」データにはIndicationが向いています。

---

## Notification——応答なしのサーバ起点通知

<!-- topic: Notification パターン -->

**Notification（Handle Value Notification）**はサーバからクライアントへの一方向通知です。クライアントからの確認応答（Confirmation）はなく、フロー制御もありません。

```
クライアント                              サーバ（センサーデバイス）
    │                                      │  値が変化
    │◀─ Handle Value Notification ─────────│
    │◀─ Handle Value Notification ─────────│  （後続を待たずに連続送信可）
    │◀─ Handle Value Notification ─────────│
```

応答がない分、高速にデータを送り続けられます。BLE接続間隔（Connection Interval）の制御は下のリンク層が担うため、ATTレベルでは「送れるだけ送る」動作になります。ただし送達保証はないため、途中パケットが失われても再送されません。

NotificationとIndicationのどちらをサポートするかは、キャラクタリスティックのPropertiesフィールド（4.4節参照）で定義されます。また、どちらも送信前にクライアントがCCCD（Client Characteristic Configuration Descriptor）に設定を書き込む必要があります。この仕組みは4.5節で詳しく扱います。

## Command——応答なしの書き込み

<!-- topic: Command パターン -->

**Command**はクライアントからサーバへの応答なし書き込みです。ATT仕様では"Write Command"として定義されており、第2章のAPIでは "Write Without Response" に相当します。

サーバはWrite Commandを受け取っても応答を返しません。受け付けた場合でも、処理できなかった場合（バッファフルなど）でも、クライアントには何も返りません。その代わり、Request/Responseのトランザクション制約がなく、接続間隔の許す範囲で連続送信できます。

コントロールポイント型のキャラクタリスティック（例：デバイスをリセットする命令）でよく使われます。操作に対して応答確認が不要な場合、またはスループット優先の場面での連続送信に適しています。

## Find系コマンド——サービスディスカバリの基盤

<!-- topic: Find Request 系 -->

Find系コマンドは、ATTテーブルのハンドルとタイプを探索するためのコマンドです。接続直後のサービスディスカバリで使われます。

**Find Information Request / Response**
ハンドル範囲を指定して、その範囲内のすべてのアトリビュートのハンドルとタイプ（UUID）のペアを取得します。GATTがディスクリプタの位置を特定するために使用します。

```
クライアント: Find Information Req（開始ハンドル=0x0001, 終了ハンドル=0xFFFF）
サーバ:      Find Information Rsp
             → [ 0x0001, 0x2800 ][ 0x0002, 0x2803 ][ 0x0003, 0x2A19 ][ 0x0004, 0x2902 ]...
```

1つのResponseで返せるペア数はMTUに依存します（MTU=23の場合、16ビットUUIDなら最大5ペア）。テーブルが長い場合はハンドル範囲を更新しながら繰り返し呼び出します。

**Find By Type Value Request / Response**
特定のタイプ（UUID）と値を持つアトリビュートを検索します。プライマリサービスUUID（0x2800）とサービスUUIDを指定して、そのサービスがどのハンドル範囲に存在するかを探すのに使います。

## Read系コマンド——目的に応じた6種類

<!-- topic: Read Request 系 -->

Read系コマンドは6種類あります。多くの場合はシンプルな**Read Request**だけで済みますが、状況に応じて使い分けることで効率が上がります。

**Read Request / Response**
最もシンプルな読み取りです。ハンドルを1つ指定すると、そのアトリビュートのバリューが返ります。返るサイズは最大(MTU-1)バイトです。

```
クライアント: Read Request（handle=0x0003）
サーバ:      Read Response（value=0x64）  ← Battery Level = 100%
```

**Read Blob Request / Response**
バリューが(MTU-1)バイトを超えるロング・アトリビュートを読み取るために、オフセットを指定して分割読み出しします。

```
クライアント: Read Blob Req（handle=0x0010, offset=0）  → 最初の22バイト
クライアント: Read Blob Req（handle=0x0010, offset=22） → 次の22バイト
クライアント: Read Blob Req（handle=0x0010, offset=44） → 以降繰り返し...
```

**Read Multiple Request / Response**
複数のハンドルを1つのRequestにまとめて、それらのバリューを一括で取得します。ただし、**各バリューが固定長であることが前提**です（可変長バリューが混在すると境界がわからないため）。

**Read By Type Request / Response**
ハンドル番号を知らなくても、タイプ（UUID）を指定してバリューを読み取れます。GATTがキャラクタリスティックの宣言（UUID 0x2803）を一括取得するために使用します。

**Read By Group Type Request / Response**
グループ型のアトリビュートとその終端ハンドルをまとめて取得します。プライマリサービスの一覧取得（UUID 0x2800を指定）がその典型的な用途です。

```
クライアント: Read By Group Type Req（0x0001〜0xFFFF, type=0x2800）
サーバ:      Read By Group Type Rsp
             → [ handle=0x0001, end_handle=0x0004, value=0x180F ]  ← Battery Service
             → [ handle=0x0005, end_handle=0x000C, value=0x180A ]  ← Device Info
```

## Write系コマンド——5種類の信頼性とサイズのトレードオフ

<!-- topic: Write Request 系 -->

**Write Request / Response**
最も一般的な書き込みです。サーバがバリューを確実に受け付けたことをResponseで確認できます。1回に書けるサイズは最大(MTU-3)バイト（デフォルトMTU=23の場合は20バイト）です。

**Write Command**
応答なしの書き込みです。トランザクション外のため連続送信可能ですが、送達は保証されません。

**Prepare Write Request / Execute Write Request**
ロング・アトリビュート（20バイトを超えるバリュー）を信頼性重視で書き込むための2段階コマンドです。Prepare Writeで複数のチャンクをキューに積み、Execute Writeで一括確定（またはキャンセル）します。

```
クライアント: Prepare Write Req（handle, offset=0, value=先頭20B）
サーバ:      Prepare Write Rsp
クライアント: Prepare Write Req（handle, offset=20, value=次の20B）
サーバ:      Prepare Write Rsp
クライアント: Execute Write Req（flags=commit）  ← 確定
サーバ:      Execute Write Rsp
```

**Signed Write Command**
暗号化されていない接続でも書き込みの正当性を検証できるよう、MAC（Message Authentication Code）シグネチャを付与したWrite Commandです。ペアリング済みで暗号化なしの接続で使われる場面があります。
