## アトリビュートの構造——ハンドル・タイプ・バリュー・パーミッション {#sec:att-structure}

<!-- topic: 導入——ATTサーバの「中身」 -->

ATTクライアント（スマートフォン等）は、ATTサーバ（センサーデバイス等）に対して「何番のデータを読む」「何番に値を書く」という操作を行います。この「番号」がスタート地点です。ATTサーバの中には、番号と値の組が並んだ**アトリビュートテーブル**があります。すべてのBLEデバイスのデータ操作は、このテーブルに対するアクセスとして成立します。

アトリビュート（Attribute）1個は4つの要素で構成されます。この4要素を理解すれば、ATTコマンドがどのような情報をやり取りしているかが見えてきます。


## ハンドル——アトリビュートのアドレス

<!-- topic: Handle の定義と役割 -->

**ハンドル（Handle）**は、テーブル内のアトリビュートを識別する2バイトの番号です。0x0001から0xFFFFの範囲で、サーバ内で一意に割り当てられます。ATTクライアントはこの番号を指定してアクセスします。

```
アトリビュートテーブル（ATTサーバ内）
┌────────┬────────────────────────────┬──────────────┬────────────┐
│ Handle │ Type（UUID）               │ Value         │ Permission │
├────────┼────────────────────────────┼──────────────┼────────────┤
│ 0x0001 │ 0x2800（Primary Service）  │ 0x180F       │ Read       │ ← Battery Service
│ 0x0002 │ 0x2803（Characteristic）   │ Props+0x0003 │ Read       │ ← Decl
│ 0x0003 │ 0x2A19（Battery Level）    │ 0x64 (100%)  │ Read,Notify│ ← Value
│ 0x0004 │ 0x2902（CCCD）             │ 0x0000       │ Read,Write │ ← Descriptor
└────────┴────────────────────────────┴──────────────┴────────────┘
```

ハンドルは接続中は固定されません。厳密には、**接続が確立してからハンドルは変わらないことが保証**されます。再接続後も機器の実装が変わっていなければ同じ番号ですが、仕様上は「接続ごとにサービスディスカバリを行う」ことが推奨されています。

ハンドル0x0000は「無効ハンドル」として予約されており、使用できません。


## タイプ——アトリビュートの種類を表すUUID

<!-- topic: Type（UUID）の構造 -->

**タイプ（Type）**は、アトリビュートの種類を示すUUID（Universally Unique Identifier）です。「これはサービスの定義か」「これはキャラクタリスティックの宣言か」「これが実際のデータか」——タイプを見ればそのアトリビュートが何者かがわかります。

UUIDは本来128ビット（16バイト）ですが、Bluetooth SIGが定義した標準的なサービス・キャラクタリスティック・ディスクリプタには**16ビットの短縮UUID**が割り当てられています。16ビット短縮UUIDは次のベースUUIDに埋め込むことで128ビットUUIDに展開できます。

```
ベースUUID: 0000xxxx-0000-1000-8000-00805F9B34FB
               ↑
           ここに16ビット値を入れる

例: UUID 0x2A19 → 00002A19-0000-1000-8000-00805F9B34FB
```

よく登場するタイプUUIDをまとめると次のとおりです。

| UUID（16bit） | 意味 |
|---|---|
| 0x2800 | Primary Service（プライマリサービスの宣言） |
| 0x2801 | Secondary Service（セカンダリサービスの宣言） |
| 0x2802 | Included Service（他サービスの取り込み） |
| 0x2803 | Characteristic Declaration（キャラクタリスティックの宣言） |
| 0x2900 | Characteristic Extended Properties |
| 0x2901 | Characteristic User Description |
| 0x2902 | Client Characteristic Configuration（CCCD） |
| 0x2903 | Server Characteristic Configuration（SCCD） |
| 0x2904 | Characteristic Presentation Format |
| 0x2905 | Characteristic Aggregate Format |

0x2800〜0x290xの範囲はGATTの構造を定義するための「メタデータ」のUUIDです。0x1800番台はサービスUUID（Battery ServiceなどのサービスUUID）、0x2A00番台以降はキャラクタリスティックUUID（Battery LevelなどのデータUUID）が割り当てられています。

カスタムサービスの場合は、開発者がランダムに生成した128ビットUUIDをそのまま使います。Bluetooth SIGへの登録は不要ですが、他社製品との衝突を避けるためUUID生成ツール（uuidgen等）で生成した値を使うのが慣例です。


## バリュー——アトリビュートの実データ

<!-- topic: Value の構造とエンディアン -->

**バリュー（Value）**は、アトリビュートが保持する実際のデータです。0バイトから最大512バイトまでの可変長バイト列です。

バリューのエンディアンはATT仕様では規定されておらず、上位層（GATT仕様や個別のプロファイル仕様）が決定します。GATT仕様では一般に**リトルエンディアン**（下位バイトが先）を採用しています。たとえばBattery Levelは1バイトの値（0〜100）ですが、Heart Rate MeasurementのようなUINT16の値は下位バイトから並びます。

バリューが使用できる最大長は512バイトですが、1回のATTコマンドで転送できるサイズはMTU（後述）に依存します。大きなバリューは複数のトランザクションに分けてやり取りします。


## パーミッション——アクセス制御

<!-- topic: Permission の仕組み -->

**パーミッション（Permission）**は、そのアトリビュートに対して「どの操作が許可されているか」を定義します。具体的には次の組み合わせで設定されます。

| パーミッション | 意味 |
|---|---|
| Readable | Read Requestを受け付ける |
| Writeable | Write Request / Write Commandを受け付ける |
| Readable with authentication | 認証済み接続でのみ読み取り可 |
| Writeable with authentication | 認証済み接続でのみ書き込み可 |
| Readable with authorization | 高セキュリティ接続でのみ読み取り可 |
| Writeable with authorization | 高セキュリティ接続でのみ書き込み可 |

重要な特性が1つあります。**パーミッションはATTコマンドで直接読み取れません**。ATTクライアントがパーミッションを違反する操作を試みると、サーバはエラーレスポンス（Error Response）を返します。クライアントはそのエラーコードから間接的にパーミッションを知ることになります。

```
クライアント: Read Request（認証なし接続で保護されたアトリビュートを読もうとした）
サーバ:      Error Response（エラーコード: Insufficient Authentication）
              → 「このアトリビュートは認証が必要」とわかる
```


## ATT MTU——1回のパケットで運べるサイズ

<!-- topic: MTU の意味と拡張 -->

ATTプロトコルでやり取りされる1つのパケット（PDU）の最大サイズを**ATT MTU（Maximum Transmission Unit）**と呼びます。

デフォルトのMTUは**23バイト**です。このうち1バイトはOp Code（コマンド種別）に使われるため、データとして運べる最大サイズは**22バイト**です。Read Requestへの応答（Read Response）なら最大22バイトのバリューを1回で返せます。Write Requestではコマンドバイトとハンドル2バイトが追加でかかるため、1回に書けるのは最大**20バイト**です（Write Requestのオーバーヘッドは3バイト）。

```
ATT MTU = 23バイト の場合

Read Response:
  [ Op Code 1B ][ Value 最大22B ]
   ↑ 23 - 1 = 22バイト

Write Request:
  [ Op Code 1B ][ Handle 2B ][ Value 最大20B ]
   ↑ 23 - 3 = 20バイト

Notification:
  [ Op Code 1B ][ Handle 2B ][ Value 最大20B ]
   ↑ 23 - 3 = 20バイト
```

MTUはExchange MTU Request/Responseで接続後に拡張できます（BLE 4.2以降）。双方がサポートするMTUの小さい方が採用されます。

```
クライアント: Exchange MTU Req（クライアント受信MTU = 512）
サーバ:      Exchange MTU Rsp（サーバ受信MTU = 128）
→ 採用MTU = min(512, 128) = 128バイト
```

MTUを大きくするとデータ転送効率が向上します。たとえば1KBのファームウェアデータを転送する場合、MTU=23では50回以上のトランザクションが必要ですが、MTU=251なら約4回で済みます。ただし、MTUの拡張はデバイスのRAMサイズに依存するため、RAMの少ないマイコンでは23のまま使うことも多いです。


## ロング・アトリビュート——512バイトを超えない範囲での分割読み書き

<!-- topic: Long Attribute の扱い -->

バリューが(MTU-1)バイトを超える場合、**ロング・アトリビュート**として複数のトランザクションに分割してアクセスします。読み出しにはRead Blob Request（オフセット指定付きの読み出し）、書き込みにはPrepare Write / Execute Writeを使います。これらは[@sec:att-commands]で詳しく扱います。

アトリビュートの4要素——ハンドル・タイプ・バリュー・パーミッション——はATTのすべてのコマンドが前提とする基盤です。次節では、この基盤の上でATTクライアントとサーバがどのようにコマンドをやり取りするかを見ていきます。
