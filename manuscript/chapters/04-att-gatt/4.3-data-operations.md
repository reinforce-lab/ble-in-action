## 値をどの操作でやり取りするか {#sec:gatt-data-operations}

GATTの操作は、データが向かう方向と、ATTで応答を返すかによって性質が変わります。Propertiesを決めるときは、操作名を選ぶだけでなく、製品のどの完了点を相手へ伝える必要があるかを考えます。

| GATTから見た操作 | ATTの交換 | 方向 | ATTでの応答 |
|---|---|---|---|
| Read | Request／Response | クライアントから要求し、サーバーが値を返す | あり |
| Write | Write Request／Write Response | クライアントからサーバー | あり |
| Write Without Response | Write Command | クライアントからサーバー | なし |
| Notify | Notification | サーバーからクライアント | なし |
| Indicate | Indication／Confirmation | サーバーからクライアント | あり |

: GATT操作とATTの交換パターン {#tbl:ch4-gatt-att-operations}

### Valueの意味とATTの交換パターンを分ける

GATTでは、現在状態、設定値、処理の指示、イベントのすべてをCharacteristic Valueとして表します。ATTは、そのValueをどのPDUで運ぶかを定めます。製品上の意味とATTの交換パターンは、一対一には対応しません。

| 製品上の意味 | 利用できるGATT操作の例 |
|---|---|
| 現在状態 | Readで取得し、NotifyまたはIndicateで変化を受け取る |
| 設定値 | Readで確認し、Writeで変更する |
| 処理の指示 | Write RequestまたはWrite Without Responseで要求する |
| イベント | NotifyまたはIndicateで知らせ、必要なら履歴をReadする |

: 製品上の意味とGATT操作の関係 {#tbl:ch4-semantics-and-operations}

ATT仕様でいうWrite Commandは、サーバーがATT Responseを返さない書き込みです。「校正を開始する」「LEDを点灯する」といった製品上のコマンドだけを運ぶPDUではありません。本章では、用語の衝突を避けるため、製品上の意味には「処理の指示」、ATTのPDUには「Write Command」を使います。

どのGATT操作を選んでも、Valueの意味、保持期間、再送時の振る舞い、完了条件は製品の仕様で補う必要があります。

### 現在値をReadする

Readは、クライアントが必要な時点で現在値を取得する操作です。例の機器では、LED State、Sensor Measurement、Measurement Interval、Operation StatusをReadできます。

Read Requestには、読み出すAttribute Handleが入ります。ATTサーバーがReadを許可し、Valueを返せる場合は、Read Responseに値を入れます。条件を満たさない場合はError Responseを返します。

Readは、接続直後の初期状態を取得する場合や、通知を受け取っていない期間の最新値を確認する場合に向いています。一方、値の変化を知るために短い間隔でReadを繰り返すと、変化がないときにも通信が発生します。変化したときだけ知ればよい値にはNotifyを組み合わせます。

### 変化した値をNotifyする

Notifyは、GATTサーバーからGATTクライアントへ、Valueの変化やイベントを知らせる操作です。クライアントが毎回Readしなくても、Sensor MeasurementやLED Stateの更新を受け取れます。

Notifyを受け取るには、クライアントが対象のキャラクタリスティクスを探索し、CCCDでNotificationを有効にします。Notify Propertyは、そのキャラクタリスティクスがNotificationに対応することを示します。CCCDは、接続している各クライアントが実際に受け取るかを示します。

```text
GATTクライアント                         GATTサーバー
      |                                       |
      |-- CCCDへNotification有効を書き込む -->|
      |<----------------- Write Response ------|
      |                                       |
      |<-- Sensor Measurement Notification ----|
      |<-- Sensor Measurement Notification ----|
```

Notificationに対するATTの応答はありません。Link Layerには受信確認と再送がありますが、Notificationを受け取ったアプリケーションが値を処理したことをGATTサーバーへ返す仕組みではありません。連続する測定値について欠落を検出する必要があるなら、Valueにシーケンス番号を含めるなど、製品の仕様として補います。

接続直後は、まずReadで現在値を取得し、その後の変化をNotifyで受け取る構成にできます。通知を一時的に受け取れなかった可能性がある場合も、Readによって現在状態へ戻れます。イベントをNotifyする場合は、後からReadできる現在状態があるのか、一度しか意味を持たないイベントなのかを区別します。

### Writeで値や指示を送る

Writeは、GATTクライアントからGATTサーバーへValueを送る操作です。例の機器では、LED ControlとMeasurement Intervalに使います。

Measurement Intervalは、製品が保持する設定値です。Write後にReadすれば、現在採用されている値を確認できます。LED Controlを一回の処理の指示として設計するなら、WriteしたValueを後からReadすることより、LED StateやOperation Statusで結果を確認する方が意味に合います。

Write Requestを受け取ったATTサーバーは、Handle、長さ、Value、Permissionsなどを確認します。要求を受け付けた場合はWrite Responseを返し、受け付けられない場合はError Responseを返します。

Write Responseが示す範囲は、Valueと製品仕様によって変わります。Measurement Intervalのように、値を検証して設定を更新するだけなら、Write Responseを設定完了として扱える場合があります。モーターを動かす、フラッシュメモリーを消去する、センサーを校正するといった時間のかかる処理では、ATTの応答を製品動作の完了まで待たせない方が安全です。

長い処理では、次のように完了点を分けます。

```text
アプリケーションがWriteを要求する
→ OSが要求を受け付ける
→ ATTサーバーがWrite Requestを受け取る
→ ATTサーバーがWrite Responseを返す
→ ファームウェアが処理を開始する
→ 製品の動作が完了する
→ Operation Statusで完了を通知する
```

Write Responseを「製品の動作が完了した」という意味にしたい場合は、ATTの制約内で必ず応答できる処理時間かを確認する必要があります。処理時間が外部回路や機械動作に依存するなら、Writeは指示の受付までとし、処理中、完了、失敗を別の状態として返します。

### Write Without Responseで連続送信する

Write Without Responseは、ATTのWrite Commandを使います。ATTサーバーからWrite Responseは返りません。応答を待たずに次の値を送れるため、連続したデータ転送に利用できます。

名前に`Command`が含まれますが、製品上の処理の指示専用ではありません。逆に、工場出荷時リセットのような製品上の指示でも、受付拒否の理由を返す必要があればWrite Requestを使います。

一方、クライアントは、各CommandをATTサーバーが処理した位置をATTの応答から確認できません。OSが送信要求を受け付けたこと、Controllerが無線パケットを送ったこと、相手のLink Layerが受信したこと、相手のファームウェアがValueを処理したことは別の完了点です。

LEDのON／OFFのように、一回の操作結果を確認したい場合は、応答を省く利点が小さくなります。Write Requestを使うか、LED StateのNotifyによって結果を確認できます。ログやファイル相当のデータを連続送信する場合はWrite Without Responseを使い、送信可能量と受信側の処理速度に合わせた流量制御を製品のプロトコルとして設計します。

### IndicateでATTの受信確認を得る

Indicateは、GATTサーバーからGATTクライアントへValueを送り、クライアントがATTのConfirmationを返す操作です。同じATTベアラーでは、サーバーは一つのIndicationに対するConfirmationを受け取るまで、次のIndicationを送りません。

Confirmationによって分かるのは、クライアントのATTがIndicationを受け取ったことです。アプリケーションが画面へ表示したこと、ストレージへ保存したこと、利用者が確認したことまでは保証しません。

製品の仕様でアプリケーション処理まで確認する必要があるなら、クライアントから別のCharacteristicへACKを書き込むなど、上位の応答を定義します。ATTのConfirmationと製品のACKを同じものとして扱いません。

NotifyとIndicateの選択を「高速だが低信頼」「低速だが高信頼」という言葉だけで決めることも避けます。何の受信を、どの位置で確認する必要があるのかを先に決めます。継続する測定値なら、古い値のConfirmationを待つより最新値をNotifyする方が製品の目的に合う場合があります。一回の状態変更を順番どおりに渡す必要があるなら、Indicateが選択肢になります。

### 同じ指示を再送できるようにする

通信が切れたり応答が分からなくなったりすると、アプリケーションは同じ操作を再送することがあります。LEDをONに設定する操作は、同じ値を複数回書いても結果が変わりません。一方、「一段階進める」「課金する」「記録を一件追加する」という指示は、再送によって処理が重複します。

再送があり得る操作では、最終状態を指定する、操作IDを付ける、すでに処理したIDを判定するといった設計が必要です。この性質はATTが決めるものではありません。GATTインターフェース仕様に、同じ指示を再送したときの振る舞いを記載します。

### コマンドをControl Pointとして表す

一回の処理を要求し、その結果を返すCharacteristicは、標準GATT ServiceでもControl Pointと呼ばれることがあります。カスタムGATTインターフェースでも、Command RequestとCommand Responseを分けると、設定値へのWriteと処理の実行を区別できます。

本章のセンサー付きライトでは、次のCharacteristicを使います。

| Characteristic | 製品上の役割 | Properties |
|---|---|---|
| Command Request | コマンドIDと引数を送る | Write |
| Command Response | 受付、進行、成功、失敗を返す | Indicate、必要ならRead |
| LED State | コマンド実行後の現在状態を表す | Read、Notify |
| Device Event | コマンドとは独立して発生した事実を知らせる | NotifyまたはIndicate |

: コマンドと状態を分けるCharacteristic {#tbl:ch4-command-characteristics}

クライアントは、Command ResponseのCCCDでIndicationを有効にしてから、Command RequestへWriteします。このインターフェースでは、ATTのWrite Responseを、Command RequestのValueを検証して依頼を受け付けた段階と定義します。製品上の処理が完了したことまでは示しません。コマンド処理の結果はCommand Responseで返します。コマンドがLEDの状態を変えた場合は、LED Stateも更新します。

```text
GATTクライアント                         GATTサーバー
      |                                       |
      |-- Command ResponseのCCCDを有効化 ---->|
      |<------------------ Write Response -----|
      |                                       |
      |-- Command RequestへWrite ------------>|
      |<------------------ Write Response -----|  依頼の受付
      |                                       |  処理を実行
      |<-- Command Response Indication --------|  成功または失敗
      |-- Confirmation ----------------------->|
      |<-- LED State Notification ------------|  現在状態
```

Command ResponseをIndicateすると、サーバーはクライアントのATTが応答を受け取ったことを確認できます。コマンドの頻度が高く、ATTのConfirmationを待つコストが合わない場合はNotifyも選べます。その場合に取りこぼしを検出または回復する方法を別に用意します。

Command ResponseをReadにも対応させると、通知を受け取れなかった場合や再接続後に、直近または実行中の結果を確認できます。ただし、複数クライアントや複数コマンドを扱う場合は、「直近の結果」が誰のどの要求を指すかを定義する必要があります。

### Command RequestのValueを定義する

MatterのInvoke Requestは、Command Pathで対象のClusterとCommand IDを示し、Command Fieldsに引数を入れます。BLEの一つのService内では、Service UUIDがMatterのClusterに近い名前空間になります。そのため、Command RequestにはCommand IDと引数を入れれば、同じ考え方を小さく適用できます。

再送と応答の対応づけが必要なら、Request IDも加えます。

| Offset | Length | Field | Format | Meaning |
|---:|---:|---|---|---|
| 0 | 1 | Format Version | `uint8` | Command Request形式の版 |
| 1 | 4 | Request ID | `uint32`, little-endian | 要求と応答の対応、重複検出 |
| 5 | 2 | Command ID | `uint16`, little-endian | Service内で実行する処理 |
| 7 | 1 | Flags | bit field | 初版ではすべて0 |
| 8 | 可変 | Command Payload | Commandごとに定義 | コマンドの引数 |

: Command RequestのValue形式 {#tbl:ch4-command-request-format}

ATT PDUからValue全体の長さが分かるため、単一のWriteで完結するならPayload Lengthを省略できます。独自に複数チャンクへ分ける場合や、一つのValueへ複数コマンドを入れる場合は、各要素の長さを明示する必要があります。本章の基本形では、一回のWriteに一つのコマンドだけを入れます。

Command IDは、Device Control Service内で意味が一意になるように割り当てます。たとえば、`0x0001`をSet LED State、`0x0002`をStart Calibration、`0x0003`をFactory Resetと定義できます。同じCommand IDのPayload形式を互換性なく変更しません。

Matterの`CommandRef`は、一つのInvoke Requestに複数のコマンドを入れる場合に、それぞれの応答を対応づける参照です。本章のRequest IDは、それより広い役割を持たせています。再接続やアプリケーションによる再送を扱うなら、Request IDの有効範囲、保持期間、再利用条件をGATTインターフェース仕様で定めます。

### Command Responseで結果を返す

Command Responseには、元のRequest IDとCommand IDを入れます。さらに、コマンドがどの段階にあり、成功しなかった場合は何が起きたかを示します。

| Offset | Length | Field | Format | Meaning |
|---:|---:|---|---|---|
| 0 | 1 | Format Version | `uint8` | Command Response形式の版 |
| 1 | 4 | Request ID | `uint32`, little-endian | 対応するCommand Request |
| 5 | 2 | Command ID | `uint16`, little-endian | 対応するコマンド |
| 7 | 1 | Phase | enum | Accepted、In Progress、Succeeded、Failed |
| 8 | 2 | Status | `uint16`, little-endian | 成功または失敗理由 |
| 10 | 可変 | Response Payload | Commandごとに定義 | コマンド固有の結果 |

: Command ResponseのValue形式 {#tbl:ch4-command-response-format}

単純な処理では、SucceededまたはFailedだけを一回返せます。時間のかかる処理では、Accepted、In Progress、最後のSucceededまたはFailedを返せます。進捗率を頻繁に送るなら、Command Responseとは別にOperation Statusを現在状態として公開する方法もあります。

Statusには、コマンドに共通する結果を定義します。

- Success
- Unsupported Command
- Invalid Payload
- Invalid State
- Busy
- Not Authorized
- Internal Error

コマンド固有の結果データはResponse Payloadへ入れます。MatterのInvoke Responseも、コマンド固有の応答データまたはStatusを返す構造です。BLEではATT Error ResponseとCommand ResponseのStatusを使い分けます。

- Handleが存在しない、Writeが許可されていない、暗号化条件を満たさない場合はATT Error Response
- Command IDが製品仕様上未対応、現在状態では実行できない、実行中に装置エラーが起きた場合はCommand Response

Valueの長さや形式が不正で、Writeを受け付ける前に判定できる場合はATT Error Responseを返せます。ただし、製品固有の詳細な失敗理由をアプリケーションへ安定して伝える必要があるなら、Command ResponseのStatusへまとめます。

### Request IDで重複実行を防ぐ

ATTのWrite Responseを受け取る前に接続が切れると、クライアントには、サーバーがコマンドを実行したか分からない場合があります。同じRequest IDで再送できるようにすると、サーバーは重複を検出できます。

サーバーは、処理済みRequest IDと結果を一定期間保持します。同じRequest IDと同じCommand ID、Payloadを受け取った場合は、処理を繰り返さず、以前の結果または現在の進行状態を返します。同じRequest IDで異なる内容を受け取った場合は、要求の衝突として拒否します。

Request IDを接続内だけで有効にするなら、再接続後の重複実行は防げません。ボンディング済みクライアントごとに再接続をまたいで有効にするなら、サーバーはクライアントの識別と処理履歴を不揮発メモリーへ保持する必要があります。すべての製品で永続化するのではなく、コマンドの危険性と重複時の影響から決めます。

できる限り、結果の状態を直接指定するコマンドにします。`Toggle LED`より`Set LED State = ON`の方が、再送しても最終状態が同じです。Request IDは、非冪等な操作や、同じ指示を二回実行してはいけない場合に加える仕組みです。

### 同時に実行できるコマンドを決める

最小の実装では、同時に実行できるコマンドを一つに限定できます。処理中に別のCommand Requestを受け取った場合はBusyを返します。これなら、Command Responseが返る順序を管理しやすくなります。

複数のコマンドを並行実行する場合は、Request IDによって各応答を対応づけます。Writeを受け取った順序と、処理が完了する順序は同じとは限りません。MatterのInvoke Interactionでも、非同期処理を含む複数コマンドの応答順は、要求順と異なる場合があります。

コマンド間に依存関係があるなら、クライアントが前のCommand Responseを待って次を送るか、複数の処理を一つのCommandとして定義します。BLEのATTトランザクション順序だけに、製品処理の完了順序を依存させません。

### イベントと現在状態を分ける

Notificationで送られてきたValueが、現在状態なのか、一回限りのイベントなのかによって、取りこぼした場合の意味が変わります。

LED Stateは現在状態です。Notificationを一回取りこぼしても、Readすれば現在のON／OFFへ戻れます。ボタン押下イベントは、発生後にReadしても同じ出来事を再現できない場合があります。すべてのイベントを失えないなら、シーケンス番号、履歴、クライアントからのACKなどが必要です。

NotifyかIndicateかを選ぶ前に、Valueが状態とイベントのどちらを表し、過去の出来事をどこまで保存するかを決めます。IndicationのConfirmationがあっても、アプリケーションがイベントを永続化したことまでは保証しません。

【ファーム開発者の方へ】Writeコールバック内で時間のかかる処理を完了させようとすると、ATTの応答が遅れます。Valueの検証と指示の受付までを同期処理にし、時間のかかる動作は別の処理へ渡せるかを検討してください。アプリケーション側へは、どの応答が受付を表し、どの状態が完了を表すかを伝えます。

ここまでで、Valueをどの方向へ送り、どの位置で応答を得るかを決めました。次節では、送受信するValueのバイト列を、双方が同じ意味に解釈できる形へ定義します。
