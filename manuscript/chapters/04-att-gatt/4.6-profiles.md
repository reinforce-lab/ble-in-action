## GATTプロファイルの実装パターン——標準プロファイルとカスタム設計

<!-- topic: 導入——サービスディスカバリのATTシーケンス -->

これまでの節でATTとGATTの仕組みを積み上げてきました。この節では「実際に使う」視点から、接続後のサービスディスカバリの流れと、プロファイルの設計パターンを見ていきます。

スマートフォンのアプリがBLEデバイスに接続した直後、まず行うのは**サービスディスカバリ**です。「このデバイスはどんなサービスを持っているか」「各サービスにどんなキャラクタリスティックがあるか」を探索します。この探索は、4.3節で学んだATTコマンドを使って行われます。

```
接続確立直後のサービスディスカバリシーケンス（ATTコマンドの流れ）

クライアント                              サーバ
    │                                      │
    │ 1. プライマリサービス一覧を取得       │
    │── Read By Group Type Req ───────────▶│
    │   （type=0x2800, 全ハンドル範囲）     │
    │◀─ Read By Group Type Rsp ────────────│
    │   ← [Battery Svc: 0x0001-0x0004]     │
    │   ← [Device Info: 0x0005-0x000C]     │
    │                                      │
    │ 2. 各サービスのCharacteristicを取得  │
    │── Read By Type Req ─────────────────▶│
    │   （type=0x2803, Battery Svcの範囲）  │
    │◀─ Read By Type Rsp ──────────────────│
    │   ← Battery Level Decl（Props/Handle/UUID）
    │                                      │
    │ 3. ディスクリプタを取得              │
    │── Find Information Req ─────────────▶│
    │   （Battery Level の後ろのハンドル）  │
    │◀─ Find Information Rsp ──────────────│
    │   ← [0x0004, 0x2902]（CCCDあり）     │
    │                                      │
    │ 4. Notifyを有効化                     │
    │── Write Request（CCCD=0x0001） ──────▶│
    │◀─ Write Response ────────────────────│
    │                                      │
    │◀─ Handle Value Notification ─────────│  ← 通知が届き始める
```

この一連のシーケンスは、iOSのCore BluetoothやAndroidのBluetoothGattで`discoverServices()`を呼ぶと内部で実行されています。OSのBLEスタックが面倒を見てくれているだけで、ATTレベルでは上のコマンドが飛び交っています。

## 標準プロファイル——Bluetooth SIGが定義した共通仕様

<!-- topic: SIG標準プロファイルの実例 -->

Bluetooth SIGは多くの標準プロファイルとサービスを定義しています。標準プロファイルを使うメリットは、nRF ConnectなどのツールがUUIDを自動的に名称に変換して表示してくれる点と、対応機器とのInteroperability（相互接続性）が保証される点です。

代表的な3つを見てみましょう。

### Device Information Service（UUID: 0x180A）

機器のメーカー名・モデル番号・ファームウェアバージョンなどを文字列で提供するサービスです。スマートフォンのシステムがデバイス管理のために参照します。

| キャラクタリスティック | UUID | Properties | 内容 |
|---|---|---|---|
| Manufacturer Name String | 0x2A29 | Read | メーカー名（例：Nordic Semiconductor） |
| Model Number String | 0x2A24 | Read | 型番（例：nRF52840-DK） |
| Firmware Revision String | 0x2A26 | Read | ファームウェアバージョン（例：1.2.3） |
| Hardware Revision String | 0x2A27 | Read | ハードウェアリビジョン |

すべてReadのみで、Notifyはありません。起動時に1度読めば十分な静的情報です。

### Battery Service（UUID: 0x180F）

バッテリー残量を提供するサービスです。多くのBLEデバイスに実装されており、スマートフォンのOSがバッテリー残量を表示するために標準的に参照します。

| キャラクタリスティック | UUID | Properties | 内容 |
|---|---|---|---|
| Battery Level | 0x2A19 | Read, Notify | 0〜100（%）のuint8値 |

CCCDを持ち、Notifyが可能です。残量変化をアプリがリアルタイムで受け取れます。

### Heart Rate Service（UUID: 0x180D）

心拍計の標準プロファイルです。Heart Rate Measurementキャラクタリスティックは必須でNotifyを使い、計測値をリアルタイムに送信します。

| キャラクタリスティック | UUID | Properties | 内容 |
|---|---|---|---|
| Heart Rate Measurement | 0x2A37 | Notify（必須） | フラグ1B＋心拍数（uint8 or uint16） |
| Body Sensor Location | 0x2A38 | Read | 装着位置（胸 / 指 / 手首など）のenum |
| Heart Rate Control Point | 0x2A39 | Write | エネルギー消費カウンタのリセット命令 |

Heart Rate Measurementはフラグバイトによって値が可変フォーマットになっています。bit0が0なら心拍数はuint8（1バイト）、bit0が1ならuint16（2バイト）です。標準プロファイルの仕様書を読む習慣が重要なのは、このような細かい規定があるためです。

## キャラクタリスティック設計の3分類

<!-- topic: 設計パターンの3分類 -->

カスタムプロファイルを設計するとき、キャラクタリスティックは用途によって3種類に分類できます。この分類を意識するとPropertiesの設定が迷いなく決まります。

### 分類1：外部センサー値（センサーが測るもの）

デバイスが計測・観測した値です。クライアントが定期的に読むか、変化したときに通知を受ける典型的なパターンです。

- **Properties**: Read + Notify（または Indicate）
- **Permission**: Read可、Write不可
- **例**: 気温、湿度、加速度、バッテリー残量

### 分類2：デバイス内部状態（設定・動作状態）

デバイスの現在の動作モードや設定値です。クライアントが参照するだけでなく、書き込んで設定変更することもあります。

- **Properties**: Read + Write（状態参照のみなら Read のみも可）
- **Permission**: Readのみ、またはRead + Write
- **例**: 測定間隔、通知の閾値設定、デバイス名

### 分類3：コントロールポイント（操作指示）

デバイスに対する「命令」です。読み取る意味がなく、書き込むだけです。

- **Properties**: Write（応答が必要なら）または Write Without Response（操作が頻繁なら）
- **Permission**: Writeのみ
- **例**: デバイスリセット、LEDのON/OFF、工場出荷時設定に戻す

ReadとWriteを両方持たせてしまいがちですが、コントロールポイントにReadは不要で、センサー値にWriteは不要です。用途と分類を明確にしてからPropertiesを設定するのが設計の鉄則です。

## 設計例：懐中電灯サービス

<!-- topic: 具体的なカスタムサービス設計 -->

3分類を使って、懐中電灯デバイスのカスタムサービスを設計してみましょう。

**機能要件**: スマートフォンのアプリから懐中電灯のON/OFFを制御でき、現在の点灯状態と明るさセンサーの値をアプリで確認できる。

**GATTサービスの設計**:

| キャラクタリスティック | 分類 | Properties | 内容 |
|---|---|---|---|
| FlashLight Switch | コントロールポイント | Write Without Response | ON=0x01, OFF=0x00 の書き込み |
| FlashLight Status | 内部状態 | Read | 現在の点灯状態（ON/OFF） |
| Light Sensor | センサー値 | Read + Notify | 照度センサーの値（uint16, lux単位） |

加えて、Battery Serviceを別サービスとして追加することで、バッテリー残量監視も実現できます。Battery ServiceはSIG標準なので再実装は不要です。

**ATTテーブルとして具体化**:

```
Handle | UUID   | 値の内容
0x0001 | 0x2800 | FlashLight Service UUID（カスタム128bit）
0x0002 | 0x2803 | FlashLight Switch Decl（Properties=Write WoR, Handle=0x0003）
0x0003 | Custom | FlashLight Switch Value（Write Only, 1B）
0x0004 | 0x2803 | FlashLight Status Decl（Properties=Read, Handle=0x0005）
0x0005 | Custom | FlashLight Status Value（Read Only, 1B）
0x0006 | 0x2803 | Light Sensor Decl（Properties=Read|Notify, Handle=0x0007）
0x0007 | Custom | Light Sensor Value（Read, uint16, lux）
0x0008 | 0x2902 | CCCD for Light Sensor（Notify購読設定）
0x0009 | 0x2800 | Battery Service UUID（0x180F）← 標準サービスを再利用
0x000A | 0x2803 | Battery Level Decl
0x000B | 0x2A19 | Battery Level Value
0x000C | 0x2902 | CCCD for Battery Level
```

FlashLight SwitchはWrite Without Responseです。LEDのON/OFFは操作ごとの応答確認よりも低遅延が優先されるため、CommandパターンのWrite Commandが適切です。Light SensorはNotifyを持つため、照度が変化したときだけアプリに通知でき、クライアントによるポーリング（定期的なReadの繰り返し）が不要になります。

---

> **エピソード：nRF Connectでサービスを読む**
>
> スマートフォンに `nRF Connect for Mobile`（Nordic Semiconductorが無料公開しているBLEデバッグアプリ）をインストールすると、BLEデバイスのATTテーブルをGUIで確認できます。
>
> デバイスに接続すると、サービスとキャラクタリスティックの一覧がツリー状に表示されます。UUID横の▼アイコンをタップすると Read Request が発行され、バリューが表示されます。🔔アイコンをタップするとCCCDに0x0001が書き込まれてNotifyが有効化されます。第2章で「操作」として説明したことが、ATTコマンドとして発行されているのがログ画面で確認できます。
>
> Device Information Serviceが存在するデバイスであれば、Manufacturer Name（0x2A29）を読んでみましょう。Nordic製品なら"Nordic Semiconductor"と表示されます。nRF Connectは標準SIG UUID（0x180A, 0x2A29など）を名称で表示し、カスタムUUIDは128ビットの生の値で表示します。自分が実装したカスタムサービスがこのツールで正しく表示されるかを確認することが、BLEデバイス開発の基本的なデバッグ手順の一つです。
