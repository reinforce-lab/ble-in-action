## プロファイルを実装間の共通仕様にする {#sec:gatt-profile-contract}

GATTは、ServiceとCharacteristicをATTデータベースへ表し、発見して操作する共通の仕組みを定めます。しかし、GATTだけでは、心拍センサー、キーボード、温度計がそれぞれ何を公開し、どの順序で動くかは決まりません。

同じ利用場面を複数の実装で共有するには、採用するServiceとCharacteristic、Value形式、Procedure、役割、エラー時の振る舞いまでを共通仕様にします。Bluetooth SIGが発行するProfile SpecificationやService Specificationは、この契約を標準化したものです。

### Profile、Service、Characteristicの仕様を組み合わせる

標準Profileを実装するときは、Profile Specificationだけで完結するとは限りません。Profileが参照するService Specification、Characteristic Specification、GATT Specification Supplementなどを組み合わせて読みます。

それぞれが担当する内容は異なります。

| 仕様 | 主に定める内容 |
|---|---|
| Profile Specification | 機器の役割、利用するService、接続やProcedureの要件 |
| Service Specification | Serviceに含むCharacteristic、必須／任意、Service内の振る舞い |
| Characteristic Specification | Characteristic Valueのフィールドと意味 |
| Core SpecificationのGATT | ServiceとCharacteristicの表現、Discovery、Procedure |
| Core SpecificationのATT | Attributeを操作するPDUとプロトコル |

: GATT関連仕様の役割 {#tbl:ch4-gatt-specification-roles}

たとえば、あるCharacteristicのValue形式だけを実装しても、Profileが要求する役割やProcedureを満たすとは限りません。反対に、Profile名だけを見ても、受け取ったValueの各ビットは解釈できません。規格文書の参照関係をたどる必要があります。

### 標準Serviceを再利用する

製品の機能が標準Serviceの意味と一致するなら、その仕様を利用できます。Battery Serviceを採用すると、Battery LevelのUUID、Value形式、Properties、振る舞いを、対応するクライアントと共有できます。

標準Serviceを使う利点は、16 bit UUIDで通信量を減らせることだけではありません。異なるメーカーの実装が、同じ意味と手順を共有できることです。

名前が似ているだけの独自データを、標準CharacteristicのUUIDで公開してはいけません。単位、範囲、更新条件、Procedureなど、参照する仕様の要件を満たす必要があります。要件が合わない場合は、製品固有のCharacteristicとして定義します。

### 標準部分と製品固有部分を共存させる

一つのGATTサーバーは、複数のServiceを公開できます。センサー付きライトは、Device Control Serviceに加えてBattery ServiceやDevice Information Serviceを公開できます。

標準Serviceだけを知る汎用アプリケーションは、電池残量や製品情報を利用できます。専用アプリケーションは、それらに加えてDevice Control Serviceを探索し、LEDとセンサーを操作できます。

カスタムServiceを追加しても、採用した標準ProfileやServiceの要件がなくなるわけではありません。標準部分の必須Characteristic、Properties、Procedureを保ったまま、製品固有の機能を別のUUIDで追加します。

### カスタムGATTインターフェース仕様を作る

Bluetooth SIGが標準Profileを定めていない製品機能は、開発者がServiceとCharacteristicを定義できます。本書では、この製品固有の取り決めをカスタムプロファイルと呼んできました。

正式なBluetooth SIGのProfile Specificationと混同しないため、開発プロジェクト内では「GATTインターフェース仕様」など、文書の位置づけが分かる名前を付けます。

センサー付きライトのGATTインターフェース仕様には、少なくとも次を記載します。

| 項目 | 記載する内容 |
|---|---|
| Service | UUID、役割、対応する仕様版 |
| Characteristic | UUID、役割、Properties |
| Semantics | 現在状態、設定値、処理の指示、イベントのどれを表すか |
| Access | Read／WriteのPermission、必要なセキュリティ |
| Value | 長さ、フィールド、バイトオーダー、単位、予約値 |
| Procedure | Read、Write、Notifyなどの利用順序 |
| Completion | 受付、処理中、完了、失敗の区別 |
| Command | Command ID、Request ID、引数、応答、重複実行時の振る舞い |
| Error | ATT Errorと製品Statusの使い分け |
| Lifecycle | 接続直後、購読後、切断後の状態 |
| Compatibility | 追加と変更の規則、未対応時の振る舞い |

: カスタムGATTインターフェース仕様に記載する項目 {#tbl:ch4-custom-gatt-contract}

Characteristicの一覧だけでは、操作の契約として不足します。たとえばLED Controlに`0x01`を書くとき、次も決めます。

- Write RequestとWrite Without Responseのどちらを許すか
- すでにONの場合に同じ値を書くとどうなるか
- 不正な値にはどのErrorを返すか
- Write Responseは受付と完了のどちらを表すか
- LED Stateはいつ更新され、いつNotifyされるか
- 切断中に状態が変わった場合、再接続後にどう同期するか

これらを決めると、ファームウェアとアプリケーションを別の担当者が実装しても、同じ結果を検証できます。

### 仕様の版と機器の能力を知る

GATTインターフェースを更新するときは、ファームウェアとアプリケーションの組み合わせが同じ版になるとは限りません。古いアプリケーションが新しいファームウェアへ接続し、新しいアプリケーションが古いファームウェアへ接続します。

アプリケーションが利用前に対応可否を判断できるように、次の方法を組み合わせます。

- ServiceやCharacteristicの有無を探索する
- Feature Characteristicで対応機能をビットとして公開する
- 仕様バージョンをReadできるようにする
- Value形式にバージョンを含める
- 未対応のOpcodeや値に明確なエラーを返す

バージョン番号だけで能力を推測すると、製品派生や一部機能の無効化へ対応しにくくなります。実際に必要なCharacteristicやFeatureを確認する方が確実です。版番号は、Value形式や仕様書を対応づけるために使います。

### 仕様から試験条件を作る

GATTインターフェース仕様は、実装方法だけでなく、ファームウェアとアプリケーションの結合試験にも使います。

LED Controlについて、次の試験を導けます。

- 暗号化された接続から`0x01`をWriteすると受け付ける
- 暗号化されていない接続からのWriteは規定したATT Errorになる
- 予約値をWriteすると値のエラーになる
- Write Responseの後、LED Stateが規定した順序でNotifyされる
- 同じ操作を再送しても最終状態が変わらない
- 通知を購読していないクライアントへはNotificationを送らない
- 再接続後にReadすると現在状態へ同期できる

パケットキャプチャでは、Write Request、Write Response、Notification、Handle、Valueを仕様と照合できます。アプリケーションログでは、OS APIから見えたCharacteristicとValueを確認できます。製品の動作、GATTの契約、ATT PDUを同じ試験条件へ結び付けられます。

【ホビーストの方へ】最初から専用アプリケーションを作らなくても、汎用のBLE探索アプリケーションをGATTクライアントとして利用できます。Service、Characteristic、Properties、Value形式を先に決め、Read、Write、Notifyを手動で確認すると、ファームウェア側の契約を小さく試せます。
