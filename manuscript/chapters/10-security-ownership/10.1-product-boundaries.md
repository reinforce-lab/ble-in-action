## 10.1 責任境界と製品状態を共有する {#sec:ch10-product-boundaries}

BLE製品の動作には、複数の実装と仕様が関わります。問題が起きたときに「BLEが失敗した」とまとめると、どの担当が何を確認すべきか分かりません。まず、責任境界を分けます。

| 境界 | 主に決めること | 観測する例 |
|---|---|---|
| Bluetooth仕様 | Advertising、接続、ATT、暗号化の手順 | ATT Error、切断理由、暗号化状態 |
| ファームウェア | GATT Value、製品状態、Bootloaderとの連携 | Request受付、状態遷移、Reset Reason |
| OS API | 権限、接続ライフサイクル、Callback | API Error、接続状態、購読結果 |
| アプリケーション | 利用者操作、再試行、表示、データ保存 | 画面状態、Request ID、選択した製品 |
| 製品運用 | 所有者、配布Version、回収、サポート | アカウント、配布履歴、問い合わせ記録 |

同じ処理でも、境界ごとに完了の意味が違います。Write Responseは、ATTサーバーがWrite Requestを受け付けたことを示します。モーターが目標位置へ到達したことや、設定を不揮発メモリーへ保存したことまでは示しません。OTAの進捗が100%になっても、新しいイメージで起動し、自己診断を通過し、Confirmされたとは限りません。

### 製品状態をAPI状態から分ける

アプリケーションでは、OS APIの状態をそのまま製品状態にしません。次のように、利用者が行いたい処理の段階を定義します。

```text
利用不可
  ↓ Bluetooth利用可能
発見中
  ↓ 対象を選択
接続中
  ↓ Service／Characteristic確認
同期中
  ↓ 初期ReadとNotify購読
利用可能
  ↓ 要求を送信
処理中
  ↓ 製品から結果を受信
完了
```

切断は、どの段階からも起こり得ます。再接続後に`利用可能`へ戻るには、以前のCharacteristic参照を使い回すのではなく、接続、探索、初期同期を進め直します。ファームウェア側も、接続が切れたときに処理を中止するのか、処理だけを継続して結果を後から読めるようにするのかを決めます。

### 横断できる識別子を持つ

両側の記録を結ぶには、時刻だけでは足りません。スマートフォンとマイコンのClockは一致せず、再起動でマイコンの時刻が戻る場合もあります。次の識別子を製品仕様へ含めます。

- Request ID: どの要求に対する結果か
- Sequence: 測定値やイベントの欠落、重複、順序を判断する
- Protocol Version: Value Formatの互換性を判断する
- Firmware VersionとBuild ID: どの実装が動作していたか
- Boot IDまたは起動回数: 再起動をまたいだログを区別する

秘密鍵、Pairingで得た鍵、個人情報を識別子代わりにログへ残してはいけません。問い合わせに必要な識別子と、攻撃者や第三者へ見せてはいけない情報を分けます。

責任境界と製品状態は、デバッグ資料だけに置くものではありません。GATTプロファイル仕様、アプリケーションの状態管理、試験項目が同じ状態名と識別子を使うことで、片側だけが正常と判断する状況を減らせます。
