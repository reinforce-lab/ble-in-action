### 7.3.2 設定とコマンドを製品動作へ反映する {#sec:ch7-command-state}

第6章ではCommand RequestをWork Queueへ渡しました。本章では、コマンドを製品の状態遷移として処理します。

#### 7.3.2.1 受付可能な状態を決める

同じOpcodeでも、現在状態によって受付可否が変わります。

```text
IDLE ── Start Measurement ──> MEASURING
  ↑                              │
  └──── Complete／Error ─────────┘
```

MEASURING中に同じ要求を受けた場合は、拒否、予約、既存処理への参加のどれかを仕様として決めます。ATT ErrorはValue形式や現在の受付可否に使えますが、受付後のセンサー失敗はCommand ResponseのStatusで返します。

#### 7.3.2.2 Request IDで非同期処理を対応づける

製品ロジックは、OpcodeだけでなくRequest IDも処理状態へ保持します。

```c
struct product_command {
    uint8_t opcode;
    uint8_t request_id;
    uint16_t argument;
    int64_t accepted_at_ms;
};
```

完了時に同じRequest IDをCommand Responseへ入れることで、クライアントはWrite Responseより後に届く結果を要求と対応づけられます。再接続や再送を扱う製品では、最近処理したRequest IDと結果も一定期間保持します。

#### 7.3.2.3 設定変更を一度に反映しない

Measurement IntervalのWriteが成功しても、すでに動作中のタイマーをいつ変更するかを決める必要があります。

- 現在の周期を終えてから新設定を使う
- Write受付時点で再予約する
- 次回起動時から適用する

設定Value、実際に適用中の値、永続化済みの値を区別すると、電源断や更新後の振る舞いを説明できます。
