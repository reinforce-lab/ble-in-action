## 7.9 変更して再測定する {#sec:ch7-remeasure}

原因候補を絞ったら、一度に一つの要因を変更し、同じ条件で再測定します。

### 7.9.1 改善と副作用を同時に見る

Advertising間隔を長くすると平均電流は下がりますが、発見時間は長くなります。接続間隔を短くすると応答は速くなりますが、radio eventが増えます。Notifyをまとめると効率は上がりますが、最新値の遅延が増えます。

| 変更 | 改善を期待する値 | 同時に確認する値 |
|---|---|---|
| Advertising間隔を延ばす | 待機電流 | 発見時間 |
| 接続間隔を延ばす | 接続中電流 | command latency |
| Notifyをまとめる | packet効率 | data latency |
| sensorをpower down | 待機電流 | 起動時間、初回値 |
| logを減らす | 処理時間、電流 | 調査可能性 |

: 変更と副作用の例 {#tbl:ch9-change-tradeoff}

### 7.9.2 証拠を再現可能な形で残す

- hardware revision
- firmware commitとbuild設定
- SDK、tool、OS version
- 電源電圧、距離、電波条件
- 操作手順と試行数
- raw capture、log、PPK2 data
- 集計方法と除外条件

結論だけでなく元データを残すと、別の担当者が同じ判断を検証できます。

第5章で選んだ構成を、第6章で通信へ、本章で製品動作と更新へ具体化し、要求と照合しました。以後のプラットフォーム章では、同じGATTインターフェースをiOS、Web、Android、Linuxから利用し、各OS固有の観測点と制約を加えます。

### 7.9.3 Notifyが遅い問題を切り分ける

「センサー値の表示が遅い」という症状を例にします。

1. GPIO markerで測定開始と完了を記録します。
2. System EventでMeasurement Workの開始と終了を確認します。
3. packet captureでNotificationの送信時刻を確認します。
4. クライアントログでOS callbackと画面更新を確認します。

測定完了からNotificationまでが長ければfirmware内部、NotificationからOS callbackまでが長ければ通信またはplatform、callbackから画面までが長ければapplicationを調べます。「BLEが遅い」という一つの原因へまとめません。

### 7.9.4 待機電流が高い問題を切り分ける

期待したSystem ON idleよりbaselineが高い場合は、周期的peakと一定の底上げを分けます。

- 周期的peak: timer、Advertising、接続event、polling
- 一定の底上げ: sensor、LED、regulator、pull-up、debug interface
- 不規則なpeak: retry、log、Flash、外部割り込み

firmwareから周辺機器を一つずつ停止し、同じ測定窓で比較します。SoCの推定値と基板全体の実測値の差には、外付け回路が含まれます。

### 7.9.5 更新後に元へ戻る問題を切り分ける

転送完了後に旧versionで起動した場合は、転送を繰り返す前に次を確認します。

1. Secondary Slotのimage IDとhash
2. MCUbootが選んだswap／boot state
3. 新イメージが起動した時刻とreset reason
4. Confirm処理を実行したか
5. Watchdogまたは自己診断でresetしたか

packet captureはSMP転送完了までを示せますが、その後のBootloader判断は示しません。Bootloaderログと更新状態を組み合わせます。
